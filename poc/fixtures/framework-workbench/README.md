# 服务申请业务案例

这套合成案例用于检验系统能否从源码回答业务问题：申请何时被接受、何时需要人工复核、哪些申请可以生效，以及失败后哪些结果仍不能确认。主线是“申请受理 → 人工复核 → 夜间生效”；框架控制方式只是这些规则的实现背景。

页面导读是依据现有合成源码预先编写的说明，不是模型分析结果。只有接入源码并发起分析后，才会产生本次模型回答。案例没有执行 COBOL、连接数据库或模拟真实业务办理。

## 三个案例回答什么

| 案例 | 核心业务问题 | 源码支持的解释 |
| --- | --- | --- |
| 申请受理与金额分流 | 什么金额可以受理，何时转复核？ | 金额须大于零；不超过 5000 拟设为已批准，超过 5000 拟设为待复核；取消跳过保存，保存失败走错误处理。源码未定义币种。 |
| 人工复核与决定保存 | 怎样明确通过或拒绝，决定影响什么？ | 金额须大于零且须有明确决定；通过拟保存为已批准，拒绝拟保存为已拒绝，同时保存当前金额。取消或保存失败不能算复核完成。 |
| 已批准申请的夜间生效 | 哪些申请生效，结果怎样核对？ | 只有服务类别且已批准才进入生效处理；更新前再次核对条件，保存成功才增加本轮生效数，提交成功才推进已提交进度。 |

三个案例共同讲解业务流程，但它们是独立的合成入口。受理与复核使用不同的示例申请标识，没有证明两者在一次真实运行中衔接为同一笔申请；也没有提供真实候选清单或实际夜间执行时间。复核权限、人员角色和完整业务制度不能从这里推定。“生效”只表示申请状态变化，不表示实际服务已经开通或发生资金划拨。

## 从条件追到结果

受理先请求取得申请，并准备后续修改所需的暂存记录。只有输入被接受才进入保存处理；金额不合法时要求重新输入，取消则不保存。金额不超过 5000 与超过 5000 对应不同的拟保存状态。后续去向优先处理错误，其次处理取消；没有这些情况时，待复核申请指向复核，其余指向申请摘要。源码能够说明这个去向决定，不能证明实际页面已经跳转。

复核围绕申请编号和金额进行。正金额加明确的通过或拒绝决定，才满足可见的业务校验；没有有效决定需要重新输入。更新先请求锁定记录，返回成功后设置决定对应的状态和当前金额，再请求保存。这里需要区分“决定已经填入记录”与“保存已返回成功”；实际存储实现没有包含在案例中，不能进一步保证决定已经持久保存，也不能断言并发修改一定得到正确处理。

夜间处理先判断类别与状态，只有服务类别且已批准的申请才有资格转为生效。更新前再次确认资格，防止仅依据之前读到的条件继续修改；条件已经改变时跳过并请求释放记录。成功保存才增加本轮生效数。其余申请增加跳过数，不在这里改变申请状态。

## 失败与再次运行怎样解释

夜间处理分别统计已读取、已生效和已跳过的数量。每成功读取两笔就尝试提交一次，包含随后被跳过的申请；末尾不足两笔的剩余结果也会尝试提交。因此，读取数、提交次数和生效数不是同一个业务指标。

提交前先请求保存最后读取的申请标识和三类累计数量，成功后才请求提交申请修改。只有提交也返回成功，才更新本次运行记住的已提交进度。保存返回成功增加的本轮生效数，在提交之前仍不能视作已经完成的最终数量。

出现错误时，程序先把统计恢复到上次提交时记住的数量，再请求撤销未提交修改；撤销失败会记录新的错误。计数已经恢复，并不表示申请数据已成功撤销。重启时可以请求恢复已保存的统计，但后续仍从首笔请求读取；没有实现按申请标识接续的逻辑，不能保证再次运行不会重复处理。实际候选清单是否排除已生效记录，以及保存的进度与业务数据是否一致，仍需补充实现确认。

## 哪些业务结论仍缺少依据

| 未提供的材料 | 对业务解释的影响 |
| --- | --- |
| 实际存储、暂存与锁定处理 | 可以解释拟保存哪些字段以及失败分支，不能确认保存已持久完成、暂存记录可正确取回，或多人同时修改时不会互相覆盖。 |
| 完整表单校验与权限配置 | 可以解释正金额和明确复核决定这两项可见条件，不能把它们说成全部办理要求，也不能指定谁有权受理或复核。 |
| 候选清单形成规则与实际调度 | 可以解释读到一笔申请后如何筛选，不能证明所有符合条件的申请都会被处理，或处理会在某个真实时间运行。 |
| 提交、撤销与进度恢复的实现 | 可以解释请求顺序和统计变化，不能仅凭数量认定数据全部提交或撤销，也不能保证再次运行没有重复或遗漏。 |

缺少这些材料不妨碍解释源码中已有的条件与影响。模型应把能确认的业务规则说清楚，再说明未知事项会影响哪一种业务结论，而不是把整份回答停留在技术边界清单。

## 证据与入口

`manifest.json` 包含简体中文、繁体中文和英文的案例问题、导读步骤与说明。每个步骤保留实际源码锚点；程序名、文件路径和源码不翻译。源码使用中性名称，包含 4 个程序和 7 个共享文件。

| 案例标识 | 分析入口 | 主要源码 |
| --- | --- | --- |
| `online` | `SERVICEENTRY` | `source/programs/service-entry.cbl` |
| `client_server` | `SCREENCONTROL` | `source/programs/screen-control.cbl` 与 `source/programs/service-mainline.cbl` |
| `batch` | `NIGHTBATCH` | `source/programs/night-batch.cbl` |

核对证据时，已批准、待复核、已拒绝、生效分别对应源码状态 `APPROVED`、`REVIEW`、`REJECTED`、`ACTIVE`；服务类别对应 `SERVICE`。外部存储、页面、表单验证与进度保存对象只有请求位置，没有附带实现。技术调用和控制阶段用于定位依据，不应取代业务结论。

## 在工作台验收

1. 切换三个案例，确认问题围绕受理、复核与生效，并打开导读引用核对实际文件、行号和源码。未发起分析时，应明确显示预写导读，不能宣称模型已完成分析。
2. 接入案例源码并发起分析。模型应读取本次实际源码，回答受理金额条件、超限去向、复核决定及取消或保存失败的影响；每项判断应能回到相应引用。
3. 对夜间案例追问“为什么这笔申请会被跳过”和“读取两笔是否等于生效两笔”。回答应区分类别与状态条件、读取数、保存成功数和提交后的进度，不应把实际服务开通或资金变化补写进结论。
4. 追问“中途失败后，哪些结果已完成；再次运行是否会重复”。回答应解释恢复统计、请求撤销与实际数据状态之间的差别，明确接续位置和避免重复仍缺少依据。
5. 在源码副本中将阈值改为 4000，或改变生效资格状态，再重新接入。新回答应依据新快照解释规则，不能继续复用旧答案或旧引用。
6. 用下方大文件副本提问“末尾金额条件如何决定申请状态”。检查模型是否找到末尾规则、引用是否正确，以及未阅读范围是否如实显示。

可从项目根目录使用同一分析入口；Windows 将 `python3` 改为已安装的 `python` 即可：

```text
python3 poc/analyze_source.py --source poc/fixtures/framework-workbench/source --entry SERVICEENTRY --analysis-mode business --question "申请金额需要满足什么条件，何时转复核，取消或保存失败时会怎样？" --output .poc-data/framework-online --allow-network
```

其他案例将入口替换为 `SCREENCONTROL` 或 `NIGHTBATCH`，并使用不同输出目录。模型调用需要已配置的获准接口；省略 `--allow-network` 可先核对源码接入，但不会产生本次模型分析结果。

## 可选的大文件副本

不把八万行重复源码放进默认案例。下面的 PowerShell 片段在独立目录生成 `LARGEREVIEW`，关键业务条件位于末尾，默认工作台案例不受影响。它只用于阅读覆盖和引用验证，不是生产性能基准或可执行业务系统。

```powershell
@'
from pathlib import Path
root = Path('.poc-data/framework-large-source')
root.mkdir(parents=True, exist_ok=True)
head = [
    '       IDENTIFICATION DIVISION.',
    '       PROGRAM-ID. LARGEREVIEW.',
    '       DATA DIVISION.',
    '       WORKING-STORAGE SECTION.',
    '       01 REQUEST-AMOUNT PIC 9(7)V99.',
    '       01 WORK-AMOUNT PIC 9(7)V99.',
    '       01 REQUEST-STATE PIC X(12).',
    '       PROCEDURE DIVISION.',
    '       MAIN-ROUTINE.',
]
tail = [
    '       FINAL-DECISION.',
    '           IF REQUEST-AMOUNT <= 5000',
    '               MOVE "APPROVED" TO REQUEST-STATE',
    '           ELSE',
    '               MOVE "REVIEW" TO REQUEST-STATE',
    '           END-IF',
    '           GOBACK.',
]
filler = ['           MOVE REQUEST-AMOUNT TO WORK-AMOUNT']
lines = head + filler * (80000 - len(head) - len(tail)) + tail
target = root / 'large-review.cbl'
if target.exists():
    raise SystemExit('Use a new output directory; source already exists.')
target.write_text('\n'.join(lines) + '\n', encoding='utf-8')
print(target.resolve())
'@ | python -
```

把生成目录作为本机源码接入并选择 `LARGEREVIEW`。Linux/macOS 可将同一段 Python 内容保存为临时脚本运行。这里不附任何预置模型结论。
