# 聚焦 Bitbucket 源码分析，冻结本地分析并隔离新链路

2026-11-07，用户明确后续聚焦 Bitbucket Cloud 源码分析。源码由 AS400 每周同步，目标是避免每台电脑先下载完整源码并建库，且不购买新增常驻服务器。用户要求先做设计和可行性分析，同时保持现有本地源码分析不作修改。

**已接受的决定是研发方向和隔离边界，不表示技术方案已经验收。** 用户随后明确授权“开始设计和修改”，实施范围保持隔离。以 `b49173b0065386658c3ba253a9c887989f403cb6` 为设计检查基线，冻结本地接入/更新、解析与索引、问答、恢复、历史、引用、导出、设置及相关数据语义；新 Bitbucket 能力采用独立来源、资料查询、证据会话、调查编排和状态。允许原样调用已有能力；共享外壳只容纳明确的远程分流，不借机重构本地核心或修改公共默认行为。

推荐验证“周期离线预计算、在线版本化分片、客户端按需调查与源码核验”。技术方案仍是[设计草案](../19-bitbucket-online-analysis-design.md)，执行环境、长期存储、资料格式、问答复用程度及 GB 级性能有待验证。当前整份 SQLite 包含源码页并绑定本机路径，不能把下载它等同于免整库下载；Bitbucket 文件托管也不等于远程查询服务。

## 取舍与后果

统一抽取来源层并重构原问答链可能减少重复实现，却会让本地行为、缓存身份和恢复流程一起变化，因此本阶段不采用。独立远程适配增加接口对照和两条链维护成本，换取本地能力与数据的稳定边界；冻结不表示本地实现无缺陷或已经完成发布验收。

后续若发现必须改本地核心，应记录耦合和替代方案，先由用户另行决定是否调整范围。不能修改原测试来适配远程，也不能静默迁移本地资料库。旧 Bitbucket 本机快照入口保留，不自动转成新在线模式。

初次记录只确定设计、可行性和工作约束；后续授权已落实为[独立源码模块与合成验证](../../specs/online-analysis-material.md)，仍未部署、上传企业源码、启用新模型、运行流水线或构建应用。既有授权与正式发布验收规则继续有效。后续实施顺序与退出标准以设计中的 D1–D5 为准，不因本文状态为 accepted 就将待验证项视为已完成。
