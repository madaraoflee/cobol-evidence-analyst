Main conclusion
The online implementation is a bounded, model-directed lexical/source investigation, not an exhaustive formula inventory. There are two separately reproducible defects around known unfinished work, in addition to the absent inventory capability. These do not establish which exact failure occurred on the user's company dataset, and a useful partial answer is not itself a defect.

1. Confirmed defect: known unfinished global-search work can be silently completed.
Synthetic input contains 27 indexed files; 25 contain PREMIUM, one uses PRM-AMT and calls another arithmetic program. The first search correctly returns 20/25, truncated=true, next_offset=20. The scripted model reads only premium_00.cbl, explicitly leaves '24 candidate files remain unverified', then returns complete=true with remaining=[] and one valid citation. The runner accepts status=answered, error=null after 3 model calls and 2 actions. The actual OnlineWorkbench completion path then sets pending=None. The API therefore loses the continuation checkpoint for an explicitly unfinished exhaustive request.
Code: poc/online_investigation.py:678-680 replaces remaining with each model response; :686-697 accepts a final answer based on citation membership and the model's complete/remaining flags, with no outstanding-search/work check. poc/online_workspace.py:696-699 removes pending on answered.
This is demonstrated with deterministic replies to test acceptance, not a claim that a real model necessarily chooses those replies.
Minimum direction: retain a separately structured ledger of in-scope unfinished work (search cursor, discovered candidate files/occurrences, pending source ranges and relationship expansion). A final answer must either discharge each item with evidence/reason or remain partial and resumable. Do not make every broad lexical match mandatory for unrelated narrow questions; scope/exclusion decisions need explicit representation.

2. Confirmed defect: unfinished search cursor falls out of the model context and eventually durable state.
The model is initially told total_matches=25, truncated=true and next_offset=20. After it performs 13 distinct reads with action responses omitting remaining, the next prompt contains only the latest 12 observations: no search observation/cursor, remaining=[], observations_omitted=2. The full checkpoint still has the first search at this stage, but no observation-recall tool is available; recall/evidence_catalog only address read source evidence. In a second run the harness explicitly resumes default-budget investigations five times, accumulating 98 actions. The checkpoint keeps only 96 observations, the still-unpaged initial search is deleted there too, and no structured unfinished-work record replaces it. All 97 read evidence pages remain, so this is specifically lost work/navigation, not evidence deletion in this reproduction.
Code: poc/online_investigation.py:231-234 defaults missing remaining to []; :345-350 retains 96 observations and at most 512000 encoded bytes; :565-568 sends only 12 observations plus an omitted count; :416-425 can recall only evidence, not old search work. :679-680 overwrites the free-text remaining list.
Minimum direction: do not use the observation display window as the sole unfinished-work storage. Persist a small structured task ledger independently, always include unresolved summaries/cursors, and allow recovery of old observations where necessary. Preserve completed results and evidence separately; increasing the window alone only postpones loss.

3. Product capability gap, not an index omission proven by this fixture.
Only search, relations, incoming, read, recall and evidence_catalog are available. There is no file inventory, formula candidate/rule listing or occurrence iterator. _action rejects files/rules/formula_candidates with ONLINE_INVALID_MODEL_ACTION. The material actually contains the abbreviated file's COMPUTE rule with reads BASE-AMOUNT/RATE-VALUE and write PRM-AMT. Searching premium excludes it; searching compute finds it. Thus keyword mismatch can miss a business formula even though its arithmetic fact and source are present. It is incorrect to say this fixture proves the parser failed to index the arithmetic.
Code: poc/online_investigation.py:58-69 and :159-165 tool surface. poc/online_material_export.py:157-164 exports business_rules, and :208-216 indexes all verified source lines. poc/online_material_reader.py:277-296 exposes rules only internally. poc/online_material_query.py:220-228 returns relations, dropping the rules from its public operation; there is no corresponding rule operation. poc/online_material_query.py:168-217 is any-term lexical file ranking, not semantic formula search.
Static CALL/COPY relations can be paged after a path/target is known; expansion is model-directed. Reverse routes only support CALLS and INCLUDES_COPY (online_material_query.py:233-241). No automatic exhaustive graph worklist exists. Dynamic/name ambiguity is deliberately preserved, not established runtime linkage.
The existing prompt explicitly defines complete as answering from stated evidence, never repository-wide/runtime completeness (online_investigation.py:79-85), and the manifest advertises indexed_snapshot_only / sparse semantics / unexported occurrence details (online_material_export.py:308-335). Deleting that instruction would remove honesty, not add coverage. A real exhaustive capability needs a selected-snapshot inventory, arithmetic candidate/occurrence traversal, business-concept and dependency mapping, and a reconciled coverage ledger; runtime business proof remains a separate boundary.

- Default one question/resume runs at most6 model calls or24 actions, with at most8 actions per model response. Reproduced both limits: model budget returns needs_continuation/ONLINE_MODEL_BUDGET_EXCEEDED; action budget preserves premium_24.cbl as pending and returns needs_continuation/ONLINE_ACTION_BUDGET_EXCEEDED. What the model knows
Initially: selected repository/revision, indexed file count/input coverage boundaries, lexical total/truncation/cursor, requested remaining text and any read evidence.
After observation-window eviction: omitted observation count remains, but it does not identify the omitted query/cursor/tasks. Read evidence and a bounded evidence catalog remain accessible. full_repository_or_runtime_proof is always false; indexed_files and input_coverage_complete describe material input, not which candidates the current investigation has checked.
