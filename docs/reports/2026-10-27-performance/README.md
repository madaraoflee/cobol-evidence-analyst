# 同机性能修复与离线等价验证

本次不通过缩小源码范围、减少证据、放宽检查或固定时间截断提速。修改集中在消除同一分析过程中的重复计算，导入路径、历史格式、数据库结构和请求限额保持不变。

## 为什么上一次耗时不能直接归因于代码

此前两个 Windows 原生报告来自不同托管机器。两个包的 Python、编译器与依赖版本相同，但这不能保证 CPU、磁盘和负载相同。修复前先在同一 Mac、同一 Python 上串行比较 `56050b8`、`3628a05` 和优化版，三个版本按 ABC/BCA/CAB 轮换顺序，分别创建全新索引。

324 个文件、约十万行（含一个 25,000 行程序）的三轮结果中，旧版与当前版冷导入中位数分别为 4.63 秒和 4.61 秒，普通问题首请求准备分别为 4.54 秒和 4.51 秒，没有重现之前约 45% 的差距。这个结论限定于同机源码测试，不能单凭它断言两个 Windows EXE 完全等速。

## 找到并修复的重复工作

- 稀疏索引为同一语句反复分词，字段解析又对没有下标的普通字段重新分词。现在复用同段源码的词法结果，带下标或引用修改的字段仍完整解析。
- 大量普通语句被当作潜在程序头完整清理和扫描。现在先做不会漏掉有效程序头的标记筛选，实际程序头继续走原解析流程，同一程序身份结果也不再重算三次。
- 证据选择每加一组页，就重新比较所有旧页。现在只检查新页可能改变的覆盖关系，版本、COPY实例、替换轨迹、顺序和预算都保持原规则。
- 同一字段和语句在多个来源证明中重复规范化。缓存限定在本次函数调用，证据正文、版本和发生位置仍逐项检查。
- 框架绑定和布局检查重复重建同一 COPY 布局。现在仅在同一次数据库读取中共享布局；依赖深层 COPY 的事实仍检查完整依赖摘要，没有跨请求缓存。
- 请求压缩对同一个比较值反复编码，现在复用一次编码结果，实际请求表示不变。

## 如何验证没有牺牲内容

完整索引事实按表和全部业务列计算摘要；实际首请求源码按路径、版本、行范围、完整正文和截断状态计算摘要。三版本所有轮次均完全一致。专门对嵌套COPY、REPLACING、深层成员更新、缺失证据和同一行生成指令等七个场景做完整事实与物理来源对照，结果也完全一致。

时间仅包括产品的导入或首请求准备，不包括生成测试源码、全表摘要计算，也不包括模型生成。首请求被本地函数截获，所有网络连接被阻止，真实模型调用为零。回答机制、导入和历史由完整离线回归及最终 EXE 的原生回归另行验证，不以首请求测试冒充真实模型答案评分。

具体大库结果、完整回归计数和源码指纹见同目录 `verification.json`。Windows工作流新增默认关闭的手动对比开关，会在同一构建任务中串行运行两个固定旧包与新包，使用相同的12,000程序案例和相同验收合同，结果单独保存在 `native-release-performance` 产物中。正式验收要求没有改变。

## 重现

使用完整源码快照，保持测量期间文件不变，不要同时运行其他测试：

```sh
python3 tools/benchmark_release_performance.py \
  --variant previous=/path/to/56050b8 \
  --variant current=/path/to/3628a05 \
  --variant optimized=/path/to/current-checkout \
  --output /path/to/new-report-directory \
  --files 300 --lines 250 --longest 25000 --repeats 3
```

大库使用 `--files 12000 --repeats 1`；`--profile` 的剖析单独执行，不纳入普通计时中位数。Windows手动工作流使用 `compare_previous_candidates=true`，不需要真实模型配置。
