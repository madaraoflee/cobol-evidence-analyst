# 按真实进展收敛的源码分析修复

本次修复让默认调查按真实供证进展继续，并补齐取消固定轮数后可能出现的循环路径。自定义 system prompt 的现有链路经实际请求构造测试确认：配置原文在补读、答案修订、截断续写、恢复及显式续查中保留。本文记录源码验证，不表示已发布应用或真实模型业务答案验收通过。

## 修复结果

默认 `max_model_requests` 和 `max_investigation_rounds` 改为 `null`；资料足够仍可一轮回答，新的相关源码或源码绑定的关系支持继续调查。明确保存的旧 8 次／6 轮、其他次数与期限仍生效，不自动改写用户设置。

进展按源码版本、行号、原文及 COPY 展开上下文去重，换片段边界、重建引用编号不再创造新进展。重复无效动作和没有新增证据的补查仍会收束。显式时间目标已要求只回答时，再收到工具动作会停止并保存待查位置，不因总请求数为空而重复等待。

截断续写以首次续写实际供材量、配置输出窗口和请求大小派生累计正文及输出机会。重复正文按原始输出计费；恢复和手动继续均保留累计消费。手动继续可重新尝试先前无进展的输出，以适用用户修改后的要求，但不能刷新已耗尽额度。用尽后保留草稿、引用及截断状态。没有添加禁止“源码不足”等措辞的规则，本次通过真实原文供应和进展判断支持模型分析。

## 本次验证

151 项调查、配置、system prompt、进展、期限、续写与恢复测试通过；另 54 项评估适配、流式等待和验收检查器的源码测试通过，合计 205 项不重复测试。结果见 `verification.json` 及两个日志。

新增端到端样例使用真实索引，在同一个金额程序中连续补读 10 次，第 11 次请求才回答；每轮在传输层外检查原问题、自定义 system 原文出现一次、上一次补读原文确实进入请求。其他回归覆盖没有新证据时 3 次内收束、无视只回答要求时 2 次停止、区间切换不冒充进展、正文微改耗尽派生额度、显式继续不刷新累计消费，以及提示词修改和清空后继续正确传入。

首次适配组运行有 1 项因本机临时端口权限失败；允许本机离线端口后整组 54 项通过。一次手工组合测试命令写错了 5 个模块名，修正入口后最终 151 项全部通过。未用这些失败运行冒充通过结果。

本次没有调用真实模型，也没有构建 app、安装包、验收工具或 release。全量回归、真实模型复测和统一提交由用户已授权的整合聊天继续完成。文件指纹包括共享工作区其他已存在改动，不能把该指纹清单理解为本任务独立完成了其中所有修改。

## 全量揭露的问题与后续修复

第一次整合全量运行 4,236 项，留下 5 个失败及 2 个错误事件，0 跳过，252.795 秒。原始失败详情存入 `initial-full-regression-failures.json`，不将该轮记为通过。本任务负责其中 4 个失败及同一验收工具引发的 2 个错误；LINKAGE VALUE 的另一失败由业务来源修复任务处理。

逐项捕获了模拟传输内部的断言，确认两个案例仍期待旧剩余次数 8／7；改为新默认 `None` 后，原有调用图、两轮重复读后回答、金额规则和引用断言均保留。反虚假记忆案例的“999”实际来自 `request_body_sha256`，并非模型候选正文；现将检查移到传输层外，直接核验候选文本没有错误公式、确认事实为空、已撤回错误块，以及最后模型仍解释“乘以二”。没有用本地公式回退冒充该测试通过。

长正文案例首条模拟输出 45,019 字符，但此前仍使用 1,024 token 的默认窗口，已超过派生累计正文额度。该测试仅把单次输出配置设为 8,192 token，保留原 45k 正文、32 KiB 请求、只传尾部和最终全文逐字拼接的全部断言；不增加生产续写额度。

验收工具的外部等待计算原先直接拿空次数乘超时，导致异常。现保留产品 `maximum_model_requests: null`，在验收报告另列独立 `watchdog_request_allowance: 8` 及 `verification_default` 来源，计算有限的验收等待期限；不修改产品策略，也不把验收等待期当成回答完成承诺。显式部署次数和期限继续限制验收等待。

上述 6 个文件的修复后，5 个相关模块共 95 项全过，16.653 秒，差异检查通过；日志与指纹见 `followup-verification.json`。本次初始 205 项与后续 95 项来自不同测试模块。此后全量重跑与真实模型 TLS 失败案例复测仍交整合任务完成，不能仅凭定向结果宣称全量已过。

## 真实问答的工具协议与空正文恢复

修复输出拼接和状态误判后的一轮源码全量已达到 4,245 项全过，但真实问答仍有失败：一题把未识别的标签工具协议作为正文，另一题正常结束却没有业务正文。不能凭全量通过或 `answer_available` 就宣布目标完成。

完整的原始工具回复已从已完成请求账本读取，归档于 `captured-tool-response.json`，没有只靠截断预览判断。调用包的闭合标签并不匹配，因此使用通用词法结构识别后进入既有一次格式纠正，不解析执行其中内容；不在代码里写供应商标识。合法 JSON 动作仍经过原白名单和路径验证。格式恢复保留补读机会，包括尚未命中源码的 discovery；纠正后确实把新原文送入第三轮，再形成带引用业务答案。普通 HTML、业务 XML、单独 invoke 和示例保持原意，逐字符工具包不出现在正文预览。

另捕获并修复了重开续命：第二次坏包收到未处理时中断，若纠正资格只存在内存，恢复会再给一次请求。现在将已用资格和待纠正状态保存；第二坏包恢复只本地重放，总请求仍为两次；第一次坏包未处理时中断则仍保留唯一纠正机会。

空正文原 message 受既有日志裁剪规则影响没有留存，不能声称读到了未保存原文。可核验事实为账本 completed、单个 assistant choice、正文为零、stop、无工具字段，351 completion tokens 均为推理。新路径仅对已明确收到且被原解析器判为空的合格内容使用一次相同原文和相同 system 直接回答；已有答案时保留原稿。拒绝、未知 Mapping/number/parts、非文本内容、工具调用、超时及未知远端结果均不能借此重试。原解析器已支持的空 JSON answer/text 字符串保持兼容，不新增产品格式门槛。

105 项定向测试全过（17.483 秒），覆盖两条恢复、中断重开、流式预览、格式误判反例、自定义要求及原文完整性。用实际 240 字符回复进行离线回放，确认所有分段前缀被暂缓，协议不作为答案；第二次合成回复能交付业务解释。离线回放不是新的真实模型通过证据。本轮没有调用真实模型或构建应用，源码已再次交整合任务冻结，等待最终全量及真实三题复测。具体文件指纹和日志见 `protocol-recovery-verification.json`。
