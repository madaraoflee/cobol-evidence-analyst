# P3-E：重复调用上下文与可行性验证

日期：2026-09-08

本轮验证的结论是：在受支持的源码调用与参数布局范围内，按完整调用点链区分同一子程序的多次使用是可行的。系统已能为共享子程序分别保留两条参数身份链，并阻止内容复制、链条缺失或预算截断被当成入口回写证明。这是完整业务分析的一个必要切片，不是完整错误路径、COBOL 执行或模型业务回答验收。

## 可复核的例子

新样例 `call-context-v3/main` 有 7 个程序、8 个源码调用点，展开为含入口在内的 12 个静态上下文。`PAIRMAIN` 在两个位置调用 `CALCWRAP`；两个包装程序上下文继续经过同一个 `CALCWRAP → SHAREDWK` 调用点。若只用程序名，甚至只用最后一个调用点作为身份，都会把这两条链合并。

| 分支 | 共享程序状态 | 对应入口状态 | 请求传递 |
| --- | --- | --- | --- |
| A | `SHAREDWK::WORK-STATUS` | `PAIRMAIN::STATUS-A` | 入口 CONTENT，内层 REFERENCE |
| B | `SHAREDWK::WORK-STATUS` | `PAIRMAIN::STATUS-B` | 入口 CONTENT，内层 REFERENCE |

共享字段的静态符号 ID 相同，但上下文字段 ID 不同。状态参数全程使用 REFERENCE，可形成各自的候选回写链；请求经过 CONTENT 后，内层 REFERENCE 只对应副本，不恢复对入口原参数的回写。上下文身份不表示新分配的工作区，也不证明存储没有别名。

另有 INPUTCHK 的 VALUE 整数参数、RATESTEP 算术和错误分支、两次 RESULTFN 结果映射、PAIRJOIN 汇总，以及映射/汇总程序无法调用时入口清零。独立边界目录保留递归、动态目标、重复实参别名和循环内调用。旧 v1、复杂 v2 均保留；复杂 v2 演示也已接入上下文分析。

## 实现与验收边界

`call_contexts.py` 只读已有索引，在完整静态调用点链上生成上下文，保留参数位置、组内成员、传递方式、双方字段和来源引用。递归、歧义、动态目标和不完整绑定不会被猜测补齐。上下文数量、深度、展开调用、参数行、边界和来源文本都有预算，输出包含截断状态。

`context_paths.py` 把本地错误观察引用挂到相应上下文，再沿准确的父子参数身份组合状态/输出对应。不跨分支搜索同名字段，不从 MOVE/SQL 猜测中间值。只有整条链到达入口、且全部是 REFERENCE，才标为入口候选回写；实际错误值、分支执行和最终输出仍未证明。本地源码观察可被两个上下文引用，不能计作两次真实错误。

`context_demo.py` 根据单独编写的 profile 比对每个程序的上下文数、入口映射、共享程序组成员、叶子传参方式以及两条状态链。当前正例通过 48 项源码上下文验收。此 PASS 只适用于明确选择的样例结构；命令返回码 1 表示该结构验收失败，0 不表示业务运行通过。

12 个业务场景仍全部为 `NOT_EXECUTED`。账本中的 A=250、B=120、合计 370 是透明输入下的手算期望，不是运行结果，也不用于把源码上下文分析升级为数值核验。未安装编译器、未执行 COBOL/SQL、未调用公司 API、未修改四个模型调查工具或接通界面。

## 反例是验收的一部分

验证不止查看正例：还故意把第二次调用的状态接到第一笔、改变传参方式、删除调用或组成员、篡改索引中的参数目标，以及构造循环父节点、重复映射和预算截断。错误输入必须失败或保留明确边界，不能仍声称完整参数对应。

最终全量回归 302 项通过（资源警告按错误处理）。本轮新增 65 项：上下文引擎 21 项、独立索引变异 5 项、参数链组合 7 项、独立组合反例 9 项、夹具 12 项、端到端 11 项。正例 48 项源码验收全部通过；第二笔状态串接、首笔状态改 CONTENT、删除第二次调用这三类源码变异均使验收失败。旧复杂 v2 仍保持 205 条确认参数映射、92 条候选回写和未解析动态目标。

来源检查验证本地索引内部的一致性，包括源码清单快照、来源行范围、重叠文本及相关索引事实；它不是防篡改认证。原始源码字节没有外部可信签名，协调重写整份数据库不能靠数据库自身的 Hash 排除。

运行方式：

```text
python -W error::ResourceWarning -m unittest discover -s poc/tests -q
python poc/context_demo.py --database .poc-data/context-v3/structural-index.sqlite --json-output .poc-data/context-v3/result.json --markdown-output .poc-data/context-v3/result.md
```

Windows 从项目根目录运行 `poc\run_context_demo.bat "D:\cobol-output\context-v3"`。所有输入与结果都应留在获准的本地目录；本轮新增能力没有外部依赖和网络请求。

## 下一段主线

现在仍不能确认“错误一定经过哪个分支返回”。下一步应在这些上下文中建立异常/溢出子句的正式控制流与状态变化，再处理重复 PERFORM、循环/数组和持久工作区；动态调用需要带版本的配置数据。只有这些证据闭合后，才用真实业务问题验收模型是否回答完整。

代码理解技能指导本轮把调用身份、参数对应和错误路径作为不同关系分别检验。因此本轮的可行性结论停留在源码上下文身份，不会把静态图连通等同于业务执行。
