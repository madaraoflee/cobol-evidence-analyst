# 在线万文件调查的查询性能修复与验证

本次确认了两处会随仓库增大而放大CPU成本的查询缺陷：单文件读取扫描了整个记录种类；实际进度更新又反复解析全库JSON做统计。修复使用SQLite索引缩小读取范围、复用索引中的统计值，完整保留来源、业务结论、待办、恢复游标和历史版本。没有提高测试时限、删减万文件输入或减少金标断言。

## BUG-20261111-009：读取一个文件却扫描整个记录种类

`InventorySession.rows(path=...)` 同时按会话、记录种类、路径筛选并按key排序。原三列索引 `record_path(session,kind,path)` 没有覆盖排序；实际SQLite执行计划选择了主键索引 `(session,kind,key)`，为了寻找一个路径的记录遍历整个kind。真实10,001文件库中，返回一条finding用了50,052条SQLite虚拟机指令。

真实中性源码工具流程中，1,000文件调用该查询12,039次，累计SQL执行耗时2.22秒；2,000文件调用24,081次、耗时9.52秒。调用数翻倍而该查询耗时约增为4.3倍，与执行计划一起确认了二次扫描放大，而非仅依据代码推测。耗时包括测量开销，不是公司模型时延。

修复先建立四列索引 `(session,kind,path,key)`，明确让路径查询使用该索引，再移除被完整覆盖的旧三列索引。未改分页排序、过滤条件或结果数据，也没有同时保留两个冗余path索引增加写入负担。相同10,001文件记录与查询结果下，指令数降为45，执行计划按会话、kind和path直接定位。证据见 [原查询计划](10001-query-plans.json) 与 [索引前后对照](path-index-before-after.json)。

## BUG-20261111-010：每次进度更新反复解析全库JSON

实际 `run_investigation` 启用持久进度回调时，单个有效read动作实测调用 `summary()` 九次。2,000文件下，该步总耗时0.0645秒，其中摘要统计0.0415秒；10,001文件下，总耗时0.2793秒，其中摘要统计0.1923秒。每步统计随全库增长，再乘随调查规模增长的动作数，会形成二次CPU放大。[实际产品调用对照](product-summary-counts.json) 使用真实中性原文读取及生产调查流程，不调用远端模型。

原统计对每条candidate解析 `occurrence_count`，对每条file解析 `inventoried`。修复增加候选出现次数的表达式索引和已清点文件的条件索引，并在对应查询中明确选择索引。仅创建索引时，实际SQLite仍选择旧路径索引，两条查询各解析10,001份JSON；明确使用索引后，两条查询的JSON解析次数均为0，数值仍为10,001。见 [只建索引的对照](expression-index-before-after.json) 与 [明确使用索引的对照](expression-index-explicit-query.json)。解析次数通过受控、同值的确定性JSON函数回调计数测量；其耗时不能冒充原生内置函数的绝对性能。

没有新增手工统计表或计数缓存。索引由SQLite随写入、提交和回滚维护；旧发布结果仍使用原先固定的记录版本。这次消除了两项重复JSON解析，其他轻量索引计数仍随记录数变化，不能据此宣称整个调查已变成常数或线性复杂度。

## 保留不支持“全流程已加速”的实验

早期只增加四列索引、仍保留冗余三列索引的实验，虽然改善了目标SQL，却没有证明总体加速：1,000文件17.44秒到16.61秒，2,000文件34.18秒到38.08秒。完整记录保留于 [原流程](combined.json) 和 [仅加索引的流程](indexed-combined.json)，没有删除不利结果或只挑最快一次。

该实验还纠正了对旧Windows长测试的归因：万文件测试驱动逐文件直接调用生产工具，通常不执行产品的逐动作进度回调；1,000/2,000文件驱动中，两条JSON聚合各仅调用25/41次；连同按kind计数在内，三项摘要聚合合计耗时分别约0.044/0.145秒。因此摘要统计是实际产品的明显开销，不能单独解释旧CI长测试全部用时。连接、事务、存储和目标平台也影响总耗时。

该规模夹具是10,001个小型中性程序，解释响应由实际供应原文生成；金标仅用于出口比对。它验证持久化、恢复、来源及交付，不证明真实模型的业务语义质量，也不等于复杂公司仓库或Windows设备的速度验收。
