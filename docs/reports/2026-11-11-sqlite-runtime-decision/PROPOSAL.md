# 共享数据库组件最小冻结例外方案（待用户决定）

Windows受控中性200文件同机对照中，受管理连接的WAL/FULL方案为17.472秒，两次旧方式平均51.608秒；完整金标、原文复核、分页导出、回滚和旧发布结果保持。见 [同机结果](windows-experiment/summary.json)。这是临时单执行线程实验，不是万文件、最终EXE或公司模型验收；Windows没有逐SQL线程ID动态记录，也没有增加最终keeper关闭后的独立重启验收。

当前Windows构建解释器实际SQLite3.50.4处于官方WAL-reset缺陷影响范围。本地结构索引和目录也使用WAL，因此不能为在线提速直接切换新方案，或把共享DLL升级冒充在线私有改动。官方依据：[WAL-reset说明](https://sqlite.org/wal.html)、[连接关闭检查点配置](https://sqlite.org/c3ref/c_dbconfig_defensive.html#sqlitedbconfignockptonclose)。未将此上游风险归因为照片中的500、失忆或真实损坏。

拟请用户允许一次最小共享组件例外：应用私有运行时继续使用同版CPython3.13，只将SQLite组件从3.50.4更新到已校验的官方3.54.1，不替换用户电脑或构建机全局Python。官方Windows x64归档SHA3-256：`c2d09c8babb9399277055c057c97a53f1ffd7c5f11d0c1f2118ffdfa39f2daa4`，DLL SHA256：`4b59d3cded9dc1608544160f3b4b10ac974c6ac0d6ffc23064e5f4c8dbd05aea`；目前仅静态核对下载，Windows装载及兼容性未验证。3.50.7只有查到回补源码，规范预编译DLL地址404，不把它当成可校验成品。

在线保存优化只作用于独立OnlineInventoryStore/OnlineState及其资源释放：FULL提交不降级，保留全部来源、已完成动作、待办、历史版本和旧发布结果；用明确管理的连接生命周期减少重复打开和同步成本。旧SQLite或不支持配置的源码环境保留安全原路径，不能默默启用有已知缺陷的WAL。

拟实施范围是新的私有运行时准备工具与固定散列清单、Windows源码/应用/办公室构建使用同一组件，以及最终EXE的实际加载版本/路径/来源散列核对。不会修改本地业务分析功能代码、资料格式或旧断言。在线专属生命周期与崩溃恢复会新增回归；必要的在线测试资源清理只释放句柄，不改旧输入、金标、成功条件或跳过策略。

全部旧缺陷、Python和浏览器测试都须在最终源码及Windows组件上重新执行；原45分钟回归门槛、25案例79样本、全局清单与恢复检查保持。失败即阻断。万文件、最终EXE、真实公司模型及目标设备均不得用这次200文件实验替代；未通过项目继续保留开放。

替代方案：维持共享组件及原保存方式，则当前已复现的Windows长测问题仍未关闭；真正独立在线数据库引擎需要额外ABI/驱动或进程桥接，代码和打包范围更大，不作为本次最小修复。未获批准前不更换共享运行时，不触发使用新组件的应用构建；线上及本地旧数据不删除、不覆盖。

该决定来自项目AGENTS.md的明确冻结规则：“若必须改本地核心，先记录原因与替代方案，由用户另行决定范围，不能顺带修改。”用户本轮已授权生成EXE，本次只请求共享组件这一额外范围，不重新询问已有构建授权。
