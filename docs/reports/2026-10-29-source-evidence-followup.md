# 源码证据一致性与 Bitbucket 修复续查（2026-10-29）

本轮确认的问题主要发生在状态切换时：配置变了、源码刷新了、COPY 实例不同了，系统仍可能沿用旧身份或旧完整性判断。修复目标是让每项结论对应实际供应的源码版本、编译配置和展开实例，并让 Bitbucket 的“已是最新”同时要求本机副本完整。

这是对[上一轮源码证据审查](2026-10-29-source-evidence-audit.md)的续查，保留上一轮报告与回归指纹；本轮最终验证另行记录，不覆盖历史结果。

## 已复现并修复

| 路径 | 原缺陷与影响 | 修复和回归证据 |
| --- | --- | --- |
| 问答中的源码刷新 | 局部刷新未沿用建库的编译条件，已确认分支可能退回未知；源码字节相同但读取配置或解析器变更后，旧捕获仍可用于新索引。 | 捕获绑定索引配置指纹，事务内核对快照、索引类型及版本；刷新显式传入原编译配置。验证条件开关、配置变更和旧解析器拒绝混用。 |
| 刷新后的文件身份与概览 | 无扩展名过程 COPY 更新后可能失去类型；COPY 改成真正程序时旧 Copybook 符号残留；程序名和全文截断状态未同步更新。 | 保留原 COPY 提示，实际 PROGRAM-ID 出现时清除临时旧身份并重新解析该文件；重算程序样本、程序数量、全文完整性和截断边界。 |

## 最终回归

4,386 项 Python 主测试全部通过，零失败、零跳过；比上一轮增加 37 个测试方法，子场景另在各方法中覆盖。262 项网页测试和 1 项工具测试也全部通过。四组 Python 并行运行约 88.34 秒，这只是本机源码回归耗时，不是实际模型回答延迟。

已核对四组报告的发现清单及测试文件哈希一致，全部测试 ID 恰好执行一次；最终测试文件和 45 个有改动的代码文件均重新核对 SHA-256。结果、源码指纹和新增测试 ID 见[本轮回归摘要](2026-10-29-source-evidence-followup-regressions.json)。验证针对当前未提交工作区，包含上一轮已修复的源码改动。

固定公开语料的 8 个文件与 `docs/eval/public-business-v1/manifest.json` 的 SHA-256 一致。最终完整回归在允许本机回环 HTTP/TLS 服务的环境运行；受限环境早先的端口监听失败未计作通过。Bitbucket 增量测试包含 12,202 文件规模、重命名、删除、目录边界、分页、取消和本地读写故障。

## 完整性与效率边界

“源码已下载”“已进入索引”“当前请求已供应原文”“依赖闭包完整”是不同条件。本轮防止这些条件在刷新、去重和裁剪时被错误继承，不能据此声称每次回答都通读全库或已验证全部业务语义。动态调用、外部实现、不支持的语法和缺少的运行证据仍需明确保留边界。

效率上的改进有具体约束：按问题范围避免无关业务补读，正确区分已有与新增语义材料；仅在主动 Bitbucket 更新时核对全文件字节，普通重启和打开本机副本不增加全库散列或联网。Cloud 后续更新按文件增量获取；Server / Data Center 仍使用归档，未声称具备文件级增量下载。COPY 改成程序时只重新解析该文件，不重建全库。

所有验证使用本机测试、原创夹具、固定公开源码和模拟 HTTP 接口。没有访问企业私有仓库、使用真实凭据、调用真实模型或构建应用、安装包、验收工具及 release；源码回归不能代替企业接入和 Windows 最终 EXE 的真实验收，也不能代替真实模型的业务回答质量与耗时评测。
