# 多轮供证与自然业务顺序问题修复

最新候选现场截图暴露了此前回归没有覆盖的组合：问题没有程序名、同一业务词命中多个初始化程序、模型连续补查后关键原文退出上下文。程序确实存在会造成“本轮无法确认”的缺陷，不能把这个现象一概归因于模型能力或仓库没有源码。

## 已确认的原因

一次业务问题会发出多轮模型请求。旧实现只在模型主动返回可选 `findings` 等候选记忆时保存回读线索；合法的普通 `read` 不要求附带这些字段。随着后续原文加入，较早材料会退出默认 36,000 字符的当前源码预算。中性离线复现中，第 2 轮看过的处理顺序在第 5 轮起不再供应，而记忆块一直为零。原文在本地归档，并不等于下一轮模型收到它。

第二个缺陷使失忆难以恢复：模型再次申请读取相同行段时，工具去重只检查“以前是否读过”，不检查“最近一次请求是否实际带着原文”，于是跳过回读。最终答案只能围绕残留材料解释。这个问题属于同一问题内部的多轮供证，与界面是否还显示聊天记录不同。

自然顺序问题还存在检索偏差。“各项余额按什么顺序抵扣”原本未被识别为需要跨步骤业务解释。没有程序身份时，命中的根又被转成集合、按文件名排序并取前 6 个；初始化程序可以占满名额。复现中 7 个初始化匹配项使后面的调用入口及其子程序尾部规则没有进入完整工作集。此前七层调用回归明确写了程序名及“整体业务流程”，因此没有暴露这条路径。

通用业务模板进一步放大了表象：针对顺序的问题也要求解释批次、在线、表和文件类别，产生大量与问题无关的“未确认”章节。缺少局部证据不应抹掉其他已经支持的步骤，也不应靠声明顺序或段落名称猜业务执行次序。

## 修复行为

实际收到有效响应后，程序记录该次请求真正供应过的源码身份，生成有界的回读目录。目录保留路径、行段、源码及节录哈希、实际请求来源，最多 32 项/16 KiB；完整来源留在本地。目录没有原文，也不授予引用权或证明业务结论。请求字节不足时先裁目录，明确记录遗漏数，不优先牺牲仍可容纳的原文。

明确重读已退出上下文的材料时，恢复同版本、同绑定的归档原文并提高本轮供应优先级。恢复后又被新材料挤出仍可再次回读；同一个尚未成功供证的周期不会反复恢复。恢复不冒充新证据，不清零无进展计数，来源版本、归档、COPY 上下文和排他范围检查仍有效。取消后重放及用户继续补查保留来源绑定，不重复发送已完成请求。

顺序问题现在使用现有的有界业务供证流程，沿可见控制流、段落、子程序与参数交接找原文。概念候选保留文本检索顺序，并最多给两个不同 CALL 导航形状保留提前阅读位置；原读取预算不变，未选根继续列入 frontier。该排序只提高阅读覆盖，不证明哪个程序才是业务入口，也不确认动态目标或生产执行顺序。

回答合同要求解释实际先后、进入/跳过条件、金额或状态变化、交接和例外。纯顺序题不强加系统概览；明确同时询问概览与顺序时保留两部分。中英文否定技术细节、简短要求、逐行解释、字段排序、单一公式、排他范围及“优先股”等边界有独立回归。

HTTP 500 另行处理：通用 `server_error` 不再遮住服务端提供的明确类型；冲突或未知原因仍保持未知。安全详情新增实际请求轮次、阶段、状态、字节数及包含的源码文件/片段数，不输出源码、路径、密钥或原始错误正文。截图未展开错误详情，现有证据不能确认该次服务端 500 的具体原因，也不能声称此次已修复未知服务端故障。

## 验证与交付

源码与最终 Windows 包的验证结果分别记录，不用源码测试代替 EXE 验收。新增桌面 HTTP 检查覆盖无程序名且有七个初始化干扰项的顺序问题，以及默认预算下第九轮实际回读关键顺序原文；单元集另覆盖十四轮再次驱逐后回读和重启/续查边界。

所有模型响应均为本机合成接口，使用中性生成源码，未发送公司源码、未调用外部模型。这些结果验证检索、原文供应、连续性与回答合同，不构成真实模型答案质量评分。具有相同调用形状的大量候选仍可能需要后续补查，不能保证任意公司复杂链路一次读全。

正式发布仍受同包真实模型、人工评分及目标办公设备验收约束；缺项仅交付候选，正式版本不自动替换。
