# 当前业务行为解释与请求准备速度优化

本轮把流程解释的重点落到“什么条件下执行、例外怎样处理、记录或状态得到什么结果”。改进保存在独立分支 `codex/business-behavior-quality-speed`；优化前的 `7dd3e57` 保存在 `codex/baseline-20261007`，没有合并回 `main`。双版本下载、配置和启动见[办公室切换说明](../version-switching.md)。

## 实际改动

原来的计算题已有公式、条件及后续覆盖提示，流程题的回答完善主要依赖通用指令。本轮为已定位的流程问题增加一组来自实际供应源码的阅读线索：分支条件、条件中的退出、读写、赋值、调用和循环。自然问法如“为什么没有生成账单”也进入现有流程调查。

线索随每轮实际材料重新生成，每条只引用真正包含该语句的源码页。相邻页可组合，不跨源码缺口、版本或段落推断控制关系；注释、字符串和嵌入语言不作为 COBOL 行为。最多输出 12 条线索，扫描上限为 80,000 字符，并保留省略标记；原有源码供应额度没有缩小。它是辅助阅读提示，不是执行图，也不证明分支可达、事务提交、实际输出或完整业务规则。

回答引导要求把“校验、按配置处理、更新状态”等动作解释成具体条件与后果，并区分单笔返回和整批停止。只在新增检查能明确识别答案全部是笼统流程用语时，才提议在原有预算内完善一次。自然业务措辞、具体简短答复和只读流程不会仅因缺少固定词语而被强制重写。已有公式检查、错误停止、引用约束和最大请求次数保持原有机制。

新的阅读线索放在可裁剪的分析提示中，不扩大系统提示的固定体积；请求空间不足时优先保留源码。修订判断复用同一次初稿评估，减少相同材料的重复处理。

速度改动集中在请求中的源码范围核对：每次核对先按路径组织范围，避免每个目录项和引用反复扫描、排序所有页。范围索引只在当次核对内使用，后续裁剪或原地修改仍重新核对，不跨请求复用旧覆盖结论。

## 速度对照的准确范围

为了隔离性能改动，在同一套当前问答流程中，只切换优化前/后的源码范围核对实现。使用一个 5,000 行合成程序及其 COPY 文件，先准备语义缓存，再交错运行各五次。计时从提问开始，到首个模型请求装配完成为止；不含建库和模型等待。

| 指标 | 优化前核对实现 | 优化后核对实现 |
| --- | ---: | ---: |
| 请求准备时间中位数 | 2.193 秒 | 1.797 秒 |
| 实际供应源码片段 | 129 | 129 |
| 实际供应源码字符 | 25,288 | 25,288 |
| 请求大小 | 229,969 字节 | 229,969 字节 |

本组准备时间减少约 18.1%；全部十次请求逐字节一致。这是性能改动的隔离对照，不是旧版全部代码与新版全部代码的端到端速度比较，也不代表公司源码或真实模型的最终回答耗时。

可重复执行：

```sh
python3 poc/benchmark_evidence_context.py --directory /path/to/new-disposable-benchmark --baseline-ref codex/baseline-20261007 --lines 5000 --repeat 5
python3 -m unittest discover -s poc/tests -q
node --test poc/tests/*.test.cjs
```

基准目录只用于原创合成数据，工具生成 `report.json` 保存测量、请求摘要和比较结果。目录需使用新的可写位置。基准不访问模型接口。

## 办公室交付

提供四个 Windows 启动脚本，原版与改进版的源码入口使用不同端口；桌面入口使用独立的用户数据目录。分析结果目录仍需在界面分别选择，脚本不会自动迁移旧历史或覆盖原环境。源码分支可以直接使用；两个 Windows 桌面包需要在允许构建的 Windows 电脑分别生成，本轮 macOS 环境没有生成 Windows EXE。
