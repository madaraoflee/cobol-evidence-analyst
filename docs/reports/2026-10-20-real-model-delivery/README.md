# 业务解释、框架依据与正文流的真实模型验证

本轮验证使用真实 HTTP 模型和中性源码，评审最终交付正文，不把索引命中、局部状态或草稿出现当成业务正确。Windows 最终 EXE 的同包验收另行执行；这里的 Mac 源码结果不能代替目标办公设备和人工评分。

## 冻结范围

四题在首次请求前冻结，题目、13 项必需结论、禁止推断、物理行段和文件摘要见 [cases.json](phase1/cases.json)。普通新人问法查询余额、普通程序分析结算流程、普通 COPY 的操作约定，以及只改变 REDEFINES 布局的反例，各用新会话。金标准只留在评测端，不作为模型提示。中性夹具来自仓库已有测试，未发送企业源码或私有框架手册。

初始代码为 `52469d636103920371632429d56a78c6f62f4e09`。原始 [计划](phase1/plan.json) 绑定实际加载文件摘要、模型参数与预算；[归档清单](phase1/archive-manifest.json) 绑定保存的原件。模型请求使用现有获准配置，显式低推理、8192 输出上限，每题最多 3 次。全任务保守费用预留上限 2 元，按[官方峰值费率](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)计算输入字节上界与输出额度，发送前持久预留，失败不退回额度；这不是实际账单。

观测复用实际 `analyze_source → run_business_chat → UrllibTransport`，不替换流式实现、不拆分完整答案模拟播放。记录原生正文增量、生产进度接口快照及浏览器 DOM 变化；DOM 收到变化不等于测量物理屏幕绘制。浏览器只增加被动观测，不发送额外问题。隐藏推理、请求头和密钥不进入归档。

## 首测保留的结果

前三题均收到真实 SSE 正文，浏览器在响应结束前多次更新：B1 为 35 次，B2 为 47 次，F1 为 43 次。核对阶段实际发生，但三题首稿与最终正文相同，暴露出局部核验不能识别的语义问题，不能按系统的 ANALYZED 状态算通过。

- B1：业务用途已明确，仍无依据地断言查询不锁定，多行查询的分支解释还自相矛盾。
- B2：解释了结算记录生成规则，但把文件名当作 LF/PF 类型，作出过强的一一对应、无痕迹断言，三处引用使用内部规则编号。
- F1：操作请求与运行效果分开，也带上手册限制；却遗漏普通 COPY 独立存储、后续赋值为什么不覆盖操作码的解释。
- F2：TLS 握手失败，零模型正文；本地回退不是模型答案。该轮立即停止，未自动重发。

逐项独立代理评审及精确答案引句见 [首测汇总](phase1/run/agent-review-summary.json) 和同目录各题记录。它们不是人工验收评分，不换算总体准确率。首轮共 4 次物理请求，保守预留 `698792` 微元，包含失败请求；第二阶段只能使用余下 `1301208` 微元及最多 8 次物理请求。

## 首测引出的修复

交付约束明确要求：业务介绍围绕用途、数据流与决定性条件推进，声明清单只在解释当前行为时展开；查询语句不能证明无锁或具体数据库事件到状态码的映射；写出请求不能代替持久化成功；文件名不能证明 LF/PF；框架约定必须解释调用、布局和最后有效赋值怎样共同支持它。

本地新增有限的 SQL 边界提名，依据实际供应的完整语句和答案中的具体断言进入现有核对、修订、无进展停止及请求预算。它只提名高风险片段，不解释数据库实现，也不证明任意业务散文正确。内部规则编号不能充当用户可解析的引用；代码中的引用格式示例仍可正常说明。正确且有依据的首答不强制增加模型请求，预算不足仍保留局部未核实状态。

修复后完整离线回归为 **3557 项全部通过，零失败、错误和跳过**，用时 204.78 秒，固定公开语料已启用；121 个产品文件的测试前后摘要一致，439 个 Python 文件通过 3.10 语法解析。详见 [源码回归](source-regressions.json) 与 [独立审查](source-review.json)。记录中的 baseline_commit 是未提交修复所基于的 HEAD；实际测试内容由前后文件摘要绑定，不能解释成旧提交本身已经包含这些修复。页面代码未改，上一冻结版的 202 项浏览器回归仍适用于相同文件；Windows 工作流另会重新执行浏览器回归。

独立审查曾发现正确限定语误触发复核，以及多条 SQL 的风险报告挤掉源码。修复后的真实请求裁剪反例在 32768 字节限额下保留唯一原文及风险，100/200 条 SQL 的复核请求分别为 18779/25580 字节，没有裁剪；风险摘要有固定大小和引用数量上限。正常限定语不增加请求，修订也不能引入新的已识别风险。

## 修复版的真实复测仍保留失败

第二阶段绑定 `a4669339f3f63799b796f235b6447cac7ebebb5f`，沿用原题目、金标准和夹具。B1 的真实最终正文通过逐项独立代理评审：用途、数据流、分支和输出得到解释，未再断言查询无锁，也未把数据库事件强行映射到固定状态码。B2 再次在 TLS 握手阶段失败，零模型正文，RunStore 保留未确定请求；该题不评分，本地回退不算模型通过。该阶段立即停止，没有自动重发。两次物理请求保守预留 `338608` 微元，连同首测累计 6 次、`1037400` 微元，失败额度未退回。见 [第二阶段归档清单](phase2/archive-manifest.json)、[B1 评审](phase2/run/B1-agent-review.json) 和 [B2 未完成记录](phase2/run/B2-agent-review.json)。

第三阶段仍绑定同一 `a466933` 基线，复用[首轮 cases.json](phase1/cases.json)，只实际执行了 F1。普通 COPY 的解释已补齐：独立字段布局使后续 KEY/VIEW 赋值不覆盖操作字段，调用前最后有效的操作值仍为 ADVANCE；请求动作与运行结果的边界也得到保留。但最终正文仍未通过：它从 KEY/VIEW 字面量推断“没有携带具体主键，而是用某种标识定位”，材料并未证明这种角色或排除主键用途。正文还使用圆括号引用，并把一个实际 `ev_page_` 标识写成 `ev_`；最终渲染产生 **0 个源码引用链接**。正文增量交付通过，产品的 `ANALYZED` 状态不能抵消这些语义与交付缺陷。精确引句与哈希见 [F1 评审](phase3/run/F1-agent-review.json)、[原始观测](phase3/run/F1-observation.json) 和 [归档清单](phase3/archive-manifest.json)。

F1 完成后，操作者在 B2 前的题间等待处中止执行；第三阶段没有发出 B2/F2 请求。[operator_stop 汇总](phase3/run/summary.json)是在中止后，依据保留的计划、实际账本与已完成观测离线生成的记账记录，不表示三题执行完毕。F1 增加 1 次物理请求、`186122` 微元预留；前三阶段合计 **7 次、`1223522` 微元**。原有两次未知远端结果的失败请求继续计入预算，均未退款。

## 引用修复的范围与源码验证

针对第三阶段暴露的引用问题，当前修复只接受本次实际供应的精确引用 ID：把匹配的中英文圆括号或方括号统一为可解析引用；仅当完整 24 位摘要唯一对应实际 `ev_page_` 证据时，才允许相同摘要的 `ev_` 别名。未知、过期、截断或歧义标识不会凭相似名称补齐，代码示例和链接目标受保护。修复与未解决记录各有数量和字节上限。这项处理修复来源定位，**不证明 KEY 的业务角色，也不证明引用旁的自然语言结论正确**；独立审查明确记录 `semantic_verification=false`。

引用及框架资料来源修复后的完整源码回归为 **3577 项全部通过，零失败、错误和跳过**，用时 **196.579 秒**，未调用模型，外部网络被阻断。直接核对报告中的前后摘要映射，均为 **122 个产品文件且逐项完全一致**；**442 个 Python 文件**通过 3.10 语法解析。另有 83 项相关独立核查通过，未复现 P1/P2 问题；该审查仍为代理源码审查，不是人工业务验收。详见 [引用修复源码回归](citation-source-regressions.json)、[原始测试日志](citation-source-regressions.log) 和 [引用及来源独立审查](citation-source-review.json)。这些新记录与前述 3557 项报告分别保存；新报告的 `baseline_commit` 同样表示修复所基于的提交，实际测试内容由文件摘要绑定。

## 本地误改的修复与精确重放

第四阶段 F1 的模型原文是“如果调用在运行时发生异常，源码没有提供本程序的处理规则”。原供应检查把“没有提供”误换成“完整源码已提供”，混淆了原文供应与业务规则是否存在。修复后区分缺失的对象是物理源码还是源码中的规则、行为、处理；只修前者，不据源码存在而补造业务逻辑。29 项聚焦测试通过，也保留真实原文缺失声明的修正。

依照实际修复审计的偏移倒放，重建的 2796 字符原模型正文 SHA 为 `e1a1bcc3e9f91701410da62a464d85c0a24d17ca125618d97827a470fea10786`，与原生观测首个完整正文完全一致。再经修复后的实际 `run_business_chat` 重放，同一实际源码 ID、路径、版本和行范围得到相同 SHA、零网络连接、一次脚本传输，异常未知句保持完整。见[记录正文重放](replay/F1-recorded-model-replay.json)与[独立评审](replay/F1-recorded-model-replay-agent-review.json)。这是对已取得真实正文的离线精确复放，**不是新增真实模型调用，不覆盖第四阶段实际交付 FAIL，也不等于整个系统语义通过**。

## 最终源码检查、预算与发布判断

输出边界约束进一步明确：DISPLAY 去向须有实际定义；未显式设置返回码不能排除调用方观察输出或效果。新增提示曾使最低 32768 字节预算的反例丢失唯一源码：测试回调因空页抛出 StopIteration，产品报成 TRANSPORT_ERROR，不能解释成真实网络故障。此轮 [3581 项中 1 项失败](absence-source-regressions-failed.json)及日志保留。压缩同样语义的提示后，请求为 32726 字节，6000 字问题和唯一源码均保留，三个请求预算测试通过，未扩大预算或修改原断言。见[独立预算核查](replay/minimum-source-budget-agent-check.json)。

最终代码 `4a4e0c8aded571dc4a0fd86d922d40e87b8fef40` 的完整回归 **3581 项全部通过，零失败、错误或跳过**，用时 **201.443 秒**，122 个产品文件前后摘要一致，外部网络被阻断；443 个 Python 文件通过 3.10 语法解析。见[最终源码回归](final-source-regressions.json)及[日志](final-source-regressions.log)。源码检查与真实正文评审分别判定。

第四、五阶段合计 4 次真实请求，保守预留 **733374 微元，约 0.733374 元**，在本次用户 1 元补测上限内；所有阶段累计 **11 次、1956896 微元，约 1.956896 元**，原两次失败与未知请求仍计入，未退回额度。这是输入字节上界和输出额度的保守预留，不是实际账单；剩余累计额度不能覆盖一次同配置输出预留，停止新增模型请求。

**本轮未满足“真实验证有效后合并发布”的条件。PR #11 保持未合并，没有触发 Windows 构建、创建新版本或替换正式 Latest。** 另一开发工作区未提交内容未被复制、修改或提交。本轮证明正文流与限定范围的框架推断有所改进，也证明仅靠提示和有限局部检查不足以稳定阻止业务推断。后续需要由实际供应材料约束的独立语义复核，并在新的获准预算下验证它；不能追加硬编码答案或放宽原评分标准来声称通过。Windows 最终同包真实模型、人工与目标设备验收仍须独立执行。
