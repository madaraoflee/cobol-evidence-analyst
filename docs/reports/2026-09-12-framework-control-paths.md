## 现在能回答什么

问题：“这四笔请求为什么只有两笔被处理？”

| 请求 | 路径引擎得到的原因 | 最后数据 |
| --- | --- | --- |
| A001 | FIRST 读入，传入子程序的状态为 PENDING；子程序返回 WORK，随后保存、提交并记录检查点 | DONE |
| A002 | 类型不满足声明的文件访问条件，根本不进入业务校验 | PENDING |
| A003 | NEXT 读取成功，实际子程序收到 REVIEW 并返回 SKIP；控制 COPY 不进入保存段 | REVIEW |
| A004 | NEXT 读入，校验通过后保存、提交 | DONE |

文件筛选和业务跳过现在是两个独立原因。进入 A003 子程序时，处理决定还带着上一笔的 WORK；子程序实际执行后将其改成 SKIP。这个过程有实参、形参布局、返回写回及源码位置记录，不是按字段名称拼接说明。

批处理正常路径实际发生的访问顺序是：FIRST、SAVE、COMMIT、CHECKPOINT、NEXT、NEXT、SAVE、COMMIT、CHECKPOINT、NEXT、CLOSE。联机入口按请求键 GET，最后选择 SUMMARY、REVIEW 或 ERROR，不套用批处理循环。

## 失败与重启的区别也保留下来了

| 场景 | 最终业务状态 | 数据及恢复义务 |
| --- | --- | --- |
| 保存遇锁 | LOCK | 没有提交更新；不把锁冲突当作空文件 |
| 提交失败，回滚成功 | CMER | 原持久数据不变，待提交写入已清除 |
| 提交和回滚都失败 | RBER，原始原因仍为 CMER | A001 的 DONE 仍是待提交写入；CLOSE 不会替它回滚 |
| 检查点失败 | CKPE | A001 已提交，但没有新检查点；不能抹掉已提交结果 |
| 提交并记录检查点后，后续读取失败 | IOER | 保留已提交的 A001 与检查点，供下一次恢复 |
| 第二次从前次模型输出恢复 | OK | 从 A001 之后读到 A003，跳过后处理 A004；不再次保存 A001 |

重启案例使用前一个案例实际产生的已提交数据和检查点。检查点绑定契约版本、数据哈希和访问路径；没有检查点、键不存在或绑定不匹配时停止，不假造成功。这些校验只保障模型一致性，不认证生产检查点。

## 为什么不是固定样例故事

测试会修改源码再重新分析：在 FIRST 后插入额外 NEXT 会漏处理 A001；改变子程序条件会改变处理记录；在控制 COPY 末尾覆盖错误状态会导致原错误预期失败；删除控制 COPY 则不能闭合路径。

独立审查还复现并修正了两类错误闭合风险：小写 CALL 不得绕过已有被调源码而使用外部契约；带 INITIAL 等未支持生命周期条款的程序不得错误沿用上次工作存储。原始源码行、COPY 包含位置和哈希逐条核对，布尔值与整数也不会被验收器错误判为同一记录值。

## 本次退出边界

这是给定输入下的一条确定性、有步数上限的条件化路径。未知条件停止；普通源程序调用只采用普通进入/返回假设；外部错误按场景明示选择。不自动遍历全部路径，也不证明生产执行。

契约当前限定单数据集、等值条件合取、唯一升序键、更新现有记录；源程序文本状态只支持 ASCII。复杂 DDS select/omit、JOIN、真实 ODP、并发锁等待、多数据源事务、完整计算、Job/CL 与配置路由仍待扩展和同版资料验证。新路径工具尚未接入 Agent 问答和界面，Windows 包装入口尚未实机验收。

架构与领域建模技能指导本轮始终把“源码事实、声明契约、真实执行”分开记录；代码理解技能用于复用既有控制流与证据结构，避免另造不能追溯来源的结果。
