# Smart AS400 业务分析质量与速度对比

当前最需要补齐的是 **IBM i 运行上下文和答案完整度**。已有算术反例在本轮所测范围通过，但 CL 批次启动、库列表、文件覆盖和真实框架效果还没有形成完整可查询的链；离线构造的不完整回答进入默认链后，仍可能遗漏已在证据包中的条件、错误处理和后续累加。缩短时间阈值不能解决这两类问题。

本轮完成了实际静态组件运行、默认问答链的离线机制回放、目标能力核查和官方产品资料对照。**尚无商业产品同题端到端实测，也没有新增真实公司模型或 Windows EXE 验收，因此不能宣布完整问答质量或速度胜出。**

源码基线为 `639f86825819acb463c5926551d70fda2e39b712`，产品分析逻辑为 `3b099c058f258824237835d7ea802a90055dee02`。测量机器为 Apple M2、8 GB、macOS arm64；Python 3.14.4。原始结果、逐次时间、输入与工具哈希见同名 JSON 和本地证据包。本轮未改变产品实现、依赖、EXE 或发布状态。

**实际质量结果**

统一语料清单包含 11 个中性合成程序，以及固定 CardDemo commit `59cc6c2fd7ebd7ef7925cad552a01a4b8b6e4d5e` 中两个程序和六份 COPY；各工具实际执行的子集不同，以原始结果为准。各组分母不同，不能换算成跨产品准确率排行榜。

| 实测范围 | 结果 | 能证明什么 |
| --- | --- | --- |
| 我方 11 个已知语义反例 | 58 项断言通过；另 7 项算术异常/调用链探针通过 | 所测读写角色、限定字段、occurrence、作用域、Section 目标和部分流关系正确；不是 65 道业务题，也未执行完整 COBOL 数值语义 |
| 我方 5 道公开问题、7 个 fake 分支 | 均有最终正文，两类错误声明发生修订；逐答案审阅仍发现遗漏 | 默认核验与保留正文机制运作；不证明真实模型准确率或答案完整 |
| 我方两个 CardDemo 原始程序的 Builtin IR | 均为 `parse_complete=false` | 仍有不支持的 IF、INITIALIZE、STRING 或 MOVE 形态；纯前端计时未展开 COPY，不能称完整分析速度 |
| ProLeap 原生 grammar/ASG 与自写投影 | 11 程序的 20 条赋值读写正确；18 个具体检查正确，3 项测量缺项。8 条局部公开合同中 7 条匹配，REWRITE 未被比较桥导出 | 有可用的独立解析与绑定参照；未测项不算工具错误，不等于完整 def-use、源证据或业务解释通过 |
| REKT 同 8 条局部公开合同 | 每轮 2 条结构匹配、2 条 ADD 图边错误、4 条投影不支持，三轮一致 | 图导出成功不等于业务规则正确；generic 节点仍保留原文，不能称源码丢失 |
| Che4z 2.5.1 原生 CLI | 固定格式小例获得 AST；两个公开程序均退出 1，只有 URI/language，无 AST/诊断 | 公开程序测量不可用；原因未定位，不能据此判定整个工具的语言能力 |

REKT 的 ADD 问题有公开程序和最小例两份证据：`ADD A TO B` 导出写 A、读 B；`ADD A TO B GIVING C` 导出写 A 且缺少 C。相邻 `MOVE 0 TO C` 正确写 C，排除了把所有边方向读反的解释。固定提交的 ADD 依赖分支交换了输入/目标，与原始图相符。结论仅限所测 RC03 图导出路径，不外推解释器或未测最新分支。[固定版本源码](https://github.com/avishek-sen-gupta/cobol-rekt/blob/beae6b716ba97793cfd9004802747918af7caea3/smojol-toolkit/src/main/java/org/smojol/toolkit/analysis/graph/DataDependencyPairComputer.java)

ProLeap 的输入变换、证据位置也有边界：free fixture 每行增加一列中性 TANDEM 指示位，原始和变换哈希均保留；原固定格式程序未改写。COPY 展开坐标尚未映射回原始文件，所以不能把此次原生位置结果直接当成可点击的生产证据。运行版本为发布的 2.4.0，当前主分支未测。

固定格式短行续行字符串的填空语义尚未独立评分，不能由这些通过项认定完整续行兼容。最初将 sparse index 直接传给旧 CFG 的两项失败仍保留；58 项通过采用默认链所建 structural sidecar 对应的受支持接口。这是测量输入契约更正，没有产品修复或提分。

**默认答案的完整度差距**

逐条审阅七份实际保存答案与固定源码/gold 后，发现以下内容已在供应的全文中，却未完整写入答案：

| 问题 | 已保留的正确内容 | 需要补齐的内容 |
| --- | --- | --- |
| 超限拒绝 | 公式、比较方向、102 被 103 后续覆盖 | INVALID KEY / 101，以及余额来自外部文件的边界 |
| 月息正例 | `/1200` 公式与累加顺序 | 调用处非零利率条件、金额尺度和未使用 ROUNDED 的边界 |
| 月息错误修订 | 999 已修为 1200 | 修订后仍未补出已供源码中的 ADD 累加及后续写交易调用，保留“累计值待核对”；这不是修订删除了原有正确事实 |
| 账户更新 | 本题 gold 所列余额更新、归零、REWRITE、状态及错误处理已覆盖 | 仍不能把静态改写请求认定为数据库运行成功 |
| 文件映射与未实现段落短答 | 核心结论成立，未编造手续费 | 补充运行配置或调用点上下文；不能因缺少固定章节将整个正确短答阻断 |

原机制测试中有两个正例的 `source_assertions` 为空，错误分支主要检查“是否发生过修订”，没有检查修订后是否保留其他必要事实。因此“7/7 机制通过”必须与业务完整度分开。这里是独立代理对离线答案的源码审阅，不是人工签字或真实模型评分；没有由此编造准确率。

**实际速度结果**

下列阶段工作量不同，分别报告，不计算倍数排名。本地阶段的墙钟计时按工具顺序执行，操作系统文件缓存未清空；样本少，不报告 p95。

| 阶段 | 实测 | 计时边界 |
| --- | --- | --- |
| 我方 11 小程序 IR | 各文件 7 次重解析的中位数相加 9.355 ms；3 个新进程整批中位数 73.799 ms | 前者不含读文件/启动；均不含建索引、完整调查或模型 |
| 我方 1,000 个独立合成程序、139,000 行 | 首次 business_sparse 索引 18.778 s（单次）；无变更复用中位数 231.553 ms（3 次） | 没有跨文件 CALL/COPY 复杂度；不能代表复杂企业仓库尾延迟 |
| 我方新 FactStore 读取单程序 | 中位数 29.202 ms（7 次） | 程序事实读取，非整题回答；没有将对象内字典缓存当作业务查询速度 |
| 我方中性批次默认链到首个 transport 入口 | 明确程序的问题 141.4 / 125.8 / 124.4 ms | 6 份源码页、8,282 源字符、请求 99,112 bytes；首轮建立 semantic sidecar，后两轮复用；未发送远程请求 |
| ProLeap 两个公开程序 | warm 中位数 182.643 / 226.207 ms；首轮 1,101.965 / 1,216.081 ms | 含文件读取、COPY 预处理、parse/ASG 与自写投影；不含 JVM 启动 |
| REKT 两个公开程序 | 新 JVM 整次 CLI 中位数 3.122 / 2.741 s（各 3 次） | 含 COPY、AST/CFG/数据结构、四类 JSON 导出和落盘；无 LLM |

另测“这个批次怎么触发、哪些记录会跳过？”时，每次使用无历史的新会话，未唯一绑定程序，首请求约 19–21 ms、源码页为 0，状态为 `needs_discovery` / `can_answer=false`。这是发现请求的准备时间，不能作为快速完成分析的成绩，也不能据此判定已有焦点的追问失败。

明确程序时本地准备较短，说明在这个小样本上本地准备没有复现“几十分钟”。尚未测得远程模型耗时、后续补查次数和完整答案时间，因此这轮不能给出办公室长等待的唯一根因。下一次实测必须把本地准备、请求发送、首段有用结果、补查、修订和最终覆盖同时绑定到同一 run。

对同一请求的精确计量显示，99,112 bytes 中源码原文只有 8,282 bytes。较大字段包括 `file_impact` 21,450 bytes、`call_chain` 12,877 bytes 和调用效果边界 7,350 bytes；部分参数数组重复七次。只读共享字典试验将请求降为 90,445 bytes，解码后完整对象相等，保留全部六份源码页、49 项文件观察和九个调用 occurrence。这是可压缩空间的证据，尚未接入产品，不能换算成 token、答案质量或远程耗时收益。重复信息也不是此次长等待已确认的唯一原因。

**目标平台的实际缺口和改造顺序**

本轮选择已有框架、文件影响和默认问答相关测试共 81 项，全部通过，0 跳过；使用 fake transport 或无模型，联网 socket 禁止。现有能力包含版本化效果契约、实际调用参数/布局、版本冲突处理，以及有限 DDS/PFILE 供证。`target_validated=false` 仍然成立。

中性框架样例只有 4 个 COBOL 程序与 7 个 COPY，没有真实 CL、DDS、SQL 或外部存储实现；未配置手册时框架效果为空。CL 当前可收录和分类，但未形成 SBMJOB、库列表、OVRDBF、MONMSG 等效果解析与回归。DDS/SQL 的有限能力不能升级为实际逻辑文件选择、访问路径、锁或事务已确认。

据此，下一批应按以下顺序进入已有默认链：

1. 将 CL 入口、参数、作业描述、库列表顺序、OVRDBF 的目标/成员/作用域与 DDS/COBOL 文件关系接成可查询证据。配置不明保留候选；真实调度器和表数据仍需对应证据。批次触发题首先检索这条链。
2. 对已供源码建立逐题必须覆盖的业务事实，修订公式时保留原有正确条件、累加和副作用；补齐当前 IR 已报告的不支持形态。短答按问题范围验收，不能以固定章节作为质量代理。
3. 复用现有 SQLite、FactStore、sidecar 和摘要，把稳定关系在导入/变更时生成，提问时按程序/字段/路径读取；对证据包中重复的计划、元数据与正文计量后再删减。用答案覆盖验证压缩效果。
4. 用相同公开或获准脱敏的 IBM i 样例测首次导入、刷新、首次问答和追问；绑定最终 Windows EXE、真实模型、答案哈希与实际证据。质量、完整度和延迟共同通过后，才按现有联合验收流程正式发布。

这是由本轮结果支持的实施顺序，并不表示以上缺口已经修复。商业产品本轮运行数为 0，付费模型请求为 0，企业源码外传为 0；既有候选版本不会因这份比较自动转为正式版。

复核入口：同目录的 `2026-10-15-ibmi-business-comparison.json` 保存机器可读汇总及逐项证据指纹；本地 `.build/comparison-2026-10-15/evidence.zip` 保存原始结果、夹具、实际 fake 回答、原生图、计时样本和历史测量脚本，内附完整性核验与重放说明。该证据包用于审计，不是办公室验收 EXE；第三方解析器与 Java 运行时未打包进产品。
