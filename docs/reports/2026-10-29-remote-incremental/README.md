# Cloud 每周更新增量同步回归

已确认旧版存在实际传输问题：打开已保存资料库和同版本检查均可复用本地文件，但 Cloud 检测到新提交后仍重新下载整个仓库 ZIP。现在首次接入保留一次归档下载，后续更新先比较两个固定提交，只获取新增或改变的所选目录文件，按已记录 SHA-256 核验并复制其余本机文件。原快照不覆盖、不用硬链接，新文件编辑不会影响旧答案所引用的版本。

依据官方 [Cloud diffstat](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commits/) 使用新提交在前、旧提交在后的 `new..old`，并明确 `topic=false`，完整处理分页。元数据和内容均从[固定提交的文件接口](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-source/)读取，覆盖新增、修改、删除、重命名以及进出所选目录的重命名。接口返回的分页 URL 只允许同一服务、仓库和提交比较，不允许显式改变筛选或比较语义，不把凭据发送到响应指定的其他地址。

旧快照没有下载清单时，只枚举旧提交目录元数据，再核对与本机源码路径绑定的最早索引版本散列；未经记录或已损坏的文件单独获取。新快照在源码目录外保存文件清单，因此不被业务源码索引当作程序读取。认证、404、429、缺页、内容长度错误或取消都停止本次任务并清理新快照，不自动重试或改为整仓下载。原目录及其清单不被修改。

`verification.json` 和 `tests.log` 记录88项定向回归全部通过、零跳过，其中19项增量传输测试使用实际本机HTTP服务器，另含6项工作台增量接线回归。12,202文件、约12.5 MB 的合成旧快照只修改一个文件后，实际更新有3个HTTP请求：1次变更清单、1次文件元数据、1次文件内容；下载16字节，复用12,201文件，没有ZIP请求。新快照准备约1.899秒，耗时只反映本机磁盘和本机模拟HTTP，不代表企业网络或索引速度。

独立复核还复现了两个遗漏并补上反例：远端版本没变但本机源码缺失时，工作台原先只看索引就误报最新；明确返回空字符串 `next` 且没有总数时，分页原先可能接收不完整差异。现在主动更新会核对本机文件集合与 SHA-256，缺失文件或等长且保留修改时间的篡改都在新快照中按文件修复；原源码和旧对话不被改写。完整副本仅请求一次版本元数据、不下载内容；普通重启和打开不调用全库完整性检查或远端接口。无效分页停止并清理新快照。

首次 Cloud 接入仍下载一次整仓ZIP；改为逐文件下载会让万级源码产生万级请求，并可能触发[官方API限流](https://support.atlassian.com/bitbucket-cloud/docs/api-request-limits/)，所以本次没有把这种方式作为默认“加速”。Server / Data Center 仍使用所选目录归档。新提交生成新快照后仍建立新的本地索引，本次没有将文件增量下载冒称为索引增量或远程按需查询。

另以公开开源仓库的固定提交完成5次不带凭据的元数据读取，核对真实目录页、文件 `format=meta` 与diffstat分页。文件条目含请求snapshot的 `commit.hash`、`size` 和列表形式的 `attributes`；diffstat内的old/new只含路径、类型与链接，本实现不要求其包含文件大小或提交对象。真实目录游标是非数字字符串。官方[分页契约](https://developer.atlassian.com/cloud/bitbucket/rest/intro/#pagination)将next定义为不透明链接，因此实现接受省略默认参数或使用游标的同endpoint下一页，仍拒绝换仓库、换提交及显式改变筛选。原始精简记录见 `public-api-contract.json`；未读取该公开仓库的文件内容。公开契约检查不代表企业认证或企业完整同步已验收。

未调用真实企业仓库或模型，未构建应用或发布包。工作台入口的增量参数传递、持久记录、离线打开、完整副本复用与坏副本修复已覆盖；页面显示由主任务整合验证。这份报告证明本轮源码的传输、版本和错误恢复机制，不替代目标电脑验收。

最后一次独立复核另修复 429 限流错误未进入界面映射的问题，提交阶段和后台任务失败均使用明确的三语提示，不展示服务端原文或自动重试。首次下载的超时和容量提示也明确 Cloud 获取整仓快照，选择子目录不会减少首次传输。88 项远端 Python、42 项远端界面/i18n 回归再次通过；整合后的全部 262 项前端测试通过。失败结果持续显示并支持页面刷新恢复；完全退出并重启应用后仍恢复原库和对话，但不保留上次失败任务卡。

对用户截图中的固定提交链接另作了入口复核：打开已有资料库，经“检查并更新”填写分支，或勾选“跟随默认分支”，两条路径都沿用旧快照作增量基线。本机 HTTP 模拟分别发生 4 次、5 次请求（后者多一次默认分支元数据），均只下载 1 个变化文件，零 ZIP，旧源码不变。仅清空版本栏仍保留原固定提交；从侧栏重新“接入”并选择不同版本属于建立新来源，可能再次获取初始 ZIP。周更应使用已有资料库的更新入口。
