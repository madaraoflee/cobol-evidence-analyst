# 累计业务分析、上下文整理与全局续查

本轮修复的是多轮调查中“前面已经读到的业务条件不能延续到后面”的状态断裂，而不是把答案写得更短。此前修复的原文回读目录能够帮助重新定位被挤出的片段，但并不等于保存累计业务分析；当前实现增加带来源的累计分析和专门的上下文整理，同时把受批次上限影响的未读来源、关系和规则继续保存在全局待查项中。

## 已定位的问题与处理

旧流程中的来源窗口是有界的。早期源码离开当前请求后，仅靠最近片段或回读位置，后续回答仍可能失去此前的业务解释。现在，整理请求读取真实供应过的原文和上一代累计分析，保留规则候选、适用条件、处理顺序和交接、冲突及待查事项。新一代必须通过来源及条目保留核对，才能替换工作摘要；原文、旧代和实际请求记录继续保存在本地。后续回答引用早期来源时仍核对原始版本、行范围和包含实例，不把摘要当作源码。

另一类缺失来自批次限制。来源展开、单批文件与规则数量限制曾经可能使未处理分支不再进入下一轮。现在通过持久待查状态分批继续，当前批次“可以回答”与整题调查“已经完成”分别记录。动态目标尚未确定、材料缺失和用户配置的预算边界仍作为明确限制保留；不会因为一个局部答案已经有依据，就把已发现的其余链路标为完成。

整理失败、响应不完整、来源绑定失效或输出过大时，上一代分析和原文保留，显示未完成状态。同一失败材料不自动无限重试。恢复重放已有真实响应，整理、回答及复核共用整题模型额度，断线不会增加可用次数。

普通聊天追问曾是另一处交接缺口：新问题即使沿用同一业务对象，也不等于恢复同一道问题的调查。现在，系统先在本地核对会话归属、对象、版本及实际请求依据，符合条件的普通追问可以继承原文和累计分析，无需点击“继续补查”；新问题使用自己的证据义务与预算。换题、归属或版本不符时不沿用旧分析。

有限预算下还有一项交付修复：当追问仅剩一次可用请求，而继承的旧原文仍需整理时，系统保留全部原文及待整理记录，使用预留请求回答当前依据能支持的部分并明确标为未完成，不能在尚未请求模型时直接拒答，也不能把未整理材料视为已完成分析。

界面默认显示简短进展，可以展开待核阶段发现和上下文整理状态；选择“仅进度”只影响展示。这里展示的是可核对的工作结果，不是模型私有思维链。“结构保留核对通过”仅表明条目与来源关联保留，不证明改写后的完整业务含义一定正确。

## 验证记录

新增的桌面 HTTP 场景读取十四个中性合成辅助文件，保留默认源码窗口和请求字节上限。通过实际接口完成十五轮普通请求及四轮专门整理；后面的请求仍携带第一份辅助来源中的条件、交接和未完成事项，早期原文已经离开当前窗口时，其引用仍能通过本地不可变原文核对。测试同时核对持久化的四代分析、唯一请求记录、共享额度、实际传输大小和真实进度接口中的整理中及整理完成状态。

该场景随后关闭并重新打开服务，以同一会话直接发送一个普通追问。追问只新增一次模型请求，继承全部四代累计分析及早期条件的原文引用，同时保留独立的新问题预算。全局待查状态另有引擎级检查，确认有待查分支时真实进度和恢复点均保存正数，不能被摘要中暂时为零的待查条目掩盖。

原有九轮显式回读场景单独关闭自动整理，用于验证回读后备路径；新增场景使用默认开启的整理机制。两条路径分别验证，关闭设置不用于绕过新功能验收。

最终源码验证绑定提交 `6a67df0b16528d99733d248b689a5df5d298315b`，在没有未提交改动的工作区完成。四个分片合计 **4,817 项 Python 测试通过，零跳过**，每项恰好执行一次；另有 **296 项浏览器测试和 1 项工具测试通过**。详情及记录摘要校验值见 [source-regressions.json](source-regressions.json)。

## 尚不能据此宣称的效果

结构保留与可恢复性测试不能证明模型在自然语言整理中完全没有遗漏细微条件，也不能保证尚未被解析器发现的全部程序入口或运行路径都已覆盖。本轮没有使用公司源码，也没有向外部模型发送公司材料。真实复杂链路的业务解释质量和目标电脑的启动时间，仍需同包真实模型及目标设备验收；正式发布继续执行 `tools/publish_desktop_release.py` 的联合验收门禁。
