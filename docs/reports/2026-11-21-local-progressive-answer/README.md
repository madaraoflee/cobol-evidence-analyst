# 普通本地问答的同题交付核对

原题沿用“保费收取时 reserve 和 refund 的扣减顺序及适用条件是什么？”。主程序 `cash.cbl` 共 10 行，退款程序 `return.cbl` 共 7 行，与此前在线对照使用的两个文件逐字节一致。这次从普通本地工作台导入源码、建立临时资料库、发送问题、读取任务进度和最终对话，再从助手消息重新打开原文引用。[原始中性程序](../../../poc/tests/test_online_automatic_source_search.py) · [本地入口和观察方法](../../../poc/tests/local_progressive_acceptance.py)

在改动前的固定版本 `59a00784bfcdb025f61bf749bd7869c3087f1d0e`，首轮模型请求已经包含两个完整程序。暂扣响应时，进度显示“已补充相关源码，正在核对处理条件与结果。”，对话只有用户的问题。放行一句“先使用准备金，剩余应收大于零时调用退款处理。”后，工作台结束本轮并标为部分回答。换成讲清条件和金额的完整回复，也只请求一次，同样标为部分回答。[改前记录](before.json) · [改前回归输出](before-tests.txt)

## 修改后的实际交付

| 原题和受控输入 | 等待第一轮回复时 | 实际交付 |
| --- | --- | --- |
| 首轮只讲准备金和调用退款 | 已显示主程序的准备金类型条件与扣减动作，以及退款子程序中的严格小于条件，每条都有原件位置 | 携原草稿再次请求，要求核对顺序、跳过条件和最终应收。第二轮结束后显示一条完整回答 |
| 首轮即给出完整规则与金额 | 同样可以先看两条已证实的条件 | 一次请求后标记完成，交付有出处的扣减顺序及最终应收 |
| 源码改为小于等于，首轮故意仍答旧规则 | 已显示退款等额可扣的规则 | 再次请求后交付新条件，只有退款余额更大时才跳过 |
| 移除退款子程序，持续给出浅答 | 只显示准备金条件 | 复核后仍标为部分回答，只引用实际存在的主程序 |
| 两份源码齐全，单轮只许一次模型请求 | 可见两份程序中各自已核实的条件 | 用源程序核对完整执行路径，一次请求也能交付完整答案 |
| 缺少退款子程序，单轮只许一次模型请求 | 只显示准备金条件 | 保留部分状态，并显示已核实的准备金规则和有待核对的退款条件与最终应收 |
| 缺少退款子程序，模型却自行给出完整退款公式和数字 | 只显示准备金条件 | 继续调查后仍缺子程序，只交付已证实的规则，指出待查的退款程序。模型编造的比较和具体金额不会随正文交付 |

四组具备完整调用路径的最终正文由程序按已读源码生成。每次都从已保存的助手消息重新打开引用，核对文件内容、哈希和行段。阶段说明与模型草稿分别观察，等候期间对话历史只有用户的问题，完成后仅增加一条助手消息。七组均未连接网络。[七组实际状态、作答请求和最终正文](after.json)

## 同题的业务判据

类型等于 `1-RESERVECREDIT` 才减准备金。其他类型跳过准备金，仍继续检查当前应收。应收大于零才调用退款程序，零和负数直接保留。退款余额严格小于此时应收才扣减，等于或大于时跳过退款。子程序修改的是调用方传入的应收。进入时的应收扣除实际生效的两笔金额，就是交回的应收。例中应收 100、准备金 20，退款为 30 时余额为 50，退款恰好为 80 时最终仍为 80。这里的金额是按样例源码推导，程序没有提供实际记账的证据。

另设一组同题对照，只把退款比较由 `<` 改为 `<=`。输入的第一份回答仍沿用旧规则，具体数字故意保留“退款 80 仍为 80”。新的源码要求等额时扣款，正确余额是 0。还单独移除子程序，核对系统能否在缺少退款依据时保留部分状态。

## 重放

在项目根目录运行以下命令。第一条从本地 Git 对象读取改前的产品和既有夹具。第二条对当前版本重放相同输入。普通问答沿用工作台默认设置，两项预算对照显式将模型请求上限设为一次。模型回复由内存接口按场景控制，每次运行都拦截网络连接，首答等待时长由实验控制。

```sh
python3 -B docs/reports/2026-11-21-local-progressive-answer/replay.py --baseline
python3 -B docs/reports/2026-11-21-local-progressive-answer/replay.py
python3 -B -m unittest discover -s poc/tests -p test_local_progressive_delivery.py -v
```

本次比较覆盖中性源码、受控回答以及用户在本地工作台能读取的进度和消息。公司现场模型质量、真实等待时长、目标设备和最终可执行程序仍待现场核实。

## 对已有问答的影响

在初版 `026eb26` 上，全量测试定位到两项兼容问题。已有四步收款题在列出“最后奖励款”后才逐笔说明足额扣减、不足跳过以及金额来源，初版误把“最后一项”当作最终结果的起点，触发第三次请求。修正后，两次请求即可交付。对于明确追问最终应收的题，仍须给出最终结果。另一项是原有传输限额适配器收到新参数而报错。修正后保留原调用约定，按拟合后真正供给的源码复核，不用先前已移出请求的页证明当前答案。[四步扣减复测](../../../poc/tests/test_collection_flow_delivery.py) · [传输限额复测](../../../poc/tests/test_retrieval_evidence_regressions.py)
