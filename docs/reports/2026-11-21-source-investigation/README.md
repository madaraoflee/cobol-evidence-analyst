# 2026-11-21 从真实提问入口核对搜索、调用和交付

本轮用同一组中性 COBOL 源文件、问题和受控模型比较基线 `81b91c76` 与修复版本。测试记录了问答入口实际交给模型的物理源码行、执行的源码操作、待核问题、界面进度和最终回答。业务结果来自测试程序中的已知规则。公司源码、公司模型和目标 Windows EXE 仍待实机验证。

| 用户看到的现象 | 修复前的证据 | 相同输入的复测 |
| --- | --- | --- |
| 找到扣款入口，回答仍说资料不足 | 75 个初始化调用在前时，检索命中 Suspense 分支及 CALL，调用关系取前 64 条后漏掉被调方。只放 1 或 9 个干扰调用时可以取得公式。 | 先以命中原文的物理位置选调用。普通问答的首个模型请求已包含条件、调用参数、被调程序中的正数判断和实际减法。不同业务线索可取不同子程序。 |
| 在线显示调查失败 | 模型立即给出无引用答复时，连续三次协议纠正，源码读取为零。 | 在固定版本中按词查物理行，打开匹配的两个文件再问模型。样例第二次模型请求即可用两处原文说明准备金与退款的衔接。 |
| 回答引用了文件，又说没有收到 | 引用 main.cbl 第 1 至 13 行，却把“本轮未提供 main.cbl”作为成功回答交付。 | 对照同次请求确实供给的原文，要求重新回答。样例第二次起草用同一份原文回答正数分支，文件只打开一次。 |
| 只看到提示文字就断言扣减先后 | 引文全部内容为一条输出提示，系统仍宣称“先用账户余额，再用退款”。 | 检查引文能否支持这种业务主张，继续查找执行逻辑。若仍缺证据，保留精确缺口和原件位置。 |
| 页面一直显示读取 | 不同源码操作只保存同一阶段，下一轮模型等待覆盖了已经完成的查找。 | 页面保留本次任务最近实际完成的步骤，能区分候选数、匹配行、跟踪关系、已核对原文以及有限扫描。 |
| 继续调查时具体待核问题消失 | 空引用答复中的金额不足、失效冲正等后续问题未进入断点。 | 在有界的搜索与继续调查之间保存合法的业务待办。 |

本地请求记录见 [修复前](local-before.jsonl) 和 [修复后](local-after.jsonl)。在线请求与交付记录见 [修复前](online-before.json) 和 [修复后](online-after.json)。每个故障与相应测试逐条登记在 [缺陷台账](../../bugs/registry.json)。这些用例验证了系统怎样查证和交付，不推断公司的实际扣款优先级。
