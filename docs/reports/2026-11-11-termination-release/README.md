用户本轮明确要求检查长时间或不结束的调查、修复确认缺陷、上传GitHub并生成可运行EXE。构建授权已恢复；正式版仍遵循同包真实模型、人工评审和办公设备验收门禁，缺项保留候选。

## 本轮确认的七项缺陷

| 编号 | 修前实际表现 | 修复 |
| --- | --- | --- |
| BUG-20261111-001 | 空查询的归档回查连续12次相同批次，靠测试注入500才停 | 新原文与实际核对才算推进；连续无进展有限停止 |
| BUG-20261111-002 | 合法回查把坐标对象作为字典键，触发系统错误 | 正确保留坐标和来源ID两种目标，验证真实归档原文回读 |
| BUG-20261111-003 | 相同不确定分类仅换文案，16次请求仍无完成项 | 先覆盖所有未见项，再按实际进展判断停止，保留全部不确定项和待办 |

| BUG-20261111-005 | 相同确定失败动作跨检查点反复尝试，不计无进展 | 确定失败参与重复检查；停止后不重放已判无进展的执行指令，业务待办仍完整保存 |
| BUG-20261111-006 | 持续慢速响应使空闲超时失效，读取中取消要等整个body完成 | body每块前后检查deadline/取消，保留既有错误分类、URL策略，不自动重试 |
| BUG-20261111-007 | Git Windows自动换行将唯一PF冻结夹具从64字节变为66字节，SHA与原金标不符 | 固定PF为LF，真实Windows过滤逐条核对18份原文，原gold及旧测试不改 |

002/003的修前证据分别为 `valid-before.json`、`uncertain-before.json`；001为 `lookup-invalid.json`。旧源码执行本地新增7项测试全部失败，见 `old-runtime-new-regressions.log`。在线修前证据为 `failed-action-repetition.json` 和 `final-source-run-budget.json`。全部使用中性源码、实际解析/调查入口与受控响应，没有调用公司模型或传输公司源码。

30秒是在每次来源读取前检查的时间片，单次读取仍沿用既有传输超时，因此不是严格30秒整轮墙钟保证。完整全库分析仍随源码规模、业务复杂度和公司模型速度增长；本轮不把离线速度当作公司耗时或额度保证。

006另有真实本机慢滴复现：配置50毫秒空闲超时，数据持续到达时仍约380毫秒才成功；40毫秒请求取消后约321毫秒才结束，见 `slow-drip-before.json`。修复在open返回后及body分块读取前后检查总deadline和取消。连接/header内部尚不能立即中断，仍受原socket空闲超时约束；这条边界明确保留，不把body测试冒充所有网络阶段严格截止。
