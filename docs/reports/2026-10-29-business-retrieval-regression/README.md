# 业务检索、回答要求与增量更新回归

本轮针对“源码已在本机，答案却称不足”“框架解释盖过业务结果”和每周 Cloud 更新需要整包下载的问题，检查实际检索、原文供应、模型请求与最终状态。没有增加回答必须满足固定模板才能展示的门槛。

## 已复现并修复的链路

1. 长中文问题产生的大量搜索词挤掉了后续补查的新词，文件虽命中，截取原文却只取文件开头。现在优先保留本轮补查词，并在对应命中处截取；长问题中的短中文业务词也保留机会。
2. 请求容量不足时，自动匹配的无关框架概述曾挤掉实际业务段落。现在先移除这些辅助资料，保留已绑定当前源码的框架规则，以及用户或模型明确查询的框架内容。32 KiB 边界测试中的两份业务原文均被实际发送；这不是对所有规模都能完整供应的承诺。
3. “只能看到一个赋值语句”曾被算作已解释业务计算，即使同时宣称无法回答。现在这种没有业务内容的语法描述进入已有的有界补查流程；真正的运行输入、日志或生产执行情况未知仍保留，不因此无限请求。
4. 默认格式不再强制列出与问题无关的空类别；框架用于解释业务读写和控制，只有影响所问结果或用户明确要求时才展开技术标识。金额单位与币种按材料表达，不能自行补充。
5. 保存的自定义要求在真实请求中确实存在，重启后也恢复。另修复源码评测工具遗漏案例 `answer_instructions` 的问题，使自动调查与配对合成测试都使用指定要求。
6. 同一语句的读、写关系曾重复占用搜索候选名额；分组 `USING` 的成员又未被认作输入，金额累减因此误报循环或来源缺失。现在按不同语句计数，并以同一程序的签名、LINKAGE 布局与同版本原文绑定输入。返回参数、另一程序的同名字段以及外部调用后的未知修改不会冒认成已知输入。
7. 缩进造成索引候选与语义分析的列号不一致，曾跳过更精确的来源检查。修复定位后进一步分开静态输入来源与实际运行值：已声明且实际接收的参数有可解释的来源，运行值仍未知；`LINKAGE VALUE` 不变成运行初值。缺少单条语句调查时会自动精确补查。
8. 真实模型正确写出的业务状态曾因没有源码字符串引号，被本地检查误改成整段技术赋值清单。自然业务表述现在保持未验证的语义状态，不机械改写；显式错误的赋值或数字公式仍核对。另修复截断在行内字段名中、下一段从完整字段名重启时的重复拼接，保留原始响应计数，代码块和歧义文字不删改。
9. 真实模型返回的调用标记曾漏过 JSON 动作识别，出现在最终正文和流式预览中。现在识别通用调用容器并进入既有的单次格式纠正流程，后续合法 JSON 才能执行补查；正常业务 XML、HTML 和示例仍保留。明确收到的空正文可使用原有材料与自定义要求再生成一次；拒绝、过滤、未知内容结构、超时和不确定请求不自动重发。纠正机会写入检查点，中断重放不会刷新次数。105 项定向测试及另一次 29 项独立复核通过，原始模型返回的离线重放记录保留在进展收敛报告中。

本轮同时整合 [Cloud 文件增量更新及独立审查](../2026-10-29-remote-incremental/README.md)和另一对话的[按实际进展继续调查与防止无效循环](../2026-10-29-progress-convergence/README.md)。后者默认不再设总请求数／调查轮数的固定上限；重复读取、无进展修订和截断续写仍有独立收敛机制，用户明确保存的限制继续有效。

## 真实模型验证的范围

`fixture/` 是本次编写的中性业务源码与独立数值预期：主程序加一个 2,758 行的抵扣程序，规则分散在后部，另有辅助框架说明。三个问题分别检查不提供程序名的长中文业务提问、保存并重启后的固定栏目、以及明确询问框架状态的业务影响。预期答案没有发送给模型。

第一轮通过实际 `WorkbenchState` 与既有模型配置发出五次请求，原始答案保存在 `first-live-run/`。业务顺序、条件、封顶与金额推导正确，自定义答案遵循指定栏目；但默认答案自行加了“元”，且三题均有错误的 `question_evidence_incomplete` 状态，因此该轮不标为全部通过。发现问题后继续修复，保留原记录，不用新结果覆盖失败证据。

第二轮记录在 `second-live-run/`：两条业务回答的诊断已正常，币种补造消失；自定义案例一次 TLS 握手失败，没有把任务结束当成答案通过。独立复核还发现本地状态改写与截断拼接破坏了框架题正文，因此继续修复。[实际原始响应拼接回放](./inline-continuation.json)与[状态改写回放](./claim-status-repair-replay.json)保留直接证据。业务题已假设数据准备成功，未展开非准备成功状态；严格原始 gold 中该副项仍记录 partial，不以添加无关技术分支来凑齐评分。

首轮全量 4,236 项中有 5 项断言失败、2 项错误，零跳过。修复了独立验收 watchdog 对空请求上限的处理；其余逐项确认是旧轮数断言、测试把随机哈希中的 `999` 当错误公式、长正文夹具未配置相应输出窗口，以及把输入来源与运行初值混为一谈。保留正文完整性、业务结果、请求大小和真实未知的检查，未删除测试或降低业务断言；后续统一重跑全量。

第二次全量 4,245 项全部通过，零跳过，记录在 `second-full-regression.json`。同版本的第三轮真实模型结果仍是 1 题通过、2 题失败：框架题的五项业务结果均正确；普通题返回未识别的工具调用标记，被错误当作答案；自定义题返回空正文。`third-live-run/` 保留完整答案及独立复核。三轮模型配置指纹一致，自定义要求也在实际 system 消息中恰好出现一次，因此没有将这些失败归咎于“未注入提示词”。继续修复工具协议处理，空正文和远端传输失败不伪装成业务通过。

最终冻结代码的第四轮记录在 `fourth-live-run/`：普通业务题三次调用完成，实际走过“异常调用标记 → 明确纠正格式 → 合法搜索与原文读取 → 业务答案”，八项 gold 全部满足；框架题一次调用完成，五项 gold 全部满足。自定义题第二次请求又遇到安全连接失败，原记录继续保留。在同一代码、同一模型配置与同一中性源码上，单独作一次有界复测，结果在 `custom-transport-repeat/`：两次调用完成，严格只有三个指定栏目，金额推导、条件、封顶和跳过完整，九项 gold 全部满足；两个实际 system 消息中的自定义全文各出现一次。两次运行共八次远端请求，包括失败请求，不将其中的空正文恢复机制冒称为已在这轮真实运行中触发。

新增修复后的首次全量 4,274 项有 9 个失败与 62 个错误事件，全部来自本机回环服务被执行沙盒拒绝绑定端口，见 `sandbox-full-regression.json`。该运行不能算通过；同一冻结源码获准使用本机测试端口后重新运行，没有改产品逻辑或跳过用例。

最终全量 4,274 项全部通过，零失败、零错误、零跳过；262 项前端回归也全部通过。测试前后 582 个代码、配置与测试文件的散列一致，见 `final-verification.json`。真实问答正文的独立复核与源码测试分别记录，不能互相代替。

Windows 构建前再次跑全量时发现新增测试夹具的跨平台错误：文本写盘转换为 CRLF，夹具却拿 LF 字符串计算源码哈希，生产版本校验因此拒绝了不一致的材料。`windows-first-run.json` 记录 4,274 项实际执行、3 个测试方法的 8 个失败事件、2 个既定 POSIX 权限跳过；编译没有执行，也没有发布。仅模拟 Windows 写盘换行即可在本机精确复现。现仅修改测试夹具，使用物理文件字节身份，完整正反例分别覆盖 LF、CRLF，并拒绝冒用另一换行版本的哈希，12 项定向全部通过。前后证据在 `windows-newline-*` 文件中，127 个实际模型运行涉及的生产文件保持不变。随后对新提交重新执行完整 Windows 流程。

这些是源码运行环境下的真实模型开发回归。中性案例不是用户的企业程序，也不是独立留出题；维护代理的逐项复核不冒充人工验收，源码测试不替代最终 EXE 或工作电脑验收。源码哈希与供应范围记录用于核对测试对象，不证明所有业务回答的语义正确。
