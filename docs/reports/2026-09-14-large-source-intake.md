# 大规模源码接入、进度与局部分析修复

日期：2026-09-14

本次把公司源码接入从“等待全库逐语句索引”改为“轻量目录、增量复用、按入口详细分析”，并把缺失源码从整份回答的阻断条件改为相关结论的解释边界。已修改实际运行代码、三语网页、测试和手册；不只是提出新流程。

## 原因与修改

旧接入多次扫描全库并计算 Hash，首次即建立逐语句索引，大程序累积解析对象。网页没有后台进度，程序目录一次渲染全部条目。调查内核还会在连续两次找不到依赖时、读取已有证据之前停止，或因一条不支持的候选结论丢掉其他有效陈述。

现在网页默认 `catalog`：先有界读取程序头部并保存文件目录；未变化文件不重新读正文，新增、修改、删除按实际状态更新。选入口后最多取 24 文件、2 层、16 MiB 原文，依赖探测每文件最多读取 2 MiB。详细索引逐文件处理和释放；未变范围跳过派生关系重建。全文索引删除改为每文件批量处理，避免逐语句重复全表扫描。

为适配用户的 8–16GB 笔记本，应用入口的原文预算从初始实现的 64 MiB 收紧至 16 MiB。低层选择器保留可配置上限。这个预算约束输入体积，不能当作进程内存上限；密集语句和关系可能使索引体积大于原文件数十倍。公司环境仍需测量典型入口的实际占用。

进度使用真实阶段和计数：完成/剩余、百分比、已运行时间、当前文件、大文件解析行数，以及有足够样本时的阶段或单文件预计剩余。未知分母不显示假百分比；无法估计时显示估算中。停止在可检查点执行，已完成目录文件可复用；刷新页面可继续查看，短暂断连会重试。源码库每页 100 项，入口搜索结果有上限，并以路径区分同名程序。

缺 COPY、闭源 CALL 或运行配置时，模型仍可解释已有代码的 IF、COMPUTE、输入输出和调用位置，并保留边界。仅独立通过检查的陈述进入回答；局部结果标为 `PARTIAL`。按需解析范围传入模型并写入结果，防止把局部索引描述为全库。Hash、快照、引用越界和工具协议错误仍阻断；无法推断闭源返回值，也不自动完成未知路径模拟。

## 实测口径

环境：macOS，本地磁盘，Python 3.14.4。数据均本机生成，不含公司源码；生成后操作系统文件缓存已热。以下是两个独立基准，未测公司全库端到端模型回答耗时。

### 目录宽度与增量刷新

12,000 文件，其中 100 个各 80,000 行，其余 11,900 个各 4 行，总 648,891,600 字节。这不是 12,000 个全部 80,000 行。

| 场景 | 耗时 | 正文/头部实际读取量 | 峰值 RSS |
| --- | ---: | ---: | ---: |
| 首次目录 | 2.186 秒 | 2,554,700 字节 | 42.33 MiB |
| 原样刷新 | 0.333 秒 | 0 字节 | 41.89 MiB |
| 改一个大文件后刷新 | 0.337 秒 | 16,384 字节 | 41.94 MiB |

不同进程单独测峰值。目录识别完成不表示全文校验或完整程序发现，更不等于全库语句解析。原始测量在本机 `.poc-data/benchmarks/source-catalog-2026-09-14.json`，复现脚本为同目录 `run_catalog_benchmark.py`。

### 单个 80,000 行程序详细索引

独立合成程序 1,839,984 字节，以重复 ADD 语句构成压力，包含真实索引写入和关系处理。

| 场景 | 耗时 | 索引文件 | 进程累计峰值 RSS |
| --- | ---: | ---: | ---: |
| 首次详细索引 | 7.646 秒 | 133.0 MiB | 372.5 MiB |
| 无改重跑 | 0.060 秒 | 133.0 MiB | 372.5 MiB |
| 修改该文件 | 9.043 秒 | 133.2 MiB | 375.4 MiB |

这一组 RSS 是同进程累计高水位，不能理解为每轮独立内存测量。源码种类不同会改变放大比例。原始结果在本机 `.poc-data/intake-performance/scope-80000-lines.json`。没有建立旧版本全量基线，所以不宣称相对于旧版加速多少倍。

## 验证与边界

最终完整测试：727 项 Python 测试、8 项网页三语与进度／大目录回归通过。Python 3.14 的全套运行有既有 SQLite 连接 ResourceWarning，测试无失败。

自动回归覆盖：未改零读取、单改与删除、缓存恢复、头部截断与文件名入口、不同编码、详细范围预算与取消回滚、同名路径入口复用、详细失败后目录可用但旧证据无效、后台进度恢复，以及缺 COPY/闭源调用仍返回可核对局部说明。

浏览器实际使用 1,101 个合成文件验证导入、刷新恢复、停止和继续。为了能观察进度与停止按钮，验收服务在真实目录回调后增加延时；这段界面演练不是性能基准。局部问答使用模拟 API，真实执行本地索引、证据工具和单条公式核验，未向外部接口发送请求。

本次未获得公司真实源文件，没有运行真实公司 API，也未完成 Windows 实机或特定方言全覆盖验收。用户估计的 8.4–9.6 亿行数据必须在公司机器测首次目录、无改刷新、单程序更新和代表性问题，不能将上面的 2.186 秒外推为该全库的性能承诺。
