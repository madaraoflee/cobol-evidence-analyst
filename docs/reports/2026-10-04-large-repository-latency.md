# 万级源码库问答延迟修复

本次确认的主要故障在本地检索与调查链：模型尚未收到问题，就反复扫描全库关系或解析长源码。修复保留原有完整调用导航、源码哈希及实际供应检查，不用缩小候选范围掩盖延迟。

## 能复现的原因

计算路径调查原来对每个到达程序重新扫描所有关系，并用列表判断是否已访问，调用环和大量根节点会放大为超线性工作。身份定位有无法复用已有索引的大小写比较，局部关系查询的跨表 OR 连接又会扫描无关关系。纯业务词零命中时，还先展开全库导航、再把结果全部丢弃。可选语义解析在首条模型请求之前执行，读取同一文件和 COPY 来源映射也存在重复工作。

多行解析存在独立问题：行号按固定模数检查取消，跨行声明会跳过检查；SQL 每添加一行重新扫描全部前缀。5,006 行 SQL 的旧实现 3 秒仍未完成，而且预算回调只发生一次。新实现逐行维护词法状态，检查点按实际行距触发，同类 5,005 行 SQL 完整解析约 0.018 秒；两行字段声明可在第 256 行及时取消。

## 最终行为

计算依赖用邻接表与集合单次遍历。本题导航和已清洗的源码页可复用，但裁剪、不同原文、框架材料变化或草稿截断会重新判断实际可用证据。唯一明确程序全文先供应，装得下时不再重复深解析。普通片段、全文额度与请求字节限制继续适用。

查询使用既有路径、名称和关系索引；零命中业务定位直接进入有预算的词项调查。公共目录发现入口仍保留旧有全库回退，有匹配时的完整静态导航不截断。关系目录在进程内按数据库、快照和索引构建版本缓存，源码刷新或同内容更换解析选项后重新读取；缓存最多两个快照、总计 96 MiB，超限仅放弃缓存，不裁剪图。

可选深解析默认首轮 3 秒、全题本地 15 秒；首轮取两者较小值，模型等待不占这份额度。达到额度后保留原文、跳过尚未完成的可选语义工作，并记录边界。用户取消优先传播。这不是全部 SQLite、磁盘或问答总耗时的硬上限。

导入批量删除旧全文索引，按改动定义重算受影响关系，避免每个文件都重复扫全库；字段抽取结果直接复用。框架候选查找复用现有 symbol 索引。两个新增路径索引仅在主动导入／更新时准备，支持取消；普通提问不会创建它们，旧库无需重新导入即可使用查询修复。

界面分别显示定位程序、阅读源码、补充分析和模型生成。可分享诊断仅追加固定时间字段及预算枚举，继续排除问题、路径、源码、回答正文与接口配置值。

## 验证的规模和边界

本机合成库包含 12,024 文件（12,000 程序和 24 COPY 文件）、2,712,993 行、一个 25,000 行程序，数据库约 1.4 GiB。大部分程序约 224 行，包含真实声明、条件、计算、PERFORM、COPY 和环形 CALL。这个数据集验证万级目录、大索引和单个长程序；**它不是每个程序 25k 行的约 3 亿行全量测试**。

旧提交 `b0c9923` 的完整问答流程在“BILL-AMOUNT 怎么计算？有哪些触发条件？”上，90 秒内未发出第一条模型请求，采样确认卡在计算路径调查。模型传输由离线探针截获后立即停止，未访问真实接口，也未把假回答当作业务质量结果。

最终代码串行运行每题三次，以下均是到第一条请求准备好的本地时间，首次值包含新进程加载关系缓存：

| 问题场景 | 首次 | 同进程第二／第三次 | 实际供应 |
| --- | ---: | ---: | --- |
| 公共金额字段的计算与触发条件 | 9.206 秒 | 2.323／2.338 秒 | 7 文件，约 20.6k／25.1k 原文字符 |
| 明确 25,000 行程序的金额与条件 | 9.429 秒 | 3.353／4.838 秒 | 包含该长程序的 8 文件，约 22k 原文字符 |
| 截图原业务句，在合成库中零命中 | 1.426 秒 | 0.107／0.108 秒 | 0 源码，进入词项规划，尚未回答业务 |

长程序实际只供应本题相关原文，未把 25,000 行宣称为全部发送。首次磁盘读取仍明显慢于缓存命中；此结果支持消除无限调查和达到数秒级重复准备，不能保证每台现场电脑首次都在 3 秒内，更不能把规划请求当作完整答案。

独立验证 12,000 节点、60,000 关系的完整计算闭包约 0.013 秒。关系查询、调用者、共享 COPY 与历史绑定逐项对照原结果；新增 VM 工作量回归验证无关索引行增长不会放大局部查找。可选解析预算、真实取消、接口等待排除、裁剪撤销覆盖和草稿重新审查均有独立回归。

完整回归通过 1,720 项 Python 和 149 项页面测试，216 个 Python 文件通过 3.10 语法检查。实际执行环境为 macOS / Python 3.14；网页测试使用本机临时端口，模型传输使用假 transport。未进行 Windows 实机、Python 3.10 运行或真实接口验收。

导入对照在独立数据库副本更新相同 32 个文件：51.71 秒降到 15.73 秒，均含 profiler，修复后包含首次 3.76 秒的路径索引准备；单文件刷新 14.43 → 8.65 秒。25k 行单程序解析约快 9%。无改动刷新存在磁盘页缓存波动，未证明稳定加速；没有重测约 3 亿行源码的首次完整导入，不能承诺全量导入几秒完成。

实际模型的首字、完整答案时间和正确性尚未验收。截图原问题在此合成库中没有对应业务词，零命中测量只能验证规划请求不会卡住，不能证明已经回答真实账单业务。现场 HTTP 500 的服务端内部原因仍未知。

## 复现

生成业务密集合成源码并验证冷导入、无改动刷新、单文件变更及长程序尾部检索：

```sh
python poc/benchmark_intake.py --files 12000 --lines-per-file 224 --workload business --longest-program-lines 25000
```

该命令使用临时源码目录和索引，结束后自动清理；万级运行耗时和磁盘空间随机器变化。已有一次性基准目录可测默认问答到首条请求的实际本地开销：

```sh
python poc/benchmark_chat_latency.py --database /path/to/benchmark/structural-index.sqlite --source /path/to/benchmark/source --question 'BILL-AMOUNT 怎么计算？有哪些触发条件？' --repeat 3
```

第二个命令不调用模型，只输出时间和数量；正常问答路径仍可能刷新已变更的选中文件、建立本机语义缓存，因此使用基准目录。连续运行须串行，记录首次与重复值，避免把同时运行测试、其他导入和操作系统缓存抖动算作算法变化。

## 更新方式

停止旧服务，更新 `main`，重新启动；保留现有索引、源码、配置与对话。先用原截图问题复测，界面到“模型正在生成回答”时本地准备已结束。结果产生后，可复制诊断查看 `first_model_request_seconds`、`local_processing_seconds` 和 `provider_wait_seconds`，判断剩余延迟在本机还是接口。源码有新增或变更时再主动更新资料库；准备路径索引只需一次。
