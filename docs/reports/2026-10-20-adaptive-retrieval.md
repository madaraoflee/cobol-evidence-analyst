# 检索质量进化：让新线索真正进入证据链

这轮最值得改进的是证据召回与选择。当前系统并没有固定的业务主题词典，也不缺全文索引；实际问题是，问题分词、模型补搜和证据状态之间存在不一致，正确的新线索可能被截断，或者已找到原文却被误标为仅供导航，进而无法进入回答。

## 已核对的现状

`poc/repository_discovery.py` 使用通用标识符拆分、中文片段、SQLite FTS5/BM25 和 CALL/COPY 关系。索引内容来自导入源码；固定的是部分检索预算与调查策略，不是预置业务答案。`poc/semantic_scope.py` 的侧库是所选文件的结构分析缓存，并非向量语义检索库。`poc/concept_search.py` 提供源码或手册中的词语共现候选，共现本身不证明同义。

默认问答已经允许模型把中文问题转换为英文标识符、缩写，再执行真实搜索。源码中完全没有中文对应词、手册或其他跨语言联系时，纯本地词面检索不能自行推断中文业务词与英文缩写的含义。因此本轮先保证现有模型调查能够正确消费搜索结果，没有用更多业务关键词掩盖这个边界。

已复现的缺陷是：较长中文问题可占满 128 个检索词名额，追加英文搜索词被排除在统一匹配统计之外；另一段独立补搜却仍可能读到正确源码。此时 `matched_file_count=0`、`orientation_only=True` 与返回页面矛盾，默认问答会把页面当作导航材料而不采用。长搜索列表中的后续独立线索也有类似饥饿问题。

## 本轮改动范围

修复限制在检索词预算、候选排序及相应回归测试。保持现有索引格式、源码 hash/行号核验、显式文件范围、无命中导航标志、原文预算和调用关系扩展。不会新增模型调用，也不会将排序分数宣称为业务正确率。

检索词名额按输入来源轮转分配，追加搜索先取得一个名额，再与原问题共享剩余额度。发现文件、匹配计数、上下文检索与原文回退使用同一组保留词，避免出现“找到页面却统计为零”的矛盾。

每条补充线索先尝试完整标识符，再保留宽松词面召回；不同线索轮转取候选，防止第一条线索独占名额。完整标识符在原文词元中核对，并在候选上限之前过滤：SQLite 分词后相邻的普通单词不能冒充含连字符的字段名。大小写与句末点得到规范化，较长名称内的子串不会冒充完整名称。选择顺序仍只是阅读优先级，不是语义相关性证明。

本轮采用分层优先与轮转，不引入 RRF 分数、向量或重排模型。最多三个独立补搜通道，剩余建议合并为一个通道，加上原问题回退；每通道最多精确、宽松两路，共不超过十条候选查询，重复路由复用。每路返回不超过 `max_pages * 16` 个候选，最终仍受原页面与字符预算约束；这限制候选数量和查询次数，不等于限制 SQLite 内部扫描次数或保证固定耗时。

新增 11 项回归涵盖长中文问题、后续线索、完整字段名与普通词干扰、不同形态线索的公平性、显式范围、查询转义、取消、预算与真正无命中。默认问答的端到端测试使用确定性接口替身：第一轮提出英文线索，第二轮必须收到对应原文并能带引用回答，没有调用真实模型。

扩展验证覆盖问答、来源范围、缓存刷新、检索供证与相关性能回归：35 个模块、434 项测试通过，执行时禁用网络连接，前后检索模块哈希一致。随后重新运行最终修订的 11 项新回归，端到端案例仅用注释中的陌生词作为模型线索，避免已知字段的其他补救路径掩盖原缺陷。冻结旧模块的对照明确失败于第二轮 `source_supplied=False`，修复后通过；另外 8 项 Windows 工作流源码检查通过，两个工作流继续只接受手动触发。

`tools/evaluate_retrieval_routes.py` 实际调用生产检索与已有原文评测函数，对相同合成源码、问题和一页/12,000 字符预算做基线对照。基线只替换为起点提交的检索模块，其余模块保持相同；没有使用人为候选顺序。结果如下：

| 开发反例 | 原始返回 Recall@1：基线 → 修复 | 排除仅导航材料后的 Recall@1：基线 → 修复 | 说明 |
| --- | --- | --- | --- |
| 225 字中文问题后追加英文线索 | 1 → 1 | 0 → 1 | 原先已找到，但错误标成导航；本次修正计数与状态。 |
| 前一条冗长线索挤占后一条英文线索 | 0 → 1 | 0 → 1 | 按来源分配词名额，后续新线索得以保留。 |
| 短问题中的完整标识符与连续普通词竞争 | 0 → 1 | 0 → 1 | 不依赖长问题截断，单独检验完整标识符排序。 |

这里的相关证据是合成源码中预先指定的字面行段；“排除仅导航材料”也不等于最终回答已经使用了它。三题是开发反例，未经过独立业务人员复核，不代表真实业务准确率、跨语言理解能力或办公环境性能。精确数据、模块与样本指纹见[离线对照记录](2026-10-20-adaptive-retrieval.json)。

## 后续进化顺序

首先，把真实失败问题按“未召回、已召回但未装入、已供证却解释错”分开记录，继续复用现有 `retrieval_quality_eval.py`。其现有 CLI 使用人为编写的候选序列，不能当作真实检索效果；对照必须实际运行生产检索并核对原文行段。新的开发反例也不能冒充独立保留业务题。

然后，用已授权的真实模型与人工标注保留题验证跨语言搜索规划，并把术语候选绑定到版本、手册或源码来源。只有量化确认词面召回仍是主要缺口，再考虑可选 embedding 通道及重排；向量只能增加候选，不能证明调用、条件、字段回写或业务因果。模型接入和源码外传继续受既有授权范围约束。

解析覆盖方面延续已有前端适配与原生解析器影子对照，以 COPY/REPLACING、限定字段、控制流和方言为逐项验收单位。不要把“换了解析器”直接换算成完整 COBOL 语义能力。
