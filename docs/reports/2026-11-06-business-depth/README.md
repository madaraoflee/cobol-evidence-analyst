# 启动与复杂业务回答质量审查（2026-11-06）

本轮确认的问题不是简单的“模型变差”：源码定位、调用关系状态、答案审查和正文后处理都存在会降低业务回答质量的具体缺陷；启动路径还会在窗口可用前同步读取、校验大报告。修复方向是让已有源码真正进入分析、把未解析的关联与缺失源码分开，并要求答案解释业务作用和交接，而不是靠增加字数或逐句翻译代码充当详细分析。

审查起点为 `6967121e8d235950033db01e31ca6648e7bf18f7`，上一候选应用冻结于 `7fa6af655d0a8764d9335ad3d021044f351a26c7`，对应 `v2026.11.06.1-rc.1`。本轮沿 Python 的启动恢复、检索关系、调查清单、请求组装、回答复核和后处理路径逐函数检查，并补充离线复现；没有声称已逐行审完所有 Python 文件。

尚未取得用户现场的原问题、新旧回答、完整耗时日志及实际资料库规模。因此，下文能够证明这些缺陷存在、修复后的机制改变，不能证明某一个缺陷独自造成了现场的一小时等待，也不能据此保证所有真实业务问题都已达到预期质量。没有使用公司源码调用外部模型。

## 为什么已有源码仍会被说成找不到

### 关系预览的 64 条限制会挤掉当前程序的下游

[`repository_discovery._context_relations`](../../../poc/repository_discovery.py) 将上游调用方和当前文件的下游关系放进同一个有界列表，旧排序主要按路径排列。当 70 个路径靠前的上游程序都调用当前程序时，64 条预览可能全部被上游占据，当前程序真正调用的子程序反而不在返回列表中。这是关系选择问题，不能解释为“源码不存在”，也不代表系统只支持 64 个程序。

复现中，`z-main.cbl` 调用 `view.cbl`，后者再调用 `check.cbl`；70 个 `a-caller-*` 文件调用主程序。修复后优先保留当前所读文件的下游 CALL，再保留其他关系，仍明确标记有预览截断。测试同时检查普通源码读取和检索入口能看到 `view.cbl`，不靠无界扩大列表解决性能问题。

### 调用未绑定被错误归类为实现不可用

旧关系输出只要没有唯一 `target_path` 就标记 `unavailable`。但没有唯一目标至少有三种不同情况：索引里确实没有目标、存在多个同名实现、动态 CALL 的目标值尚未解析。把它们合并，会向模型传递“没有源码”的错误前提。

新增 [`dependency_sources.dependency_source_availability`](../../../poc/dependency_sources.py)，并统一用于关系返回和 [`question_investigation._dependencies`](../../../poc/question_investigation.py)：唯一索引目标、已索引的多个候选、动态目标未解析、索引内缺失分别表示。两个同名 `VIEWREAD` 实现会提供候选路径与位置，明确需要确定绑定；不会任选一个，也不会将两份实现拼成一个程序。动态 `CALL SERVICE-NAME` 不会把同名程序当作真实目标，更不会因目标尚未确定就宣告实现缺失。未知仍限制相关结论，不冒充已确认的运行链路。

候选输出有数量上限和截断标记，缓存返回独立副本，防止一次读取修改候选后污染下一次读取。框架约定也不能替代选择同名本地实现所需的绑定证据。

### 对“找不到”措辞的检查存在遗漏

[`source_availability`](../../../poc/source_availability.py) 原先识别“未提供、缺失、unavailable”等断言，却漏掉“找不到、未找到、cannot find、not found”。因此，即使实际模型请求已经包含同版本文件原文，错误缺失断言仍可能保留到最终答案。

本轮加入保守的定位失败检查：只在明确谈论物理源码文件、且该文件原文确实供应时认定矛盾；只有完整供应才能纠正“完整源码找不到”。缺少被调实现、文件内部某字段或业务规则没有定位、运行数据未给出，都不能被这一检查抹去。修复的是错误的源码可用性断言，不能将修正后的句子算作业务问题已经解释完整，更不能自动建立业务语义正确性。

以上回归见 [`test_dependency_source_availability.py`](../../../poc/tests/test_dependency_source_availability.py)、[`test_source_availability.py`](../../../poc/tests/test_source_availability.py) 和 [`test_source_availability_repairs.py`](../../../poc/tests/test_source_availability_repairs.py)。

### 动态调用已有字面量线索仍依赖模型主动搜索

后续审查又复现了更接近复杂框架的供证缺口：调用目标字段声明了 `VALUE 'CHECKROW'`，并以 `CALL SERVICE-NAME` 调用时，首轮只送调用方，已有的 `check.cbl` 没进入请求。模型直接结束会留下部分答案；只有它主动搜索 CHECKROW 时，第二轮才取得实现。见[修复前的实际请求记录](dynamic-source-before.json)。加入运行时 ACCEPT 改写后也不能把初值当成确定目标。

因此暂停了最初候选构建，在本轮补充有界的目标名称提名：从调用所属程序和目标字段的声明初值、调用前直接字面量赋值提名实际已索引的源码，先读原文，同时保持动态运行目标未绑定。首轮实际请求现在同时包含调用方与目标实现，加入 ACCEPT 改写时仍明确运行目标未解析；见[修复后请求记录](dynamic-source-after.json)。同程序字段、版本及源码原文都要核对，不把其他程序的同名字段、显示字符串或调用后的赋值混入。

重复动态 CALL 的候选来源改为共享目录，每个调用点保留位置和引用；否则一个约3KB的主程序就可能因重复元数据超过请求上限。40次动态调用、8个候选的回归要求9份原文全部保留、请求仍在默认字节预算内。相邻调用间没有目标字段赋值时复用已选赋值窗口，避免重复扫描，但仍可找到远处隔着1500条无关MOVE的目标名称。

这些都是阅读线索，不是完整的动态值分析。当前支持本程序唯一普通字段的字面量初值及调用所在行之前的直接字面量赋值；间接拼接、COPY中字段展开、限定/下标字段、同一物理行内顺序、外部输入和公司框架生成规则仍须另行核实，输出明确标记动态值集合并不完整。

## 为什么“详细回答”仍可能变成变量和状态码说明

### 业务问题的浅答审查没有一致执行

[`business_synthesis.assess_business_answer`](../../../poc/business_synthesis.py) 只在保存的自定义要求明确要求业务解释时，将纯赋值摘要列为待修订；直接提问“详细解释整体业务流程”没有得到相同处理。复现时，源码已经支持业务目的、程序职责和数据流，回答却只有“程序把 RESULT-CODE 设置为 0，然后返回调用方”，旧审查仍返回空的遗漏列表。

现在，直接业务概览问题和保存的业务解释要求使用同样的审查。实际 `run_business_chat` 回归先返回上述浅答，再检查系统发出一次有原文和具体遗漏项的修订请求，最终保留解释订单受理条件、处理职责和输入输出交接的正文。明确只问字段取值的窄问题仍可以直接回答取值；陌生业务措辞也不会仅因不匹配词表就被判错。这仍是识别已知明显遗漏的机制，不是通用语义评分器。

### Python 后处理会自行拼上技术附录

[`answer_fact_completion.complete_supplied_answer`](../../../poc/answer_fact_completion.py) 原本为了保留遗漏的源码事实，会直接向答案追加公式、调用、控制条件与字段声明。已复现：问题明确要求“详细解释 CALCULATE-AMOUNT 的整体业务流程，不要逐行翻译代码”，Python 仍在正文后追加五条技术说明，包括 `OUT-AMOUNT = ...`、累计赋值、`PERFORM WRITE-RESULT`、`IF RATE NOT = 0` 和 PIC/ROUNDED。即使模型正文符合要求，这条后处理也会把结果拉回代码说明。

修复后，业务概览将这些内容保留为带路径、版本、范围的复核候选，交给已有的模型修订轮解释其业务影响，不再自动追加固定技术段落。用户明确询问计算公式、累计或覆盖规则时，仍保留相应精确补全，避免修正表达方式时损失必要事实。

### 大请求压缩会弱化回答深度约束

[`business_chat._prompt_payload`](../../../poc/business_chat.py) 在请求超过预算、启用 `budget_wire_compact` 时，曾用统一的简化文字覆盖详细与简短回答合同。复杂链路更容易进入压缩路径，因此它恰好在材料较多时削弱了完整解释的要求。

现在普通和压缩路径都保留用户选择的详略。详细业务回答要求串起有据的 logical view、子程序、参数与数据交接，解释每一步对结果的作用、成立条件、异常和下游用途；简短要求仍被尊重。请求大小上限不变，不靠无限增加上下文解决问题。

上述三项修复的回归见 [`test_business_answer_depth.py`](../../../poc/tests/test_business_answer_depth.py) 和 [`test_business_explanation_delivery.py`](../../../poc/tests/test_business_explanation_delivery.py)。真正需要的“详细”是业务对象、进入/跳过条件、处理分工、数据来源、规则、例外和结果交付都能对应源码；MOVE、IF、状态码只有在说明这些业务效果时才有必要展开。

## 启动为什么可能长时间没有可用窗口

旧 [`WorkbenchState.__init__`](../../../poc/web_app.py) 在 HTTP 服务可用前同步恢复资料库。超过浏览器直接读取上限的大报告即使有显示用副本，也需校验完整原报告的 SHA-256；没有可用副本时还需解析完整 JSON。升级规划、显示恢复、升级前复核和升级工作线程可能重复校验同一份未改变的报告。这些磁盘与解析工作发生在用户看不到进度的时候，报告越大、存储越慢，越容易表现为“程序打不开”。这是一条确切的阻塞路径，但现场是否耗时一小时、各阶段占比多少，仍需现场记录。

修复将正式服务启动的资料库恢复放入后台任务，先让界面与进度接口可用，展示恢复、报告核验、对话恢复及索引加载阶段。恢复结果在私有候选状态中构建，核验完成后一次采用；未完成的资料库不会被标成可以提问。取消和失败保留原文件及可恢复入口，自动升级沿用原有备份、回滚和同一快照检查。

[`report_view.ReportReadSession`](../../../poc/report_view.py) 仅在同一次恢复/升级操作中复用完整报告校验，文件身份、大小、修改时间或变更时间变化即失效；Windows 额外读取文件变更时间，不把创建时间当成内容变更时间。跨重启仍需读取实际字节，不能为追求快而接受未核验的旧报告。对应入口在 [`workspace_upgrade`](../../../poc/workspace_upgrade.py)，后台恢复回归在 [`test_workspace_background_restore.py`](../../../poc/tests/test_workspace_background_restore.py)。

交叉审查还复现了后台方案的一个新回归：取消恢复后保存回答设置，会用空状态覆盖原资料库登记和会话指针。修复方案要求取消/失败后保留已经校验的轻量设置、资料库登记和原会话指针，同时不采用未核验的源码状态；无法读到保存配置时阻止用默认值覆盖。该路径也纳入“取消→改设置/接入另一库→重启”的回归，避免速度修复引入新的“失忆”。

相同的64MiB合成报告、明确模拟16MiB/s读取速度时，旧代码首次HTTP可用耗时12.206秒，修复后为0.005秒；恢复及升级来源核验从16.266秒降为4.083秒，完整报告校验从4次降为1次，重复扫描字节减少75%。首屏尚未核验时没有可提问的快照，完成后才采用有效快照。见[修复前记录](startup-before.json)、[修复后记录](startup-after.json)及[复现脚本](reproduce_startup.py)。计时从状态恢复构造开始，不含EXE载入、索引重建和模型请求，是受控慢盘模拟，不是公司Windows设备实测。首次导入、必要的旧索引升级、无显示副本的大报告转换仍有真实工作量，不能把首屏可用等同于资料库已经恢复完毕。

## 哪些判断没有被本轮证据支持

七层调用并不是原版本必然失败的深度。中性夹具包含入口、七个子程序、COPY、DDS logical file 与 physical file；检查实际模型请求时，原路径已能供应这 11 份原文以及第七层业务条件。本轮保留此项回归，是为了防止修复误伤已有能力，不能把它描述成“以前只能读一两层，现在才支持七层”。

这个样本的 logical file 由 DDS `PFILE` 定义提供线索；它不等于已经覆盖用户公司框架里的所有 logical view 协议。公司框架可能还依赖生成规则、操作码、目录约定、运行库选择或适用手册。正确方案是取得授权范围内的真实失败问题与对应源码/框架证据，冻结各层期望业务结论后验证；不能仅凭名称猜测读取、保存、锁定或提交成功。

桌面使用的 [`model_profiles.py`](../../../poc/model_profiles.py) 默认单次输出额度是 **8192 tokens**，不是底层 `company_api.py` 通用配置的 1024。显式环境或本地配置可以覆盖默认。本轮没有凭空提高模型限额。长度中断已有续写机制，但模型以 `stop` 正常结束的浅答不会仅因短而续写，所以仍需上述内容审查。上下文、语义分析文件数及回答续写都有边界；不能承诺无限链路、无限记忆或无限正文。

## 验证与发布计划

回答质量相关的 139 项针对性测试已通过，覆盖实际请求、字节预算、原文绑定、保存偏好、精确计算补全以及已知浅答修订。测试使用固定合成回复，只证明检索、传输、审查与保存行为，不能当成真实模型质量提升的评分。

包含动态调用补充修复的最终完整回归 **4,703 项 Python、286 项网页及1项工具测试全部通过**，无失败、无跳过。四组发现清单和测试源码哈希一致，执行ID并集恰好覆盖所有发现测试；见[源码回归记录](source-regressions.json)。异步恢复使旧升级测试需要等到恢复完成后再检查历史，已更新等待条件且保留全部原配置、历史和索引断言。最终 Windows EXE 验证和冻结提交待补。最终包补充检查已纳入直接业务提问的浅答修订、正文不被自动追加技术附录、七层调用/COPY/LF/PF 原文供应、错误“找不到源码”断言修正及请求记录一致性；这些检查必须在最终 EXE 上运行，不能以源码测试替代。
