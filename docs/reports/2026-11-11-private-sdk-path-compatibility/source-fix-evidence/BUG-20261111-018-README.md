The new explicit `--materialize-python3-alias` flag permits only the SDK's exact top-level `python3.exe` with that SYMLINK tag, whose target spelling is the SDK's own `python.exe`. The target must be ordinary and samefile. Outside targets are rejected before their contents are read, even if an outside hard link has the same file identity. Nested links, other names, junction tags, UNC/device targets and arbitrary aliases still fail.

The source manifest retains the original alias's raw target, complete core file identity, tag/attributes, verified target identity and target hash. The source manifest is checked again after the probe. A changed target or identity makes the preparation fail.

It omits that one link during copying, verifies the already copied ordinary `python.exe`, and explicitly copies those verified private bytes into an ordinary `python3.exe`. The final private logical manifest has exactly the complete source entry set; only this alias entry becomes its verified target hash and the SQLite DLL entry becomes the official replacement hash. No source alias or source content is removed or changed.

The workflow bootstrap enables the flag only when `source_base` was not explicitly supplied, its SDK base/current executable are ordinary, and the running executable is samefile with that SDK's `python.exe`. The selected SDK and alias binding are recorded and must still match before activating Actions environment files. Explicit source inputs retain the old strict policy. Official DLL pin/probe, private base fingerprint and final same-package native gates are unchanged.
