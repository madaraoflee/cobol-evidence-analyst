# 普通本地问答如何沿源码查完扣费题

原题是“保费收取时 reserve 和 refund 的扣减顺序及适用条件是什么？”。固定旧版 `839d085166fbef89a882c917ea73c21f7eda380b` 和修改后的普通本地工作台分别导入相同的临时源码并发送原题。入口程序从变量调用下一个程序，下一个程序也从变量调用最终扣费程序。另有九个小程序只显示 reserve、refund 字样。第一轮给模型的原件包含入口程序，两份下游实现均须另外寻找。[中性测试源码与受控回答](../../../poc/tests/local_grep_acceptance.py)

旧版四组均只读到入口程序和关键词提示文件，第四组始终未满足“已查齐三份程序才注入错误”的条件。旧版在模型回复“源码不足以分析。”后又请求了两次，三次均未定位到后续程序，最终保存为部分回答。换成模型主动索取入口程序中查到的目标，也重复请求了三次，最后把检索指令本身显示在答复里。[旧版逐轮记录](before.json) · [旧版四项失败的回归输出](before-tests.txt)

## 同题如何核对

每轮模型回复都经普通问答的传输接口返回。受控模型只能依照该轮收到的源码页提取目标名称。测试逐页将路径、起止行、字节摘要和物理原文与临时目录核对，另从已保存的消息重新打开每份引用。文中的引用和工作台附带的已读文件清单分别记录。检索命中本身只提供文件和行号，最终扣费规则必须从实际收到的原文读出。

固定旧版与修改版统一使用有效的中性余额字段 `REMAINING-DUE`，避免把 COBOL 保留字当作变量。完整样例共有 12 份源码。第一次等候模型时，工作台已显示第 5 行的准备金扣减条件，引用指向 `start.cbl`。第 8–9 行将 `ADJ731` 赋给待调程序变量，再传入当前应收。检索其定义命中 `legacy/route.cbl` 第 2 行。读到这个程序的第 4–5 行后才能获得第二个目标 `CUT526`。继续检索其定义命中 `archive/settlement.cbl` 第 2 行，真正决定退款是否扣除的是第 4–5 行。负向对照移除最后一个文件，保留主程序、中转程序和九份含关键词的源码。

若按源码赋予的两个目标正常调用并返回，业务结果如下。项目类型为 `1-RESERVECREDIT` 时，先从应收扣掉准备金，其他类型跳过这一步。接着独立检查当前应收，只有大于零才进入退款处理。退款余额严格小于当前应收时才扣，等于或大于时保留原额。最终返回的应收等于进入时的金额减去实际扣掉的两笔款项。应收 100、准备金 20 时，退款 30 得 50，退款恰好 80 则仍应收 80。

## 重放

从项目根目录分别运行固定旧版、当前源码和四项工作台回归。

```sh
python3 -B docs/reports/2026-11-21-local-source-grep/replay.py --baseline
python3 -B docs/reports/2026-11-21-local-source-grep/replay.py
python3 -B -m unittest discover -s poc/tests -p test_local_grep_delivery.py -v
```

旧版四项回归失败的输出可用同一重放脚本加 `--baseline-tests` 再现。测试使用内存中的受控模型并拦截网络连接。第四组模拟模型在确实读到三份原件后仍给出错误的扣款字段和算例。它覆盖普通工作台从提问、搜索、读取进度、保存答复到打开引用的流程。样例为中性源码片段；公司实际运行时的动态绑定、真实应收和记账、现场模型的回答质量及等待时间、目标设备和最终 Windows 程序仍待现场核实。
