# 问题分类与调查策略矩阵

> 核心判断：Agent 不能收到问题后自由搜索整个图。它必须先把问题拆成有限的原子类型，为每个子问题建立证据义务，再按关系白名单调查；是否回答由证据义务决定，不由模型“感觉已经够了”决定。

状态：`Target architecture proposal — deferred behind POC`
当前轻量实现见：[可演示 POC](./09-demonstrable-poc.md)  
日期：2026-08-28  
范围：只读 COBOL 业务分析 MVP

## 1. 第一版只支持五种原子问题

现实问题可以是复合问题，但每个子问题必须归入以下一种类型。系统保存一个 `primary_type` 和零到多个 `sub_questions`，不创建含义模糊的 `COMPOSITE` 类型。

| 类型代码 | 用户真正要证明什么 | 标准回答形态 |
| --- | --- | --- |
| `CALCULATION_EXPLANATION` | 一个结果如何由输入、运算、条件、查表和舍入得到 | 公式/步骤、分支、输入来源、最终写入点 |
| `DATA_PROVENANCE` | 一个字段在哪里定义，或它的运行时值从哪里来、经过哪些赋值和参数 | 定义 lineage、值 lineage，或两者分别展示 |
| `CONDITION_IMPACT` | 哪些条件使结果、状态或路径发生变化 | 条件—结果表、默认/异常分支、适用范围 |
| `EXECUTION_PATH` | 从哪个入口通过哪些调用或 Paragraph 到达目标 | 有序执行路径、候选动态边、循环与替代路径 |
| `ANSWERABILITY_BOUNDARY` | 当前源码能够证明什么、不能证明什么及缺少什么 | 已知事实、证据边界、待确认项和所需额外资料 |

`ANSWERABILITY_BOUNDARY` 既可以是用户主动询问时的主类型，也是所有其他类型的横切输出：任何未满足的证据义务都必须进入答案边界，不能被省略。

“代码库有哪些业务域”“改动会影响哪些系统”“自动生成 FS/TS”不是第六种 MVP 问题，分别属于 M7/M8。系统应明确路由到未来能力，而不是用相似代码拼出一个看似完整的答案。

## 2. Question Plan 契约

Question Planner 只生成调查计划，不生成代码事实。计划至少包含：

| 字段 | 语义 | 约束 |
| --- | --- | --- |
| `question_id` | 本次用户问题的稳定标识 | 全链路一致 |
| `primary_type` | 最主要的原子问题类型 | 必须属于上述五类 |
| `sub_questions` | 为完成主问题而拆出的原子子问题 | 每项有独立证据义务 |
| `type_parameters` | 问题类型特有的限定，例如 provenance 是 definition、value 或 both | 不得用默认值掩盖关键歧义 |
| `target_concepts` | 用户提到的业务概念、行为、金额或状态 | 不是代码实体 |
| `explicit_symbols` | 看起来像 Program、Paragraph、Field、Table 的原始字符串 | 必须保留原文并经工具验证 |
| `scope_constraints` | 产品、程序、日期语义、入口或业务场景范围 | 未提供时不得自行编造 |
| `query_variants` | 原始问法、词汇规范化和受控业务别名 | 默认最多三个，具体值由评测校准 |
| `proof_obligations` | 回答前必须满足的证明要求 | 每项有状态和证据引用 |
| `relation_policy` | 本题允许扩展的关系类型与方向 | 默认拒绝未列出的关系 |
| `answer_contract` | 最终答案必须包含的段落或表格 | 由问题类型决定 |
| `clarification_required` | 是否必须由用户选择解释或范围 | 只有不同解释会实质改变答案时为真 |

如果一句话包含多个目标，例如“这个保费怎样计算，费率又从哪里来”，应拆成 `CALCULATION_EXPLANATION` 和 `DATA_PROVENANCE` 两个子问题，共享同一目标实体和快照。

## 3. 精确符号与混合检索的顺序

### 3.1 显式符号先验证

用户给出的字符串若形似源码标识符，先在当前快照中执行精确查询。COBOL 的“精确”按方言规则做大小写无关的规范化匹配，同时保留原始拼写；字段还必须考虑 Program、数据层级以及 `OF/IN` 限定，Paragraph 必须带 Program 作用域。

- 唯一命中：建立锚定调查种子，保留原始符号、实体类型和 `entity_id`；
- 多个命中：按 Program、COPYBOOK、实体类型和调用上下文缩小；仍会导向不同答案时请求澄清；
- 零命中：标记为 `unvalidated_symbol`，作为词汇查询使用，但绝不能在回答中当作真实实体。

锚定种子不进入普通相关性竞争。Qdrant 的 RRF 只融合稀疏与稠密候选，Reranker 只重排这些非锚定候选；应用层随后合并锚定种子和重排候选，锚定种子优先但仍需通过关系调查证明与问题有关。

### 3.2 COBOL 词汇规范化

词汇通道同时保存“原始 token”和“规范化 token”，处理顺序为：

1. 保留原始大小写、连字符和完整标识符，供精确检索和证据展示；
2. 按 COBOL 连字符、数字边界、已知前后缀和复合词切分；
3. 移除 COBOL 关键字、通用程序词和代码库内高频低 IDF 噪声词；
4. 使用公司内确认字典和代码库上下文扩展缩写，同时保留 `original → expansion → basis`；
5. 把业务专家确认的术语映射作为独立召回信号，不改写原始源码名称。

Samurai-style 递归切词可用于没有连字符的复合标识符，但不是 COBOL 默认规则。企业缩写高度领域化，`PRM`、`POL`、`CVG` 等不能仅凭通用字典自动解释；没有字典或上下文证据时应保留原词。

### 3.3 语义表示

稠密向量默认来自确定性代码文本渲染：实体完整路径、标识符及其受控展开、注释、相关语句、SQL/文件引用和实体类型。第一基线不把 LLM 自动生成的业务摘要写入检索文本，因为摘要错误会被索引长期放大。

## 4. 问题—证据策略矩阵

下表中的关系名是统一 IR 的需求输入，最终字段和方向将在下一阶段的 IR Schema 中固化。

| 问题类型 | 必须满足的证据义务 | 首选定位 | 关系白名单 | 停止或拒答条件 |
| --- | --- | --- | --- | --- |
| `CALCULATION_EXPLANATION` | 确认目标结果；找到当前路径上的最终写入；恢复运算顺序；追踪每个输入；列出控制分支、查表、舍入和覆盖写入 | 目标 Field/Paragraph 锚定；否则业务词 + 金额/计算相关词混合召回 | `WRITES`、`READS`、`FLOWS_TO`、`PASSES_AS`、`CONTROL_DEPENDS_ON`、`CALLS`、`PERFORMS`、`LOOKS_UP`、`SELECTS_FROM` | 公式存在未解析操作数、最终写入不唯一、舍入/比例规则缺失时只能给部分答案 |
| `DATA_PROVENANCE` | 先区分 definition、value 或 both；定义来源追到声明、COPY 展开和 REDEFINES；值来源找到所有相关 reaching definitions，并跨别名和参数追到输入参数、SQL、文件、控制表或外部调用边界 | Field 锚定；字段别名和注释做混合召回 | 定义使用 `DEFINES`、`EXPANDS_COPY`、`REDEFINES`；值使用反向 `WRITES`、`FLOWS_TO`、`PASSES_AS`、`SELECTS_FROM`、`READS_FILE`、`LOOKS_UP` | COPYBOOK 只能终止定义 lineage，不能作为值来源；值在动态调用、外部程序或运行时配置处中断时必须展示边界和候选 |
| `CONDITION_IMPACT` | 确认目标动作/写入；提取支配它的条件；解析条件字段来源；覆盖 ELSE、88 级、默认和异常分支；说明条件与结果的方向 | 结果写入点或状态变更锚定；否则条件词与结果词联合召回 | `CONTROL_DEPENDS_ON`、`BRANCHES_TO`、`READS`、`WRITES`、`FLOWS_TO`、`PERFORMS`、`CALLS` | 只有文本邻近、无法证明控制依赖，或条件值来自未知运行时配置时不得声称“必然影响” |
| `EXECUTION_PATH` | 验证入口和目标；给出有序跨程序/Paragraph 路径；标明动态边条件；识别循环；区分已证明路径和候选替代路径 | Program/Paragraph 锚定优先；缺少一端时混合定位 | `CALLS`、`POSSIBLY_CALLS`、`PERFORMS`、`PERFORMS_THRU`、`GOES_TO`、`BRANCHES_TO`、必要的 CFG 边 | 任一跨程序边无法解析时，路径在该边停止并标成候选；不得把可达性近似写成必然执行 |
| `ANSWERABILITY_BOUNDARY` | 明确用户想确认的事实类型；列出源码已经证明的部分；定位缺失证据属于运行时值、外部系统、业务原因、文档还是未解析代码 | 先运行最接近的前四类调查，再检查边界类型 | `POSSIBLY_CALLS`、`UNRESOLVED_REFERENCE`、`EXTERNAL_DEPENDENCY`、证据覆盖记录 | 缺少的内容不在当前快照或静态分析能力内时拒答；同时说明需要什么资料才能继续 |

关系白名单是默认上限，不是每次都全部使用。问题是“字段来源”时，不应因为某文件词汇相近就扩展词汇图作为事实路径；问题是“执行路径”时，也不应把共变更关系当成调用关系。

## 5. 各类型的标准答案契约

### 5.1 计算解释

必须依次给出目标结果、主公式或步骤、分支差异、输入来源、舍入/比例、执行位置和未解析边界。若存在多个互斥路径，不能合并成一条不存在于源码中的“平均公式”。

### 5.2 数据来源

必须先分别回答“在哪里定义”和“值从哪里来”。值来源使用有序 lineage：

```text
边界来源 → 中间字段/参数 → 跨程序传递 → 目标字段
```

每一步都带关系状态。多个 reaching definitions 按条件分开，不任意选择最后搜索到的一条。

### 5.3 条件影响

必须使用“条件—结果—证据—适用范围”的结构，并覆盖默认和异常路径。源码只证明技术条件时，可以解释其可能业务含义，但必须标为业务推断。

### 5.4 执行路径

必须展示入口、按序节点、边类型、动态边条件、循环压缩和目标。遇到递归或调用环时以 SCC/循环段表示，禁止无界展开。

### 5.5 可回答边界

必须区分：

- 源码能够证明的系统行为；
- 静态分析暂时无法解析的代码关系；
- 需要运行时数据才能确定的实际值；
- 需要业务人员或受限文档才能解释的业务原因。

拒答不是空白结果；它必须带已经调查的范围、停止位置和继续所需资料。

## 6. 证据义务状态机

每个证据义务至少包含：

| 字段 | 说明 |
| --- | --- |
| `obligation_id` | 在本次调查内稳定的标识 |
| `kind` | target、write、input、condition、path、boundary 等义务类型 |
| `target_entity_id` | 已验证目标；未知时为空，不能编造 |
| `required_relations` | 允许用于满足该义务的关系集合 |
| `coverage_policy` | one、all、one_per_branch 或 until_boundary |
| `status` | `OPEN`、`SATISFIED`、`PARTIAL`、`UNRESOLVED`、`NOT_APPLICABLE` |
| `evidence_ids` | 满足或部分满足义务的证据 |
| `unresolved_reason` | 未满足原因和下一步可能动作 |

调查循环必须满足“单调进展”：每次工具调用至少关闭一个义务、缩小候选集合或明确一个不可跨越边界。若连续调用没有进展，即使预算尚未耗尽也应停止，避免 Agent 反复搜索相同内容。

## 7. Agent 状态与决策

| 状态 | 必须产出 | 允许的下一步 |
| --- | --- | --- |
| `UNDERSTAND` | 原子问题、目标概念、显式符号、初始证据义务 | `CLARIFY` 或 `LOCATE` |
| `CLARIFY` | 会实质改变答案的最小澄清问题 | `UNDERSTAND` |
| `LOCATE` | 锚定种子、融合候选、命中来源和排名 | `SELECT_RELATIONS` 或 `ABSTAIN` |
| `SELECT_RELATIONS` | 当前未满足义务对应的关系白名单和方向 | `EXPAND_EVIDENCE` |
| `EXPAND_EVIDENCE` | 新关系路径、源码锚点、候选或未解析边界 | `CHECK_SUFFICIENCY` |
| `CHECK_SUFFICIENCY` | 每个义务的新状态和剩余预算 | `EXPAND_EVIDENCE`、`COMPOSE`、`CLARIFY` 或 `ABSTAIN` |
| `COMPOSE` | 只引用证据包的结构化 claims | `VERIFY_EVIDENCE` |
| `VERIFY_EVIDENCE` | 快照、哈希、实体、关系和引用完整性结果 | `VERIFY_CLAIMS`、`EXPAND_EVIDENCE` 或 `ABSTAIN` |
| `VERIFY_CLAIMS` | supported、overstated、unsupported 及补查义务 | `ANSWER`、`EXPAND_EVIDENCE` 或 `ABSTAIN` |

预算至少包含工具调用数、关系深度、展开节点数、经过时间和证据 token。具体默认值属于评测配置，不属于业务规则。

## 8. 澄清与拒答的边界

只有用户能够用一个选择解决、且不同选择会改变调查结果时才澄清，例如同名字段分别存在于新单和续保程序。若两个解释都能在预算内调查，应并行保留假设并展示差异，不要增加无必要对话。

以下情况直接进入部分回答或拒答，而不是向用户索要猜测：

- 问题要求“为什么采用此业务规则”，但源码只证明规则如何执行；
- 问题要求生产环境当前值，但系统只有静态源码而没有运行时配置；
- 路径经过未提供的外部程序、生成代码或受限文档；
- 动态调用只有多个候选且源码不能唯一确定；
- 索引快照不完整、Qdrant 与 Neo4j 实体版本不一致或源码哈希失效。

## 9. 评测要求

问题规划单独评测，不与最终回答混在一起：

| 指标 | 要验证的能力 |
| --- | --- |
| 原子类型 Macro-F1 | 五类问题是否被正确区分 |
| 复合问题分解覆盖 | 每个必要子问题是否都进入计划 |
| 精确符号验证错误数 | 未存在或多义符号是否被错误锚定；硬目标为 0 |
| 证据义务覆盖 | 金标准要求是否全部进入计划 |
| 关系白名单违规数 | 是否使用了不允许的关系证明事实；硬目标为 0 |
| 澄清准确性 | 是否只在真正需要用户选择时提问 |
| 拒答精确率/召回率 | 能否拒绝源码不可证明的问题，同时不过度拒答 |

第一批金标准问题应同时标注正确类型、必要子问题、锚定符号、证据义务、允许关系、应当澄清的歧义和必须拒绝的说法。没有这些标注，就无法判断 Agent 是“调查正确”还是“碰巧说对”。

## 10. 对下一阶段的输入

统一 IR 不是从 COBOL 语法全集开始设计，而是从本矩阵反推：

- 每个证据义务需要哪些实体；
- 每类调查需要哪些关系及方向；
- 哪些关系必须区分 confirmed、candidate 和 unresolved；
- 哪些源码位置、哈希和派生信息必须随事实保存；
- 哪些循环、别名、动态调用和外部边界必须成为一等对象。

本矩阵已经据此形成 [统一 IR 与关系 Schema](./07-unified-ir-and-relations.md) 和 [Agent 调查工具契约](./08-agent-tool-contracts.md)。这些属于完整目标架构；当前 POC 只实现四类核心调查动作和轻量源码引用，见 [可演示 POC](./09-demonstrable-poc.md)。
