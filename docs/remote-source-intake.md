# 从 Bitbucket 接入源码

Bitbucket Cloud 与 Server / Data Center 都可从左侧栏“从 Bitbucket 接入”进入。首次获取把指定提交的源码保存为独立本机快照，之后重启或打开已保存资料库直接复用源码和索引，不会再次下载。需要获取一周后的更新时，再主动选择“检查 Bitbucket 更新”：先比较提交，提交没有变化、本机源码完整且本地索引可用时，不下载源码，也不重建索引。Cloud 提交改变时，通过两个固定提交的变更清单只下载新增或修改的文件，并从已核对的本机副本复制未变文件；不会每周重新下载整仓 ZIP。首次仍需要获取源码，当前 Cloud 首次接入使用一次整仓 ZIP，不能宣称首次零下载或一定更快。

本地目录入口继续使用。远程下载和索引全部成功后才切换到新快照；下载、解压、索引失败或用户取消时保留原资料库和对话。两种来源共用问答、结果展示、引用、对话记录及导出，回答详略、阅读范围、回答要求与可选编译／框架设置也沿用相同逻辑。

## 使用方法

1. 选择“从 Bitbucket 接入”（窄屏先展开左侧导航），粘贴仓库页、目录页或 HTTPS clone 链接。Cloud 示例：`https://bitbucket.org/sample-workspace/business-source/src/main/stage/`；Server / Data Center 示例：`https://code.example.invalid/projects/DEMO/repos/business-source/browse/stage?at=refs%2Fheads%2Fmain`。
2. 分支／标签／提交和仓库内目录可以留空，沿用链接中的设置；链接也没有版本时，使用仓库默认分支。显式填写的非空值优先于链接中的设置。目录填写 `stage` 这类仓库相对路径；需要多个源码子目录及共同 COPYBOOK 时选择共同父目录。
3. Cloud 的 API token 搭配 Atlassian 账号邮箱填写，并至少授予 `read:repository:bitbucket` 权限，工作台使用 HTTP Basic 认证。仓库／项目／工作区 access token 与 API token 是不同类型：使用 access token 时邮箱留空，按 Bearer 发送；Server / Data Center 的只读 HTTP access token 同样留空邮箱。邮箱和令牌只用于本次接入或检查更新，不写入配置、资料库或日志，表单提交或关闭后清空。私有仓库下次主动检查更新需重新填写；打开已有本机副本不需要凭据。公开仓库可留空，浏览器登录或 SSO 状态不会自动提供 API 授权。
4. 核对编码、固定／自由格式；需要时在“进阶读取选项”填写框架资料、编译／COPY 设置和扩展名，再提交。第一次会显示解析版本、下载、解压及索引进度，Cloud 后续更新显示增量同步进度；相同来源已有副本时直接打开，显式更改读取设置时使用该本机源码重新索引，不重新下载。接入和更新本身不调用模型。

Cloud 也接受仓库根地址、`https://bitbucket.org/sample-workspace/business-source.git` 和带完整提交哈希的 `/src/<commit>/...` 链接。Server / Data Center 支持部署前缀，例如 `https://code.example.invalid/code/projects/DEMO/repos/business-source/browse/stage`，以及 `https://code.example.invalid/scm/DEMO/business-source.git`。链接不能包含账号、密码或令牌。SSH clone、浏览器 SSO 登录、OAuth 登录流程和定时自动同步尚未实现。

带完整提交哈希的链接代表固定版本，检查更新不会擅自改成其他分支。希望跟随仓库日后的更新时，明确勾选“跟随仓库默认分支”，或填入需要跟随的分支名。勾选后本次接入及以后主动检查更新使用默认分支，忽略原链接和版本栏的固定值；它不代表启动时自动联网。Cloud 默认分支先从仓库信息读取，再检查该分支的提交，不会将其他分支的最新提交误作当前版本。

## 接入结果与失败重试

进度页出现不代表导入完成。任务结束后，页面顶部会保留本次结果，明确区分接入完成、复用本地副本、未完成和已取消；发生错误时自动定位到结果，不把错误埋在旧业务对话底部。首次成功后可在源码资料库查看本机路径、文件数量与提交版本。

只填链接适用于公开仓库。私有 Cloud 仓库需要应用自己的授权；浏览器里已登录或可以浏览目录，并不会把登录状态交给工作台。可使用账号邮箱和具备仓库读取权限的 API token，见 Atlassian 的[官方 API token 使用说明](https://support.atlassian.com/bitbucket-cloud/docs/using-api-tokens/)。401／403 通常需核对授权，404 也可能隐藏无权限的仓库；不要仅凭进度消失推断导入成功。

同一页面内可从结果卡重新检查原接入设置，凭据需重新填写。刷新后仍会显示上次失败或取消；由于原表单操作上下文不保留，应重新选择“从 Bitbucket 接入”或当前资料库的“检查并更新”，系统不会猜测操作并把打开缓存当作更新重试。若请求或进度连接中断而结果无法确认，会明确显示未确认，不自动重新提交下载；刷新可重新查看后台状态。成功打开本地副本后，不再恢复已经过时的导入失败。

## 快照和原资料如何保存

首次接入或远端提交改变时创建新的源码目录及结果目录，不覆盖以前的本地目录或远程快照。默认保存在应用数据目录下的 `remote-sources/<随机编号>/source` 和同级 `analysis`；源码运行通常位于 `.poc-data/remote-sources/`，配置了 `WORKBENCH_DATA_DIR` 时使用该目录。索引、对话与不含凭据的来源信息随本机数据保管，不提交到公开仓库。

源码资料页的“已保存的源码资料库”可离线打开登记过的本机副本；状态接口的 `source_workspaces` 提供这些条目，打开操作使用 `/api/source/open`，不访问远端。重启恢复上次资料库。重新提交相同仓库、版本选择和目录的链接也会复用已有副本；仅当读取设置改变或缓存索引缺失、损坏、需要升级时，从现存源码重新建立索引。源码目录本身已丢失时无法凭索引还原源文件，需要恢复本机目录或重新获取。

“检查 Bitbucket 更新”使用 `/api/source/remote/update`。Cloud 与 Server / Data Center 提交不变时均先核对本机文件清单及实际字节；完整副本零源码下载，本地索引需要修复时从缓存文件重建。发现缺失、被修改或无法读取的文件时，Cloud 仅重新获取对应文件，Server / Data Center 重新获取归档；均建立新快照，原目录和历史不覆盖，不会把“提交未变”误报为“本机副本完整”。这项完整性检查只在主动更新时执行，日常重启和打开已保存资料库不增加全库散列扫描或联网。提交改变时，先将分支解析为完整提交编号，再按该编号读取变更和文件，防止检查与下载之间分支移动。Cloud 使用 `diffstat/<新提交>..<旧提交>?topic=false` 并完整读取分页；重命名、删除以及文件进入或离开所选目录都按新版本处理，只对新增、改变或本机副本校验不一致的文件请求内容。未变文件按下载时记录的 SHA-256 核对后复制到新快照，不使用可互相影响的硬链接。仅其他目录改变时，不下载所选目录源码。新提交仍须从新快照建立本地索引，现阶段没有承诺索引本身按文件增量更新。新提交形成另一份资料库，旧对话、引用和源码快照仍属于旧版本；不会自动把旧回答或引用改挂到新源码，也不自动删除旧快照。

新下载的 Cloud 与 Server / Data Center 快照在源码目录旁保存 `source.remote-manifest.json`，记录固定提交、文件路径、大小与 SHA-256，不含账号或令牌。Cloud 旧版本没有此清单时，首次增量更新只枚举旧提交的目录元数据，再使用原资料库最早记录的文件散列核验已有文件；没有可核对记录的文件单独获取，后续使用新清单。Server / Data Center 旧副本先用现有索引散列核对；无法证明副本完整时重新获取归档并保存完整清单。Cloud 增量更新遇到缺页、来源不符、认证失败或429限流会停止本次更新并保留原库，不静默回退到整仓下载，也不自动重试。

先前本地路径和读取设置仍保留在本地接入表单。右侧“最近对话”按“本地源码”和“Bitbucket”分组，并显示所属目录或仓库；点击历史对话会恢复它自己的源码资料库、索引和框架资料。不同资料库的对话不会混用当前源码，删除另一资料库的对话也不会切换当前分析对象。原源码暂时不可用时仍可查看已保存历史，但需要恢复源码与有效索引后才能继续分析。

对话标题从第一个有实质内容的问题提炼主题，保留程序名、字段名与关键条件，去掉请求套话和输出格式要求，例如“REQUEST01 的金额检查流程”。简单的“继续”“为什么”等追问不会覆盖原主题。旧的自动截断标题在读取时显示为摘要标题，原消息、时间和自定义标题保持不变；生成标题不增加模型调用。

最近对话只读取工作台已登记的资料库，不扫描其他磁盘目录；最多保留 100 个资料库登记，合并展示最近 200 段对话，超出显示范围不会删除磁盘数据。旧版本保留的当前资料库与可验证的本地路径会自动纳入；其他旧资料库可通过“切换源码目录”重新接入原源码和原结果目录。下载失败会清理本次未完成的缓存；异常退出或清理时磁盘故障可能留下未采用的目录，应先确认它不是正在使用的快照再处理。

## 连接和容量边界

运行工作台的电脑需要能够访问仓库，必要时先连接企业网络或 VPN。HTTP 401／403 表示令牌或读取权限问题，404 也可能由权限隐藏造成。服务器跳转到登录页时，使用最终 HTTPS 仓库地址和有效令牌；工作台不跟随重定向。企业证书需被 Python 的 HTTPS 信任配置接受，程序不会关闭证书校验。

当前限制为压缩下载最多 512 MiB、解压文件总量最多 2 GiB、归档条目最多 100,000，ZIP 中央目录元数据最多 32 MiB。网络读操作超时为 30 秒，获取和解压还受 15 分钟总预算约束；阻塞读取可能到单次超时才响应取消。

Server / Data Center 使用服务端目录归档；Cloud 官方 ZIP 接口返回整个仓库，工作台只将选定子目录提取到本机资料库。这不是 Git 增量拉取：Cloud 首次下载仍是整个 ZIP，选择较小目录不会减少首次 ZIP 的传输大小。Cloud 后续新提交使用上述文件级增量，不再请求整仓 ZIP；每个变化文件有元数据与内容请求，变化文件特别多时仍可能触发服务端限流。Server / Data Center 暂仍按所选目录重新获取归档。未选目录中的 Linux 专用名字不会成为本机文件，也不会因 Windows 保留名而阻断选定目录；选定路径仍须可安全写入 Windows，所有归档路径仍拒绝绝对路径、上级跳转、反斜杠及异常根目录。超过整包容量时，可改用获准的本机工作副本接入；Server / Data Center 还可缩小服务端归档目录。范围以外的 COPYBOOK 不进入资料库，应选择共同父目录覆盖分析依赖。Git LFS 实体和子模块内容不会另外拉取。Cloud 文件增量不跟随 LFS 重定向，并拒绝把符号链接或子模块当普通源码；这些情况会留下明确失败并保留旧库。

实现依据官方 [Cloud 仓库信息 API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-repositories/)、[Cloud 提交 API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-commits/)、[Cloud ZIP 下载说明](https://support.atlassian.com/bitbucket-cloud/kb/how-to-download-repositories-using-the-api/)、[Cloud 文件内容 API](https://developer.atlassian.com/cloud/bitbucket/rest/api-group-source/)及 [Cloud 认证说明](https://developer.atlassian.com/cloud/bitbucket/rest/intro/)。Server / Data Center 沿用 [Server REST API](https://docs.atlassian.com/bitbucket-server/rest/7.17.0/bitbucket-rest.html) 的 commits 与 archive 接口和 [HTTP access tokens](https://confluence.atlassian.com/bitbucketserver086/http-access-tokens-1188782454.html) 认证方式。

## 验证范围

新增实际本机HTTP模拟仓库回归覆盖增量分页、删除／重命名／跨目录、旧清单迁移、损坏和符号链接副本、下载完整性、限流、取消、来源绑定以及旧快照不受新文件编辑影响。12,202文件的快照修改一个文件后，更新仅发出一次变更清单、一次文件元数据和一次文件内容请求，复用12,201个本机文件；没有请求ZIP。这里验证的是HTTP传输与文件快照机制，不是实际企业网络耗时，也没有证明新版本索引构建已增量化。

自动回归使用中性合成源码和模拟仓库响应，覆盖 Cloud／Server 链接解析、默认分支与固定提交、Basic／Bearer 请求、ZIP 范围与安全解压、成功切换、失败／取消回滚、重启恢复、离线打开、相同来源复用、未变提交不下载、读取设置变化及坏索引的本地重建。另以公开 Cloud 仓库只读验证实际版本解析、ZIP 响应与根目录格式；未进行企业私有仓库认证或完整企业源码下载。此前本机 HTTPS 模拟仓库测试的提交解析、下载、索引及 401 回滚同样不代表企业环境验收。

整合测试同时检查跨来源问答和自定义回答要求：同名程序在两个资料库使用不同规则，切换历史、重启和重试后仍取各自源码与对话，保存的回答要求进入实际模型请求。前端回归涵盖导入取消时恢复框架设置、历史恢复期间的操作冲突、迟到响应隔离，以及摘要标题不会截成错误程序名。

此前使用隔离浏览器检查了来源分组、历史对话、源码引用和回答要求入口；[2026-10-28 入口截图](./reports/2026-10-28-remote-source-ui/left-entry-grouped-history.jpg)保留为该轮历史记录，不作为新 Cloud 功能已在企业环境通过的证明。源码流程的真实模型测试与最终 Windows EXE 的离线回归分别记录，不能互相代替；企业服务器版本、代理、证书、真实权限及同包办公设备验收仍需在获准环境完成。
