# 代码理解型 Agent 的架构设计与实施流程

> 核心判断：开发顺序必须沿着“代码事实是否可靠”推进，而不是沿着“聊天界面是否可用”推进。每一阶段都交付可独立测试的能力，上一层不依赖 LLM 掩盖下一层的错误。

状态：`Target product process — current POC overrides implementation order`

当前实施顺序以 [可演示 POC](./09-demonstrable-poc.md) 为准。本文件描述 POC 通过后扩大为正式产品时的证据门槛，不再作为第一次演示的前置清单。

## 阶段 0：框架与契约

完整产品路线进入本阶段时，再完成以下设计；当前 POC 不等待这些契约闭合：

- 第一版问题分类和明确非目标；
- 离线索引与在线调查的组件图；
- 统一 IR、类型化关系和证据包语义；
- Agent 工具边界与状态机；
- 源码隐私、模型边界、可复现性和错误处理；
- 解析器、存储、向量检索和编排框架的可替换接口。

**退出条件**：对任意一个问题，都能说明由哪个组件接收、调用什么工具、产生什么事实、如何失败以及怎样被核验。

## 阶段 1：代码库画像与问题基线

这一阶段在公司环境内只做只读盘点，不需要把代码交给外部项目：

- COBOL 文件数量、总行数、固定/自由格式和编码；
- COPYBOOK 位置、COPY/REPLACING 和条件编译方式；
- CL、DDS、SQL、CICS、JCL/作业、文件和控制表类型；
- 静态 `CALL`、`CALL identifier`、`PERFORM THRU` 和 `GO TO` 的大致分布；
- 构建入口、主要程序命名和无法获得的依赖；
- 首批问题按计算、数据来源、条件和调用路径分类。

输出是统计与能力需求，不是源码摘录。**退出条件**：解析器 Bake-off 的 5 个挑战样本和关系标注范围已在公司内确定。

## 阶段 2：解析器垂直验证

用同一批样本比较 CodeGraph、ProLeap、Tree-sitter 和必要的最小自研规则，先只验证一条端到端链：

```text
SourceFile → Program → Paragraph → Statement
           → CALL/PERFORM → Field READ/WRITE → Source Range
```

输出包括统一 IR 样例、未解析清单、源码映射和精确率/召回率。**退出条件**：关键结构与调用达到门槛，字段流的缺口有明确实现方案。解析不通过，不开始 RAG 调优。

## 阶段 3：混合检索基线

在不使用 LLM 生成答案的情况下建立可消融的检索阶梯：

1. Neo4j 精确符号验证，命中后建立独立锚定种子；
2. Qdrant 稀疏词汇召回；
3. Qwen3-Embedding 稠密召回；
4. 对稀疏与稠密候选执行 RRF 秩融合；
5. Qwen3-Reranker 对融合后的非锚定候选集重排；
6. 应用层合并锚定种子与重排候选，锚定种子优先；
7. BGE-M3 dense/sparse/multivector 作为挑战实验。

代码索引单位来自 IR 的 Program、Paragraph、字段定义、SQL 块和有边界语句窗口，不采用任意 token 切块。每路分别记录排名、命中原因、索引版本、耗时和资源成本。

**退出条件**：对首批问题，大多数正确入口能稳定进入 Top-5/Top-20；稠密向量、重排序和 multivector 必须分别通过 Recall、MRR/nDCG、延迟与资源消融证明增益，否则从默认路径移除。

## 阶段 4：图引导代码调查

把重排后的 5–10 个 `entity_id` 作为 Neo4j 调查种子，围绕候选入口实现问题特定的工具：

1. 查找符号与所有定义/引用；
2. 向上和向下追踪 `CALL/PERFORM/GO TO`；
3. 对结果字段做反向数据切片；
4. 提取控制该写入点的条件；
5. 跨 `CALL USING` 映射参数；
6. 追到 SQL、文件、COPYBOOK 或未解析边界；
7. 按答案覆盖增益和 token 成本做证据预算、去重与压缩；
8. 构造最小完整逻辑闭包和证据包。

**退出条件**：不依赖 LLM，工具输出已经足以让分析人员复核主要问题；Top-5 证据路径命中率达到目标；加入代码图相对纯检索有可测量的完整路径增益。

## 阶段 5：受控 Agent 与回答核验

使用 LangGraph 承载受限状态机。接入 LLM 后只增加三项能力：理解自然语言问题、决定下一步调用哪个调查工具、把证据翻译成业务说明。回答先由 Evidence Integrity Validator 确定性检查快照、实体、关系和源码引用，再由 Claim Support Checker 判断每条 claim 是否受支持或扩大了范围。

Agent 最多执行有限次数的“定位—扩展—检查”循环；预算耗尽或证据存在歧义时拒答。**退出条件**：不存在虚构源码实体和位置，代码事实均有证据，事实、推断和待确认项被正确区分。

## 阶段 6：公司内 DXC 适配与真实试点

通用内核部署到公司批准环境后，才加入 DXC 私有规则、真实术语和内部验收集。适配应优先通过配置、规则插件和解析器扩展完成，不把私有规则写入公开内核。

**退出条件**：真实业务问题能够复现、审计和回归；聚合错误指标证明 DXC 适配持续改善，而不是依赖个别 Prompt。

## 当前 POC 应产出的交付物

当前只交付一条可演示纵向闭环：

1. Windows 文件夹扫描、编码处理和源码行号映射；
2. Program、Paragraph、Field 的结构分块；
3. SQLite 精确符号与 FTS5 全文索引，以及可选的公司 API Embedding；
4. 四个只读调查工具；
5. 最多六步的单 Agent 工具循环；
6. Streamlit 聊天、证据展开和明确拒答；
7. 以 `CALC-01` 为首问的六问演示验收。

完整统一 IR、企业工具契约、Evidence Package、Qdrant、Neo4j 和 LangGraph 在 POC 证明有必要后再恢复实施。
