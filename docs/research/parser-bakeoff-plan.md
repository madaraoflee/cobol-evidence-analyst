# 解析器 Bake-off 计划：在同一真实语料上选底座

> 核心判断：不按 GitHub 功能列表选择解析器。CodeGraph、ProLeap 和 Tree-sitter 必须在同一批企业 COBOL 上输出同一证据契约，最终按关系正确性和可扩展性决定单用还是组合。

状态：`Proposed`  
日期：2026-08-27

## 1. 候选与当前判断

| 候选 | 适合承担的角色 | 已知优势 | 当前风险 |
| --- | --- | --- | --- |
| [CodeGraph](https://github.com/colbymchenry/codegraph) | 快速结构索引和本地查询候选 | 已列出 COBOL Program、Paragraph、`PERFORM/GO TO`、字面量 `CALL`、COPY、字段、CICS 和 SQL INCLUDE 支持 | 公开跨文件覆盖表未给 COBOL 数据；字段级数据流、动态调用和 `CALL USING` 仍需证明 |
| [ProLeap COBOL Parser](https://github.com/uwol/proleap-cobol-parser) | 语义解析器和自有事实图的前端候选 | AST + ASG、变量访问、部分控制/数据语义、`COPY/REPLACE` 预处理 | JVM 集成成本；EXEC SQL/CICS 主要作为文本，企业方言需要扩展 |
| [tree-sitter-cobol](https://github.com/yutaro-sakamoto/tree-sitter-cobol) / [enterprise 版本](https://github.com/Spantree/tree-sitter-cobol-enterprise) | 快速、容错、增量语法树与编辑体验候选 | 解析速度快，适合保留不完整源码结构；enterprise 分支关注 IBM/CICS/SQL | 项目成熟度和不同语料覆盖不一致；语义关系需要大量自建 |
| [Joern CPG](https://docs.joern.io/) | 统一图模式和查询思想参考 | 将语法、控制流和数据流放入可扩展 Code Property Graph | 官方语言前端不含 COBOL，不能直接承担解析工作 |

初始优先级是：先验证 CodeGraph 能否快速提供结构底座，再验证 ProLeap 是否能补足字段和语义关系；Tree-sitter 用作容错与方言补充。只有这些组合仍无法达到门槛时，才考虑扩大自研解析器范围。

## 2. 最小挑战语料

公司环境从试点业务域挑 5 个程序；公开开发环境另行编写结构对应、但不来自公司代码的合成 fixture。两套语料不按随机抽样，而是刻意覆盖最危险的结构：

1. 一个万行级主程序，包含 Section、`PERFORM THRU`、循环和 `GO TO`。
2. 一个多层静态 `CALL USING` 链，参数在不同程序中改名或重定义。
3. 一个表驱动或变量驱动的动态 `CALL`，要求输出候选、条件和未解析原因。
4. 一个数据定义复杂的程序，覆盖 COPY/REPLACING、REDEFINES、OCCURS、88 级和固定列续行。
5. 一个大量使用 SQL、CICS、文件、作业或控制表的程序，验证外部数据来源。

每类再准备一个最小化 fixture，用于精确定位解析失败；真实大程序负责公司内代表性，原创 fixture 负责公开侧可重复诊断。不得通过删名称或改常量的方式把生产代码当作“合成样本”。

## 3. 统一输出要求

每个候选必须经适配器输出相同的 IR 和关系，至少包括：

- Program、Section、Paragraph、Statement、Field、Copybook 和外部资源实体；
- `CONTAINS`、`PERFORMS`、`PERFORMS_THRU`、`GOES_TO`、`CALLS/POSSIBLY_CALLS`；
- 字段 `READS/WRITES/FLOWS_TO` 与跨程序 `PASSES_AS`；
- SQL 表/列、文件、CICS 目标和控制表关系；
- 原始源码与 COPY 展开后源码的双向位置；
- 未解析语句、歧义候选、解析器版本和方言规则版本。

无法抽取某类关系并不等于失败；静默遗漏才是失败。适配器必须把“不知道”也变成可查询事实。

## 4. 测试方法

1. 人工标注 5 个挑战程序的关键实体和关系，采用双人复核解决歧义。
2. 固定源码快照和候选版本，在相同环境中运行所有候选。
3. 分别计算实体识别、调用关系、字段关系和源码映射的精确率/召回率。
4. 记录每一种失败的具体语法、方言、规模和修复成本，不只记录总分。
5. 对组合方案做消融：单用 CodeGraph、单用 ProLeap、结构+语义组合、加入方言规则，确认每一层是否真实增益。
6. 使用首批金标准问题验证“关系分数提高”是否真的改善证据路径召回。

## 5. 决策矩阵

权重在 M1 获得真实样本后最终确认，当前建议如下：

| 维度 | 建议权重 | 判断依据 |
| --- | ---: | --- |
| 结构与调用正确性 | 25% | 实体及 `PERFORM/CALL/GO TO` 的精确率、召回率 |
| 字段与跨程序数据流 | 25% | 读写、赋值、参数传递和来源路径 |
| 企业方言与外部语句 | 15% | COPY、SQL、CICS、动态调用和内部框架约定 |
| 源码映射与可追溯性 | 15% | 原始/展开位置、哈希、错误位置和可重放性 |
| 扩展与维护成本 | 10% | 新方言规则、升级影响、测试便利性 |
| 运行与许可约束 | 10% | 内网部署、性能、依赖、许可证和社区维护状态 |

总分只用于排序，不能覆盖硬性门槛。若字段数据流得分低于产品需要，即使解析速度和综合分很高，也不能单独成为底座。

## 6. 允许的决策结果

- **CodeGraph 为主，补自定义语义抽取**：结构和调用已足够稳定时采用。
- **ProLeap 适配器 + 自有类型化图**：ASG 更接近真实语义且扩展成本可控时采用。
- **混合前端**：一个工具负责容错语法与源码映射，另一个负责语义关系；冲突必须有确定的优先级和审计记录。
- **有限自研解析层**：只补企业方言和关键关系，不从零重写完整 COBOL 编译器。

M2 的最终交付物不是一张“工具比较表”，而是一份带实测数据的选型 ADR，以及未覆盖语法的明确风险清单。
