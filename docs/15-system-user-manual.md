# 系统使用手册（当前版本）

更新时间：2026-09-20

适用入口：`poc/analyze_source.py`、`poc/web_app.py`

当前 POC 已换为三类框架程序的服务申请案例。启动后可先看合成源码导读，再“载入此案例”建立索引，最后通过公司接口实际分析；旧保费预览已移除。完整演示步骤见本文后续说明。

网页默认业务解读已支持源码分页、普通聊天回复、分段汇总与失败时保留已有解释。公司电脑更新步骤见本文“第一次准备”和“使用本机网页工作台”。旧严格 Agent 的动作协议限制不再是网页问答前提。

本手册是办公室电脑的最新操作入口。系统的正确使用顺序只有一条：先快速接入指定源码目录，确认程序清单，再选择一个入口按需建立局部事实索引并提问。对于一万多个、每个数万行的程序，初次接入不再为全库逐语句建索引。系统不会自动读取项目里的示例源码，也不会把“索引完成”当成“业务已经分析完成”。

## 一、第一次准备

在 Windows 电脑准备 Python 3.10 或更高版本（本次目录性能验证使用 Python 3.14.4）、Git，以及公司批准的源码目录和输出目录。源码与输出放在本机 SSD/硬盘；8–16 GB 内存电脑采用下文的轻量目录流程，不预先全库详细解析。项目只使用 Python 标准库，不需要安装额外 Python 包；API Key 不写入代码、命令历史、输出目录或 GitHub。

在项目目录打开命令提示符，首次下载或换电脑时执行：

```bat
git clone https://github.com/madaraoflee/cobol-evidence-analyst.git
cd cobol-evidence-analyst
git config core.hooksPath .githooks
```

以后每天开始工作先同步：

```bat
git pull --ff-only
```

首次下载后，把项目根目录（与 `README.md` 同级）的 `.env.example` 复制一份，重命名为 `.env`，用文本编辑器填写第 3 节的接口配置。以后更新代码时保留本机 `.env`，不需要重新配置；如果另存一份新的项目目录，把原来的 `.env` 复制到新项目根目录。Git 已忽略 `.env`，提交到仓库的只有空白模板。

源码和输出目录应放在项目目录之外，例如 `D:\cobol-data\source` 与 `D:\cobol-output\analysis`。不要把真实源码、API Key、SQLite 数据库或问答结果上传到公开仓库。

## 二、先快速接入源码目录（不联网）

从项目根目录执行：

```bat
python poc\analyze_source.py ^
  --index-mode catalog ^
  --source "D:\cobol-data\source" ^
  --output "D:\cobol-output\analysis"
```

也可以使用包装脚本：

```bat
poc\run_analyze.bat --index-mode catalog --source "D:\cobol-data\source" --output "D:\cobol-output\analysis"
```

上述命令只做轻量目录接入，不需要 API Key，也不会联网。**命令行默认仍是 `full`，所以公司大库命令必须明确保留 `--index-mode catalog`。** 网页默认使用 `catalog`。

目录通常先读每文件 16 KiB；在尚未找到 PROGRAM-ID 时最多探测 256 KiB。它不统计整个大文件的全部语句，也可能看不到尾部嵌套程序。未识别到 PROGRAM-ID 的候选文件会明确标注 `name_origin=path`，文件名仅用于选择入口，不被当作已经核验的程序名。

重复接入同一目录、使用相同输出和读取选项时，未变文件根据大小、mtime/ctime 时间戳和文件身份复用目录缓存，不打开正文；新增、修改、删除会更新清单。每完成一个文件保存一个检查点，中断后重跑可复用已完成部分。目录指纹以 `catalog-sha256:` 开头，**不等于全库内容 Hash 核验**。如导出或同步工具可能保留原元数据，可加 `--verify-content` 强制逐文件流式读取全文并计算摘要；这会较慢，但仍不会替全库建立逐语句索引。

输出目录包含：

- `diagnosis.md` / `diagnosis.json`：接入范围、缓存复用、编码及边界。
- `programs.json`：发现的程序名或待解析文件入口、相对路径、`entry_key`。
- `source-catalog.sqlite`：可恢复的轻量目录缓存。
- `structural-index.sqlite`：选择入口并执行详细分析之后才建立的局部事实索引。

`INDEX_READY` 且原因是 `SOURCE_CATALOG_READY` 表示目录可选，不表示所有程序或依赖已解析。文件头截断、缺少 COPY/CALL 或闭源对象会形成覆盖边界；只要入口的可读源码可解析，就可以继续局部分析。路径无效、没有可选文件、入口无法明确识别和证据快照不一致仍需处理。

常用输入选项：

```bat
--encoding gb18030          例如已知源码编码时指定
--source-format fixed       固定列 COBOL
--source-format free        自由格式 COBOL
--exclude-extensionless     排除无扩展名成员
--extensions ".cbl,.cpy,.member"  自定义完整扩展名集合
```

编码或格式不确定时先用默认的 `auto`，再检查诊断和 `PROGRAM-ID` 是否显示正常中文。

## 三、配置接口并进行问答

在项目根目录创建 `.env` 后，填写以下三项。`COMPANY_API_BASE_URL` 是公司给你的完整 API 根地址（包含适用的版本前缀，例如 `/v1`），`COMPANY_CHAT_MODEL` 是网关接受的模型名或部署别名：

```dotenv
COMPANY_API_BASE_URL=https://approved-gateway.example/v1
COMPANY_API_KEY=填入自己的接口密钥
COMPANY_CHAT_MODEL=填入公司的模型名或部署别名
```

示例中的值都需要替换。`COMPANY_API_STYLE` 默认是 `openai_compatible`，除非接口要求其他风格，否则不必修改。`COMPANY_EMBEDDING_MODEL` 不是业务问答必填项，不用为了启动网页寻找嵌入模型。

保存为 UTF-8 文本；Windows 换行和 UTF-8 BOM 均可。文件名必须是 `.env`，不是 `.env.txt`；在资源管理器打开“文件扩展名”后核对。值可以用单引号或双引号包住；`$`、`${...}` 等按字面值保存，不会执行命令或展开环境变量。不要把 `.env` 当作需要运行的脚本。

网页和命令行入口都自动读取这份 `.env`，文件位置固定为项目根目录，不随启动终端所在目录改变。优先级是**显式命令行参数 → 启动进程已有环境变量 → `.env`**；若改了 `.env` 仍看到旧配置，检查启动终端或系统中是否保留了同名变量。修改后关闭工作台服务再重新启动。Key 只供本机服务读取，页面不会接收或保存它；`.env` 留在本机，不提交到 GitHub。

命令行只有明确加上 `--allow-network` 才会发送必要的源码证据；网页则在点击“开始业务分析”后发起本次问答。仅配置 `.env`、启动网页或接入源码都不会自动发起模型问答。

先从 `programs.json` 复制真实的 PROGRAM-ID，再执行：

```bat
python poc\analyze_source.py ^
  --index-mode catalog ^
  --source "D:\cobol-data\source" ^
  --output "D:\cobol-output\analysis" ^
  --entry "实际的PROGRAM-ID" ^
  --question "请解释该程序的主要处理步骤、输入输出和调用，并引用源码行号。" ^
  --allow-network
```

`--entry` 可填写清单中的程序名、唯一相对路径或 `entry_key`；有同名程序时优先从网页选中具体文件，或复制对应 `entry_key`，不让系统猜测同名目标。详细解析后仍无法明确入口时会显示诊断。问答结果写入 `agent-result.json` 和 `agent-result.md`。没有提问时是 `NOT_REQUESTED`，未开启联网时是 `NETWORK_DISABLED`。

### 配置实际框架资料

把公司批准的框架文字稿复制到项目内 `.poc-data/framework/reference.md`（缺少文件夹时先创建），系统默认自动加载。本次私有交付包已附带用户提供的文字稿；如果需要指定其他位置，可在同一个 `.env` 设置：

```dotenv
FRAMEWORK_REFERENCE_PATH=.poc-data/framework/reference.md
```

也可填写绝对路径，例如 `FRAMEWORK_REFERENCE_PATH="D:\cobol-data\knowledge\reference.md"`。支持 UTF-8 Markdown，包含标题、表格及可选的 `SOURCE_PAGE` 页码标记；相对路径固定按项目根目录解析。资料正文及 `.env` 都不随 GitHub 分发，换电脑时需要按公司允许的方式复制。`git pull` 更新代码后继续使用已有资料即可。接口配置与框架配置相互独立，资料路径出错时会明确显示，仍可分析现有源码。

重启网页后，“框架资料”卡片先显示**已加载**。选择实际入口并分析后，核对是否**已匹配当前源码**、哪些词项／章节命中，并点击源码引用查看真实行号。只加载文件不表示该程序采用了文档约定；`NO_MATCH` 表示当前范围未找到可用匹配，不等于程序一定不是该框架。页面中的框架解释同时显示源码引用和资料引用，属于条件性解释，不能据此宣称运行已经验证。

建议先问：“请结合框架资料说明这个程序的业务目的、主控流程、I/O 功能与状态、跨程序数据，以及因闭源对象或缺失元数据而无法确认的部分。分别引用源码和资料。” 对很大的程序，随后按读取、校验、更新、导航或重启分别提问，避免把有限证据当作全程序覆盖。

仅接入资料和导入源码不联网；点击开始业务分析后，模型收到问题、当前入口、范围说明、检索到的有限框架节选，以及工具读出的有限源码证据。实际调用模型仍由 `COMPANY_CHAT_MODEL` 决定。

## 四、使用本机网页工作台

网页工作台已接通真实源码和受控 Agent，是办公室日常操作的推荐入口。完成一次 `.env` 配置后，在资源管理器双击 `poc\run_web.bat` 即可，以后不需要先打开终端输入 API 信息。也可以从项目根目录启动：

```bat
python poc\web_app.py
```

不自动打开浏览器时：

```bat
python poc\web_app.py --no-browser
```

浏览器访问终端打印的 `http://127.0.0.1:8765`。需要换端口时使用 `--port 8787`。在页面中依次填写源码目录、输出目录、编码/格式、入口程序和问题；先连接源码并确认程序清单，再开始分析。页面支持中文简体、中文繁體和 English 三种界面语言；切换语言只翻译系统界面，不翻译源码、模型回答或证据文本。

导入进度会区分“发现文件、建立目录、准备分析范围、详细索引、校验”等阶段，显示当前文件、已完成/总量、已用时间，以及可以估算时的剩余时间。发现目录时总数未知；模型响应或某些解析阶段不显示伪造百分比，估时会随实际速率更新。文件完成进度和业务分析完成进度是不同的概念。

需要停止时使用页面取消操作；取消在处理边界生效，已完成的目录检查点保留。下次接入仍选择同一源码和输出目录，避免每次新建输出导致无法复用缓存。源码更新后重新接入，切勿仅刷新旧答案。

选定入口后，业务模式为该文件和可定位的静态 CALL/COPY 建立轻量索引，逐文件扫描且不再使用旧的 16 MiB、24/64 文件及独立调用深度截断。网页默认“完整业务链”：关联范围的源码分页连续分批解读，再按程序及业务链分层汇总。12/48 段是每批大小。需要快速定位时切换“按问题重点阅读”，其 12/48 段才是整次选读上限。完整链是可定位静态范围，不包含凭空猜测的动态目标、缺失程序或配置路由。

工作台只监听本机回环地址，并校验访问来源和当前会话；它不是对外发布的网站。一次只运行一个分析任务。重新开始分析会清除旧回答和旧证据，新的证据只对当前源码快照有效。

## 五、如何判读结果

优先查看回答中的证据编号、源码路径和行号，再回到 `programs.json` 与源码核对。若源码在索引后被修改、索引数据库损坏、证据不属于当前快照，系统会要求重新运行，而不是继续使用旧答案。

以下状态必须区别对待：

- `INDEX_READY`：索引可用，不代表业务解释完整。
- `ANALYZED`：已生成业务解释，当前选定索引范围的分段解读已完成；模型业务推断仍需核对，不等于全库或运行结果验证。
- `NEEDS_ATTENTION`：仍有缺口，先阅读诊断；可读入口通常仍能继续。`BLOCKED` / `NOT_READY`：本次输入、入口、证据或接口条件不满足。
- `PARTIAL`：已有带引用的局部解释，同时保留缺失依赖、未知运行值或闭源对象边界。
- `SAFE_STOP`：调查流程中断；可能是响应协议、接口调用、工具参数或预算问题，须查看实际停止原因，不能一律解释为证据不足。
- `ABSTAINED`：没有形成可接受的结论。若外层同时为 `SAFE_STOP`，先处理流程中断；若 `stop_reason=model_abstained`，才是模型正常选择不形成结论。
- `CITATION_VERIFIED_ONLY`：引用与源码位置可核对，但不等于证明运行时最终值。
- `SUPPORTED_WITH_BOUNDARIES`：只在明确支持的语法和边界内成立。

缺少 AS400 框架 COPY、封装对象源码或部分被调用程序，并不要求放弃当前程序。系统应先说明现有代码中的条件、计算、传参和可见调用，把闭源实现、数据库内容与实际运行结果列为未知。连续两次调查无新进展（`no_progress`）时，如果已发现可读取证据且工具预算仍足够，会转去读取这些证据并尝试形成局部回答；若无证据、校验失败或预算耗尽，仍会保留边界并停止，不能编造答案。

`run_demo.py`、其他 `*_demo.py` 和固定框架验收命令只用于合成案例回归，不是公司源码入口；不要用演示通过来替代真实源码验收。

业务轻量索引与分页阅读避免把完整文件和全量语句图同时放入内存，分页保存在本机数据库，程序说明分层汇总。路径清单、稀疏事实、页元数据与结果仍随规模增长，运行时长和磁盘占用也会增加。完整业务链不等于任意大库均已完成性能验收；公司现场需记录实际范围与耗时。旧 strict 路径的 16 MiB 详细索引预算继续保留。

## 六、常见问题

网页分析后打开“API 返回”，查看能力探测和实际调查分别收到了什么。响应即使未通过 Agent 协议也会保留有界正文；只把它作为接口诊断和待核验的模型内容，不作为源码事实。该视图同时显示具体 `stop_reason`，避免只看到汇总代码 `AGENT_SAFETY_STOPPED`。响应诊断随 `agent-result.json` 和页面 JSON 导出保存，可能含源码片段或业务文字，应与源码按同样范围保存在本机。命令行默认仍不记录响应正文；旧结果没有正文时须重新在网页发起分析。

| 现象 | 处理 |
| --- | --- |
| `python` 或 `git` 找不到 | 安装并重新打开命令提示符，确认加入 PATH。 |
| 输出目录和源码目录相互包含 | 改用两个完全独立的目录。 |
| 目录有文件但程序名标为待解析 | 检查编码/格式；目录只看有界头部。选择该文件后确认详细解析能识别实际 PROGRAM-ID。 |
| 导入很慢 | 确认网页使用目录模式；CLI 保留 `--index-mode catalog`。看当前阶段及缓存命中；关闭非必要的强制内容校验，保留原输出目录。 |
| 缺少 COPY 或封装对象 | 继续分析可见入口；阅读 PARTIAL 与 boundaries，不需要补齐闭源对象才能说明已有代码。 |
| 框架资料未加载 | 核对 `.env` 的 `FRAMEWORK_REFERENCE_PATH`、文件存在及 UTF-8 编码；资料不在 GitHub 代码里，换电脑需单独复制。 |
| 框架资料已加载但没有匹配 | 先选择真实入口进行局部解析，再核对源码中的控制 COPY、功能码或共享字段是否出现在该版本资料中；仅文件名相似不能证明匹配。 |
| 更新框架资料后看到旧结论 | 旧回答绑定旧资料摘要；重新分析以生成新资料版本下的解释，不能把旧回答自动视作新版本结论。 |
| 单程序超过详细分析预算 | 保留当前目录，选择较小入口或按业务范围重新导出；`SCOPE_LIMIT` 不表示整批导入失败。 |
| 入口歧义 | 从程序清单选择准确文件和定义位置；核对目录中是否存在重复入口。 |
| 索引期间提示源码变化 | 停止同步/复制任务，确保源码稳定后重新运行。 |
| 问答被阻断 | 先看 `diagnosis.md`，确认入口来自 `programs.json`，再检查 `.env`、覆盖它的环境变量和 API 能力。 |
| 配好了 `.env` 仍显示未提供 | 核对文件位于项目根目录、文件名不是 `.env.txt`、三个必填项都有实际值；保存后重启工作台。 |
| 修改 `.env` 后仍使用旧设置 | 先重启服务，再检查启动进程已有的同名环境变量；它们的优先级高于 `.env`。 |
| 网页端口被占用 | 使用 `python poc\\web_app.py --port 8787`，访问新端口。 |
| 页面显示旧内容或会话失效 | 关闭工作台后重新启动并刷新页面；不要复用旧浏览器标签页。 |

## 七、日常保存和提交

修改代码或文档后，在项目根目录执行测试：

```bat
python -m unittest discover -s poc\tests -v
node --test poc\tests\web_i18n.test.cjs
```

确认源码和输出目录没有被放进仓库，再查看变更并提交：

```bat
git status
git add README.md docs poc
git commit -m "说明本次改动"
git status
```

本仓库已配置提交后自动推送钩子；提交成功后会自动推送当前分支。若办公室电脑是新克隆的仓库，必须先执行一次 `git config core.hooksPath .githooks`。推送失败时先执行 `git pull --ff-only`，解决网络或远端更新后再重新提交；不要强制覆盖远端历史。

## 八、当前边界和验收要求

当前系统是“以源码证据为底座的受控分析工具”，不是 COBOL 运行时，也不保证任意方言、隐式框架和完整业务流程都能自动解释。真实源码、实际接口、Windows 编码和办公室网络必须在目标环境做一次验收；本地合成案例、模拟接口和测试通过不能替代这一步。

实现层已确认的行为包括：轻量目录按文件增量复用、选定范围详细解析后校验内容；网页只绑定 `127.0.0.1` 并校验会话；新任务清除旧证据并绑定当前快照；界面本地化不改动源码或模型文本；局部缺失保留边界继续解释，输入、证据完整性或配置不满足条件时返回明确停止状态。上述行为分别由 `poc/analyze_source.py`、`poc/web_app.py`、`poc/web/i18n.js` 及其测试覆盖。

## 九、当前业务分析流程补充

当前网页主线是“服务申请受理 → 在线复核 → 夜间批量生效”。系统先按源码分段阅读，再合并为业务说明，重点回答处理对象、办理条件、决策规则、状态与数据变化，以及失败影响。普通聊天正文可以直接展示；严格动作协议仅保留给研发核验，不是日常业务问答的前置条件。

如需使用本机批准的框架资料，将文字稿放在 `.poc-data/framework/reference.md`，或在 `.env` 中设置 `FRAMEWORK_REFERENCE_PATH`。资料不提交到 GitHub；换电脑时需单独复制。系统会把匹配的框架章节与当前源码证据分开引用，资料说明不等于运行事实。遇到接口停止时打开页面“API 返回”查看请求、正文、工具调用和本地停止原因；未核验正文不能当作已证明结论。

以后修改系统或手册，直接编辑现有文件（优先本手册、README 和对应章节文档），不要为一次改动新建日期报告、重复 POC 说明或新的操作手册。只有出现真正独立且长期维护的主题时才新增文档，并先在 README 建立唯一入口。
