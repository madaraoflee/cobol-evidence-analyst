# 缺陷登记与逐次回归

每次修复都要验证全部已记录缺陷及全部现有测试；只跑新测试、只看测试总数或只检查受影响模块，不能算本次修复通过。这个要求适用于后续维护，不改变本地分析冻结、构建授权或正式发布验收要求。

## 三份记录各自说明什么

- `registry.json` 是缺陷账本。每条有稳定编号、症状、原因、修复证据、准确的回归测试映射及验证边界。一个测试不是一个缺陷；多个测试可以共同验证一条缺陷。
- `regression-baseline.json` 是不可缩减的最低测试集合，初始绑定已发布候选对应的源码：4,842 个 Python 测试和 296 个浏览器测试。运行时还必须执行所有新增测试。不能删旧测试、删缺陷条目或删映射来换取通过；检查器会读取 Git 历史中的合同，提交了删除也不能重置基线。
- 每次运行生成独立的 `BUG-REGRESSION-REPORT.json`，逐条列出缺陷和对应测试的实际结果，同时保留完整分片、浏览器结果、输入文件哈希和源码快照。旧结果不能冒充新一轮验证。

## 每次修复的必需步骤

先登记新发现，写清能复现的输入、表现和预期；已有复现证据应保留修复前失败结果。确认原因后，增加针对故障的回归测试，再做最小修复。原有测试的断言不能为了让修复通过而削弱。测试确需调整时，记录原因、保留等价或更强的覆盖，并由用户明确决定历史合同的迁移；检查器没有“忽略失败”或自动重置基线开关。

在具有完整 Git 历史的固定工作目录运行以下维护命令；浅克隆会被阻断，不能省略历史来重置合同。公开语料使用已经核对冻结文件哈希的本地目录；缺少语料导致跳过也会阻断验收。

```bash
PUBLIC_BUSINESS_SOURCE_ROOT=/absolute/path/to/frozen-public-corpus \
  python3 tools/verify_bug_regressions.py --output /absolute/path/to/new-result-directory
```

结果目录必须是源码目录之外的新目录。命令会执行全部 Python 测试（包括 `poc/tests` 和 `tools/tests`）和全部浏览器测试，不构建应用、安装包或验收可执行文件，不触发 Actions，不调用真实模型。各组进度见结果目录的 `python-*.log`；源码、测试或合同在运行中发生变化，结果立即失效。需要先检查登记完整性时可加 `--check-only`，它只产生 `inventory_only`，不代表测试通过。

`status=passed`、`source_regressions_passed=true` 和 `all_recorded_bugs_verified=true` 必须同时成立才算**已登记范围内的源码离线回归通过**。任何失败、缺失、重复执行、跳过、预期失败或未验证缺陷都会阻断“全部通过”。平台不适用项目不能伪装成通过；需要在适用平台验证并保留结果，当前入口不会自动豁免它们。`open` 条目即使其他测试全过也仍是未验证，报告不得写成“所有 bug 已解决”。

源码离线通过不等于真实模型回答正确，也不等于目标 Windows 设备通过。没有现场复现材料的启动耗时、服务错误或业务质量问题要保留为 `open`；填满表单不能关闭它们。正式发布仍按 [同包联合验收](../joint-release-acceptance.md) 执行，且须有新的构建/发布授权。

## 历史补录边界

初始账本根据仓库提交、历史故障报告和当前回归测试回溯。记录中的 `evidence` 指向修复或复现来源，`regressions` 指向当前实际存在的检查。历史报告有时把多个故障归在一次修复里，本账本按可确认的故障拆分；不把一般新增功能冒称历史 bug。只在口头讨论或未保存的现场日志中出现的问题无法靠 Git 完整恢复，发现后必须继续追加，不能声称历史绝无遗漏。

已记录故障即使长期未再出现也不删除；重新出现时保留原编号，补充复现记录、原因和新增测试。新增缺陷的测试同时追加到最低基线。每次交付说明必须报告本轮实际运行数量、逐条缺陷结果和仍未验证事项，不能承诺测试覆盖之外永远没有新 bug。
