# 框架控制接入路径引擎与运行契约

更新：2026-09-12。F02 已接通受支持的框架控制路径；F03 已有文件筛选、游标、锁、事务和重启的可执行契约子集。**现在能得出“给定源码、契约和场景，这条路径如何结束”的结果，仍不能据此承诺真实系统的全部运行行为。**

## 与上一版的实质区别

上一版只看到控制 COPY 中写了哪些 PERFORM。本版将这些过程展开成独立索引，交给现有控制流构建器的框架模式，再推进 MOVE、文本/数值 IF、编号 section、PERFORM 范围和显式 TEST BEFORE / UNTIL 循环。调用业务子程序时核对 USING/LINKAGE 布局，进入真实源码，并在普通返回时按传参方式处理回写；外部接口则必须与所加载契约及实参布局一致。

调用链上每一步仍保留 COPY 原始行、宿主包含链和源哈希。派生 Evidence 与原始 Evidence 不混用。旧数值错误接口没有被静默改成框架执行器；Agent 问答也尚未自动使用新路径工具。[ADR-0009](./adr/0009-contract-conditional-framework-paths.md)

## 一条能核对的业务路径

原创请求场景中，批处理读取 4 条候选数据。契约只选择 `TYPE=SERVICE`，业务子程序另行要求 `STATE=PENDING`：

| 请求 | 发生了什么 | 最终状态 |
| --- | --- | --- |
| A001 | FIRST 已读入；进入校验子程序，保存并提交 | DONE |
| A002 | 不满足文件访问条件，不进入业务校验 | 保持 PENDING |
| A003 | 文件读取成功，但子程序返回 SKIP | 保持 REVIEW |
| A004 | NEXT 读入；校验允许后保存并提交 | DONE |

这区分了“文件没选到”和“业务代码跳过”。还做了源代码变异检查：在 FIRST 后多插入 NEXT 会漏掉 A001；改变子程序条件会改为处理 A003；在控制 COPY 末尾覆写错误状态会导致原有错误预期失败。因此结果不是按配置中的 section 名称生成的固定故事。

联机入口只读取指定请求并保存或跳过，最后进入 SUMMARY、REVIEW 或 ERROR；不套用批处理循环与检查点。

## 五类契约实际支持到哪里

| 契约 | 本版能推演 | 仍不支持或不能推断 |
| --- | --- | --- |
| 文件筛选 | 单数据集；按完整唯一键升序；等值条件合取；区分筛选与业务校验 | 自动解析完整 DDS/PF/LF、复杂有序 select/omit、JOIN、多记录格式、插入删除 |
| 游标 | 按访问路径与 session 明确标识；FIRST 可声明“定位并读取”或“只定位”；NEXT / GET / CLOSE 影响对应状态 | 同一程序名即同一 ODP；真实运行库、文件覆盖与共享打开关系 |
| 锁 | 场景中的外部锁；声明的读锁、写入前锁检查，以及推进/关闭/提交/回滚时的释放政策 | 真实锁等待、重试时间、并发交错、死锁、生产锁所有权 |
| 事务 | 单数据集、所有声明服务共享一个事务；读自己待提交写入；区分 pending / committed；失败提交/回滚；保留先前提交 | 多数据源/分布式事务、隔离级别全语义、真实 journal 与提交定义 |
| 重启 | 提交进度生成检查点；绑定契约/版本、已提交数据哈希和访问路径；从已提交键之后恢复；无效/缺少检查点停止 | 自动发现生产重启协议、检查点真实性认证、数据变化后的恢复策略 |

SAVE 只更新现有记录，不允许改变任何声明排序键。故障注入在模型的操作效果发生前生效，不代表生产环境所有“部分生效后报错”的行为。重启 token 与状态校验和只能检查模型一致性，不能当成真实执行凭据。

上述边界是刻意保留的：真实 LF 筛选有顺序及组合规则，ODP 共享会影响文件位置，锁与游标在事务后的行为还受运行设置影响，不能用一个通用默认值代替。[IBM 文件筛选](https://www.ibm.com/docs/en/i/7.5.0?topic=files-selecting-omitting-records-logical)、[共享 ODP 场景](https://www.ibm.com/docs/en/i/7.4.0?topic=resources-shared-open-data-pathscenario)、[事务控制说明](https://www.ibm.com/docs/en/i/7.6.0?topic=integrity-commitment-control)

## 可以直接运行与查看

从项目根目录运行，Python 3.10 或以上，仅标准库：

```sh
python3 poc/run_framework_paths.py \
  --source poc/fixtures/framework-path-v2/source \
  --contract poc/fixtures/framework-path-v2/runtime-contract.json \
  --case-set poc/fixtures/framework-path-v2/cases.json \
  --output .poc-data/framework-paths-v2-final
```

Windows 使用 `poc\run_framework_paths.bat` 传同样的参数；尚未在 Windows 实机验收。输出必须新建或为空，且不能与源码目录相互包含。不要重复使用已生成报告的目录。

一次可对照多组独立预期，生成 `framework-paths.md` 和 `framework-paths.json`。当前 15 个目录案例覆盖正常、过滤后空输入、业务跳过、锁冲突、提交失败、回滚失败、检查点失败、提交后读取失败、联机错误路由及两次运行之间的恢复。恢复案例使用前一案例真正由模型生成的已提交数据及检查点，没有手写伪 token。

分析单个获准场景可改用 `--entry`、`--scenario`、`--initial-values` 与 `--output-fields`；初始值从 JSON 对象读取。`--max-steps` 限制推进步数，`--extensions` 指定带后缀的源码范围，无扩展名成员仍被采集。本入口暂不提供旧接入入口的全部编码/格式选项；不支持的预处理、编码和布局仍可能形成边界。

报告展示的“到达终态”只属于给定场景；检查通过也只证明所列断言。当前 15 场景的 92 项预期全部通过，全库 675 项测试通过，见[验收报告](./reports/2026-09-12-framework-control-paths.md)。没有提供独立预期时报告明确标为未检查。

源程序文本存储与接口桥接仅支持 ASCII，避免把 Unicode 字符数误当成目标 PIC 的字节宽度；不模拟截断和隐式编码转换。未知分支、动态调用、缺少控制 COPY、别名、INITIAL 等额外程序生命周期条款、复杂转换及预算耗尽都会停下，不能绕过后继续给完整结论。停在边界时仍展示已知持久记录和待提交写入，并明确未证明后续结果。

## 失败时能看到的效果

提交失败但回滚成功：最终是提交错误，持久记录不变，pending 已清除。回滚也失败：最终状态是回滚错误，原始提交错误单独保留，pending 仍存在；CLOSE 不会被当成隐式回滚。检查点失败：前一步已提交的数据仍然有效，但没有新的可恢复检查点。

重启案例先提交 A001，再遇到后续读取失败；第二次用前次实际模型输出恢复，从 A001 之后读取，不重复保存 A001。契约、数据或访问路径不匹配则停止，而不是返回一个虚构的业务成功状态。
