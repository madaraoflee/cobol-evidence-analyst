## 一、最终目标怎样才算完成

最终目标仍是复杂、多样化 COBOL 系统的完整业务分析，不缩减为“找公式”或“解释单个程序”。第一轮先选择一个有代表性的复杂业务流程形成闭环，再扩展到更多流程和方言；“完整”必须相对于明确的业务问题、源码版本及资料范围验收，而不是承诺自动证明所有程序的所有运行行为。

例如用户问：**“批次为什么跳过这笔请求？联机保存失败后状态会怎样？涉及的金额如何计算？”** 一份合格结果必须同时说明：

1. 输入、输出和计算规则：各组成项、单位、条件、精度要求，以及不能确认的数值。
2. 跨程序流程与字段来源：入口、子例程、参数、查表/文件/配置如何参与，重复调用不能串线。
3. 正常与错误路径：错误在哪里产生、怎样传回、是否清零、是否提前退出或被后续覆盖。
4. 源码依据与资料缺口：关键结论可回到正确版本的文件行号；缺配置、缺定义或语法不支持时明确停下。
5. 可复核案例：正常、边界和失败案例与独立参考答案一致；区分手算期望、源码模型结果和实际运行结果。

用户不应必须先知道程序名，也不应手工运行多个分析脚本再自己拼答案。做到这五项，并通过真实模型与界面演练，才称为“该业务流程的完整分析能力交付”。

首批真实范围沿用现有产品章程的候选规模：一个业务域、约 30–50 个相关程序、20–30 个专家确认问题。它是待实际资料校准的范围，不是已经覆盖的数量，也不是全公司系统的覆盖承诺。

## 四、已交付的 T01 范围（历史记录）

### 目标

以已有入口、包装程序、共享子程序、结果映射和汇总样例为基础，证明在明确的源码模型范围内：**某个子程序返回业务错误后，各层怎样传递状态，最终输出是否清零，以及中途/返回后是否被覆盖。** 不先继续扩大程序数量。

### 本项补上的连接

原局部路径接口遇到正常 CALL 返回时，会把引用输出视为未知。T01 新增跨程序接口，进入子程序源码控制流、带入实参并在普通返回时逐层回写，再继续调用方和汇总程序。旧局部工具保持原范围，不假装已自动变成整业务分析器。

### 本项必须展示的验收案例

| 案例 | 应看到的分析效果 |
| --- | --- |
| 子程序正常返回业务错误状态 | 与“程序无法调用”的异常路径区分，状态逐层传递 |
| 同一子程序分别服务 A/B 两笔请求 | A 的参数和错误不能被错误拼到 B 的调用上下文 |
| 中途以内容复制方式传递参数 | 不误报为能写回更外层原字段 |
| 错误输出先清零，调用方随后写入非零 | 给出覆盖位置和完整模型路径，原安全验收失败 |
| 有递归、未决目标、缺失证据或预算截断 | 明示未证明的部分，不用局部成功替代整体成功 |
| 修改子程序后重新分析 | 使用新快照重算相关结果，不沿用旧摘要结论 |

交付物应包含一份可打开的报告、可追溯的机器结果、正例和反例验证，以及“本项仍不支持什么”。此项不要求解决全部正常金额精度、全部循环语义或模型自然语言回答；这些按后续任务验收，不能混报为 T01 已完成。

**T01 已达到受支持源码模型内的退出门槛。** 当时主检查 30/30、复制隔断 6/6；故意覆写的安全预期按预期失败；438 项回归通过。可直接查看 [主结果](../.poc-data/error-return-v5/result.md) 和 [覆写报警](../.poc-data/error-return-v5-regression/result.md)。正常金额仍为未知，COBOL 与真实业务仍未执行验收。
